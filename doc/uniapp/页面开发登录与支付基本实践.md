# Uni-App 页面开发、登录与支付基本实践

## 解决什么问题

Uni-App 复用 Vue 业务代码构建 H5、小程序和 App。首先需要页面能打开、接口能调用、登录能恢复、失败有反馈；平台能力不能只在开发工具中测试。

## 基本使用：页面与路由

创建与目标平台兼容的 Vue 3 Uni-App 项目，在 `pages.json` 注册列表和详情页；配置 tabBar 页与普通页。用 `uni.navigateTo` 打开普通页，`uni.switchTab` 切换 tabBar；`redirectTo` 替换当前页，`reLaunch` 重建页面栈。

```vue
<script setup>
import { ref } from 'vue'
import { onLoad, onUnload } from '@dcloudio/uni-app'
const title = ref('加载中')
let task
onLoad((options) => {
  task = uni.request({
    url: `https://api.example.com/items/${encodeURIComponent(options.id ?? '')}`,
    success: (response) => {
      title.value = response.statusCode === 200 ? response.data.name : '加载失败'
    },
    fail: () => { title.value = '网络错误' }
  })
})
onUnload(() => task?.abort())
</script>
<template><view>{{ title }}</view></template>
```

这是接口调用片段，需要真实 HTTPS 后端、小程序合法域名配置和响应数据校验。不要假设 H5 的 DOM、Cookie 和 localStorage 在所有目标端可用。页面 `onLoad/onShow` 与 Vue 组件生命周期有不同职责：首次参数初始化和每次显示刷新要分别设计。

## 常见场景：登录与失效恢复

1. 各平台取得合法临时凭证，小程序调用对应登录 API；由服务端与平台交换身份。
2. 服务端签发自己的业务会话，客户端仅保存必要凭证，所有数据权限在服务端验证。
3. 登录失效时最多启动一个刷新流程，其他请求等待其结果；刷新失败清理会话并引导登录。
4. 重放请求前检查是否可重试；原请求是支付、提交订单等操作时依赖业务幂等键。
5. 退出登录后清理与用户绑定的 store、缓存和路由，避免下一个账号读取前一账号数据。

第三方 appSecret、支付签名密钥不能放进客户端。跨端持久化通过统一存储适配层完成，安全级别按目标平台评估。

## 常见场景：支付完整链路

服务端创建订单 → 按目标平台生成支付参数 → 客户端调用平台支付 → 服务端验签接收异步通知 → 幂等更新订单 → 客户端查询最终状态。客户端回调“成功”只用于展示和触发查询，不能作为发货或记账依据。

超时或用户返回时显示“结果确认中”，不要直接再次扣款。通知可能重复、延迟和乱序；服务端使用唯一交易号、金额校验、状态条件更新，并通过对账修复遗漏。具体 API、商户资质和签名算法按平台当前文档接入。

## 跨端验证与进阶

| 基本能力 | 要验证的失败分支 | 再深入 |
|---|---|---|
| 页面与路由 | 返回、tabBar、深层页面、参数缺失 | 分包与生命周期 |
| 请求 | 弱网、取消、401、多请求刷新 | 并发控制、重试与幂等 |
| 上传 | 拒绝权限、超限、断线 | 压缩、恢复与服务端校验 |
| 支付 | 取消、未知结果、重复通知 | 状态机、验签与对账 |
| 多端发布 | 真机差异、包限制、审核 | 条件编译与原生适配层 |
