## Q1: 业务中如何抉择“确定性工作流 Agent”与“自主 ReAct Agent”？

### 📌 考察意图
考察应聘者是否具备工程理性和架构克制力。很多候选人盲目跟风，什么场景都套 ReAct / Auto-Agent，面试官通过此题直接分辨“Demo 级选手”与“生产级架构师”。

### ❌ 踩坑回答
> “自主 ReAct Agent 更高级、更有 AI 味道，能让大模型自由思考、自动调工具，所以未来肯定都要用 ReAct，工作流太死板了。”

### 💡 满分结构化回答模版
1. **结论先行**：业务选型绝非“技术越先进越好”，而是由**“任务的确定性边界、用户对延迟的容忍度、调用成本与数据安全等级”**四维象限共同决定的。
2. **核心痛点对比**：
   - **自主 ReAct Agent** 的优势在于**开放性未知探索**（如代码生成、复杂自动化审计），但致命伤是**多轮网络 RTT 导致延迟极高（2~5s+）、Token 账单不可控、存在死循环和工具参数幻觉风险**。
   - **确定性工作流（Pipeline）** 则由工程代码强掌控执行流，单次 LLM 往返，**首字延迟可压到 200ms 以内，100% 无死循环，权限控制与租户隔离坚不可摧**。
3. **架构融合折中**：在真实复杂系统中，最佳实践是**“外骨骼流水线（确定性代码兜底）+ 局部微决策智能体（仅在模糊意图消歧时受控调用 1~2 轮）”**。

### 🚀 结合本项目（时光寻忆）杀手锏
> “在我们的家庭云相册‘时光寻忆’项目中，面对的是高频 C 端移动端用户，用户对搜索的第一诉求是‘秒开（<300ms 首字）’和‘绝对不许看错照片’。如果用纯 ReAct，大模型在后台调 3 次相册检索工具就要耗费 4 秒，且容易在‘黄色/黄衣服/小黄鸭’词表之间反复打转陷入死循环。因此我们毫不犹豫选择了确定性流水线：由 TypeScript 代码在 20ms 内完成分词展开与数据库折叠聚合，LLM 仅在最后一步负责温情共情输出，完美兼顾了极致性能与温暖体验。”

## Q2: 生产环境 RAG 最常见的“明明检索到了正确文档，但大模型依然回答错误或产生幻觉”是什么原因？如何彻底解决？

### 📌 考察意图
考察对 RAG 全链路数据流和 Attention 机制缺陷的理解，看候选人是否具备“检索后治理（Post-Retrieval）”的实战经验。

### ❌ 踩坑回答
> “主要是大模型参数太小，换成 GPT-4 或者增大 Temperature 就行了。”

### 💡 满分结构化回答模版
导致该现象的核心根因通常有三点：
1. **Lost in the Middle（中间迷失）**：Transformer 注意力机制对 Context 的开头和结尾非常敏感，如果关键事实恰好夹在 10 个 Chunk 的正中间，极易被注意力权重稀释。
2. **噪声干扰与语义冲突**：召回的 Top-$K$ 文档中混入了强干扰项，大模型在矛盾信息中选择了错误的先验概率。
3. **Prompt 缺乏强引用围栏**：没有在 Prompt 中建立强制事实归因约束。

**工程治理四步法**：
- **第一步：重排序与两头重排**：引入 Cross-Encoder Reranker 打分，并将相关度最高的 Top 2 放置在 Context 的最前和最后，规避中间迷失。
- **第二步：上下文压缩（Context Compression）**：过滤掉相似度低于阈值（如 Cosine < 0.65）的冗余碎片，只喂精华。
- **第三步：强约束 Prompt 围栏**：要求大模型逐句引用标记 `[Doc#id]`，并明确注入“若信息不足必须诚实回答‘无法确认’”。
- **第四步：单票否决门禁（Visual / Logic Gate）**：在业务层引入前置逻辑过滤。

## Q3: 百万长上下文（Long Context，如 1M~2M）普及后，RAG 还有存在的必要吗？

### 📌 考察意图
考察对大模型前沿技术演进的客观认知，判断候选人是否会被厂商宣传带偏。

### ❌ 踩坑回答
> “长上下文出来后，RAG 已经没必要了，直接把几十万字全塞进去就行了，大模型都能读懂。”

### 💡 满分结构化回答模版
1. **结论**：**“长上下文并不能杀死 RAG，相反，长上下文拓宽了 RAG 的上限，两者是互补而非替代关系。”**
2. **长上下文无法替代 RAG 的三大物理死穴**：
   - **成本与延迟（Cost & TTFT）**：塞入 100 万 Token，单次请求成本高昂，且首字延迟（TTFT）通常飙升至 10~20 秒以上，高并发业务完全无法承受。
   - **大海捞针（Needle In A Haystack）的真实衰减**：学术 benchmark 的单针检索虽然能达 99%，但在“复杂多事实推理、多个冲突事实”场景下，长上下文召回率会呈现断崖式下跌。
   - **动态更新与私域权限穿透**：企业数据每秒都在变动，不可能每次修改一个字符就重传 100 万 Token；且长上下文无法做到针对不同员工的角色权限动态行级数据过滤。
3. **最佳工程组合**：**“用 RAG 负责外层粗筛与精准权限隔离（从 1 亿 Token 筛出 2 万 Token） ➔ 用长上下文模型负责这 2 万 Token 的深度对比与全局推理。”**

## Q4: 向量数据库底层原理是什么？HNSW 相比暴力搜索好在哪里？生产中如何选型？

### 📌 考察意图
考察对高维索引算法（ANN）底层原理与工程选型广度（Qdrant / Milvus / PGVector）的掌控力。

### 💡 满分结构化回答模版
1. **底层原理**：
   - 暴力检索（Flat）的时间复杂度为 $O(N \cdot D)$，数据量达百万级时延迟无法接受。
   - 工业界主流采用 **ANN（近似最近邻搜索）**，核心是 **HNSW（Hierarchical Navigable Small World，分层可导航小世界图）**。
   - **HNSW 机制**：借鉴跳表（Skip List）思想，在多层图结构中自上而下进行贪心搜索。顶层图稀疏、跨度大，实现快速粗定位；底层图密集，实现局部高精度搜索，时间复杂度降至 $O(\log N)$。
2. **四大向量数据库选型矩阵**：
   - **Qdrant**：Rust 原生开发，内存控制极佳，**最大的杀手锏是支持极其高效的 Payload 标量联合过滤**，极度适合多租户业务与中大规模（千万级）场景。
   - **Milvus**：分布式云原生架构，适合数亿至数十亿超大规模向量检索，运维复杂度较高。
   - **PGVector (PostgreSQL 插件)**：适合本身就重度依赖 Postgres 的中小团队，无需维护新组件；但千万级向量下内存与索引构建性能较弱。
   - **Chroma**：纯 Python 内存为主，适合单机原型实验，不建议作为高并发生产集群。

## Q5: 在 RAG 中为什么必须使用“混合检索（BM25 + Dense）”？RRF 融合算法是什么？

### 📌 考察意图
考察对多路召回策略（Multi-Channel Retrieval）及重排序算法数学逻辑的掌握。

### 💡 满分结构化回答模版
1. **单一向量检索的痛点**：稠密向量（Dense）擅长泛化语义理解（“开心” $\approx$ “喜悦”），但对**专有名词、人名、错误码、特定型号、精准色值**极不敏感，常发生“语义很近但事实完全不对”的翻车。
2. **混合检索架构**：
   - 通道 A：**Dense 稠密向量**（语义关联兜底）。
   - 通道 B：**Sparse / BM25 稀疏词法**（专有名词精确击中）。
3. **RRF 算法（Reciprocal Rank Fusion）**：
   由于向量余弦相似度（0~1）与 BM25 分数（无上限）不在同一个数值尺度，绝对无法直接加权相加。
   RRF 巧妙地**仅根据候选文档在各自通道中的“名次（Rank）”进行倒数累加**：
   $$RRF\_Score(d) = \sum_{m \in M} \frac{1}{k + r_m(d)}$$
   参数 $k$ 通常取 60。此算法无需调参、对极端高分具有天然平滑鲁棒性，是工业界多路融合的首选标准。

## Q6: 大模型在输出 JSON 结构化数据时不稳定，工程上有哪些治理手段？

### 📌 考察意图
考察生产环境下与大模型交互时的防御性编程经验。

### 💡 满分结构化回答模版
生产治理通常采取**“协议层 ➔ 引擎层 ➔ 校验层 ➔ 兜底层”**四级防护体系：
1. **协议层：启用官方 Structured Outputs**：
   现代 API（OpenAI / Qwen）提供了 `response_format: { type: "json_schema", json_schema: {...}, strict: true }`，利用受约束解码（Constrained Decoding / Logit Bias）在 Token 生成采样阶段直接屏蔽非法字符，从数学概率上强制 100% 语法合规。
2. **引擎层：Pydantic / Zod 运行时强校验**：
   使用 Pydantic 对模型输出进行反序列化与字段类型断言，若缺失必填字段立即拦截。
3. **校验层：防 Markdown 代码块包裹**：
   正则预处理：提取 ````json ... ```` 内的核心文本，剔除大模型自作聪明附带的开场白（如“好的，以下是为您生成的 JSON：”）。
4. **兜底层：有限次数自动重试（Correction Loop）**：
   若 JSON 校验失败，将报错信息附带到下一轮 Prompt 中让大模型针对性修复，重试上限通常设为 2 次。

## Q7: 什么是 LangGraph 的状态管理（State）与检查点（Checkpointer）？如何实现 Human-in-the-Loop？

### 📌 考察意图
考察对进阶智能体编排框架 LangGraph 底层原理的掌握，尤其是企业长流程审批与容灾能力。

### 💡 满分结构化回答模版
1. **State（全局状态）**：
   LangGraph 采用中心化的不可变数据字典（如 `TypedDict` 或 Pydantic）。图中的每个 Node（函数）只负责读取当前 State，并返回更新片段（Delta），由 LangGraph 自动合并状态。
2. **Checkpointer（检查点持久化机制）**：
   LangGraph 在每个 Super-step（节点执行完毕）都会将当前完整的 State 快照序列化写入持久化存储（如 Redis / Postgres）。这带来了两项核心超能力：
   - **容灾断点恢复与 Time Travel**：若服务器中断，重启后可从上一个检查点精准复活，甚至能回退到任意历史节点重新执行分支。
   - **Human-in-the-Loop（人工介入与审批）**：
     在敏感操作节点（如转账、删除数据）前配置 `interrupt_before=["delete_node"]`。图引擎执行到该节点会自动挂起并保存 State；等待前端管理员在后台点击“同意”或修改参数后，调用 `resume()` 恢复执行。

## Q8: 什么是 MCP（Model Context Protocol）？它与传统的 RESTful API / Function Calling 有何本质区别？

### 📌 考察意图
考察对 2025 年最新 AI 开源生态技术标准的跟进深度与前瞻性。

### 💡 满分结构化回答模版
1. **核心定位**：MCP 是由 Anthropic 发起的开源开放标准，致力于成为 **“AI 时代的 USB-C 接口”**，统一大模型宿主与本地/远程资源工具的交互。
2. **本质区别与代际跃迁**：
   - **传统 Function Calling**：开发者必须在自己的后端硬编码每个 Tool 的 Schema 与 HTTP 调用，平台与宿主互不兼容（为 Claude 写的插件无法直接塞给 Cursor 或 Antigravity）。
   - **MCP 协议**：将工具、数据与工作流抽象为 **Tools（执行动作）、Resources（只读上下文数据）、Prompts（模版）** 三大通用原语。采用 JSON-RPC 2.0 规范，只要写一个轻量 MCP Server，所有 MCP Host 客户端均能即插即用。
3. **安全与架构优势**：
   本地通过 `stdio` 管道进程通信，不暴露网络端口；天然支持跨语言与跨客户端复用，彻底终结了工具接入的生态碎片化。

## Q9: 智能相册检索中，如何解决“穿黄色衣服的铭铭”这类视觉属性与人名元数据混淆、相关性稀释的问题？

### 📌 考察意图
考察复杂多模态属性解耦检索实战，看应聘者是否有针对性调优领域算法的能力。

### 🚀 结合本项目（时光寻忆）杀手锏回答
> “这是我们在家庭相册项目中遭遇的最真实的物理 Bug。当用户提问‘穿黄色衣服的铭铭’时，相册中大量照片因为相册名称本身就叫‘铭铭’，在常规加权算法中拿到了保底及格分（15分），导致穿蓝色衣服或未被索引的照片统统挤进了召回候选集，而前端展示了 9 张照片，但大模型却只温情描述了其中真正穿黄衣服的 2 张，导致严重图文割裂。
> 我们的破局方案是引入**‘视觉准入门槛（Visual Gating）与一票否决权’**：
> 1. **属性正交解耦**：将分词提取出的强排他视觉属性（黄色衣服）与元数据属性（相册名‘铭铭’）分流。
> 2. **一票否决门禁**：若照片明确穿了冲突色（如蓝/白）且不包含目标色，无论人名多匹配，评分直接归零；未被索引的照片若备注中无明确目标色词也直接阻断。
> 3. **加权叠加**：只有在视觉门禁确认通过后，相册名与人物元数据才允许作为锦上添花累加分。
> 上线后，该类复合查询准确率直接从 22% 跃升至 100%，彻底消除了图文违和。”

## Q10: 当业务面对海量多分词查询时，ORM（Prisma/TypeORM）容易触发数据库（SQLite 64-Join）物理限制，底层如何做优化？

### 📌 考察意图
考察深入底层的全栈排障能力，看候选人遇到框架踩坑时是否能穿透 ORM 抽象直击本质。

### 🚀 结合本项目（时光寻忆）杀手锏回答
> “在我们的家庭云相册中，用户搜索经过词表泛化后通常会产生 20~30 个扩展 Token。Prisma 在处理多表外键关系关联时，如果直接在顶层数组平铺展开 OR 查询（例如：`tokens.flatMap(t => [{ album: { name: t } }, { aiIndex: { summary: t } }])`），Prisma 底层查询构建器会为每个条件生成独立的别名 `LEFT JOIN`，瞬间生成 72 个物理 Join，直接打穿了 SQLite 内核的硬限制 `SqliteError: at most 64 tables in a join` 导致服务崩溃。
> 我们的底层优化方案是**‘关系折叠聚合（Relational Folding）’**：
> 将多个 Token 的匹配条件收敛折叠到**单个关系对象内部的 OR 数组中**。无论外部扩展了 10 个还是 100 个分词，底层数据库始终仅生成 2 个干净稳定的物理 `LEFT JOIN`，彻底根除了 64-Join 崩溃隐患，且查询耗时下降了 60%。”

## Q11: 大模型流式输出（SSE）在生产端到端链路中如何设计高可用与背压（Backpressure）？

### 📌 考察意图
考察对网络协议、长链接性能损耗及全栈实时通讯的把控。

### 💡 满分结构化回答模版
1. **多事件通道解耦**：
   不要将所有数据混在单一 `data: text` 中。我们设计了正交事件分离：
   - `event: memories`：在流水线检索完成后第一时间单次推送照片卡片元数据（ID、缩略图 URL、拍摄时间），客户端立即绘制骨架屏与卡片；
   - `event: message`：后续大模型生成的温情文案以轻量增量 chunk 流式吐出；
   - `event: done` / `event: error`：规范的生命周期闭环。
2. **背压治理（Backpressure）**：
   在大模型极速推理（如 Qwen 达到 145 tok/s）时，若移动端主线程在处理 Markdown 渲染和图文混排，极易引发 UI 掉帧卡顿。
   - 服务端与客户端建立缓冲节流池（Buffer Throttle），按照每 30~50ms 聚合一次小 Chunk 刷新帧率，匹配移动端 60fps/120fps 渲染节奏；
   - 服务端监听 Node.js `res.on('drain')`，当底层 TCP 缓冲区满载时暂停上游模型拉取。
3. **断线与超时容灾**：
   配置 15 秒心跳包（`: ping\n\n`）防止网关（如 Nginx）断开闲置长链接；支持客户端断线重连带 `last_event_id`。

## Q12: 如何量化评测一个生产级 RAG 系统的准确率？介绍 Ragas 的核心四大指标与线上 AB 实验落地。

### 📌 考察意图
考察数据驱动思维与可观测性工程落地经验。

### 💡 满分结构化回答模版
1. **为什么拒绝人工抽检**：人工盲测费时费力且无法随 Prompt 和模型迭代自动化回归，必须建立基准测试集（Golden Dataset）与自动化评测管线。
2. **Ragas 核心四大指标及计算逻辑**：
   - **忠实度（Faithfulness）**：评估回答中的每一个陈述句是否均能由检索到的 Context 推导出来（利用 LLM 提取陈述句并进行蕴含推理断言，打分 0~1），衡量幻觉率。
   - **答案相关性（Answer Relevance）**：利用 LLM 根据生成答案反向预测可能的问题，计算反向生成问题与原始用户问题的向量余弦相似度，衡量是否答非所问。
   - **上下文精准率（Context Precision）**：衡量检索出来的文档中，真正相关的黄金信息是否排在最前列（计算类似 MAP 均值平均精度的加权排名分数）。
   - **上下文召回率（Context Recall）**：将真实标准答案（Ground Truth）中的事实句子与检索上下文比对，计算标准答案被覆盖的比例。
3. **线上 AB 实验与 CI/CD 门禁**：
   在代码提交或 Prompt 变更时，CI 自动跑 200 条经典 Query 的 Ragas 自动化测试。只有当 `Faithfulness ≥ 0.9` 且 `Context Recall ≥ 0.85` 时才允许合并部署；在线上灰度流量中，基于用户点赞/点踩与停留时长做端到端转化率验证。
