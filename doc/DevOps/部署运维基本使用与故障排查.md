# 部署运维基本使用与故障排查

## 解决什么问题

运维要让应用在目标机器能启动、能接流量、能观测、能恢复。先会进程、日志、网络、文件权限和容器，再学习 namespaces、cgroups 与 K8s 控制面。

## 基本使用：部署一个无状态服务

顺序是构建版本化产物 → 提供外部配置 → 启动 → 验证健康和核心接口 → 配置代理 → 验证日志 → 演练回滚。数据库、上传文件和持久状态不应依赖容器可写层。

```bash
docker version
docker run --name web-demo -d -p 8080:80 nginx:stable
docker ps
docker logs --tail 100 web-demo
curl -i http://localhost:8080/
docker inspect web-demo
```

此示例用于本机理解镜像、容器和端口映射。生产镜像应固定版本或 digest；TLS、配置、权限、资源和日志保留按环境设定。容器能运行不证明业务或数据库已健康。

## Linux 与容器的基本排查

| 目标 | 常用入口 | 如何解释 |
|---|---|---|
| 进程与 CPU | ps、top | 看进程/线程和持续趋势，不凭一个瞬间判断 |
| 内存 | free、进程指标、容器限制 | 主机剩余内存与 cgroup 内存限制是不同口径 |
| 磁盘 | df -h、df -i、du | 磁盘容量与 inode 都可能耗尽 |
| 端口 | Linux 上 ss -lntp | 是否监听、绑定地址、权限和防火墙 |
| 日志 | 服务日志、journalctl、docker logs | 找首次错误和时间关联，限制输出避免泄露秘密 |
| 容器资源 | docker stats、inspect | OOMKilled、重启、挂载和退出码 |
| 请求链路 | curl、代理访问/错误日志 | 逐段确认客户端→代理→应用→数据库 |

文件权限、用户身份、环境变量和工作目录经常造成“本机正常，部署失败”。不要遇到权限错误就把目录改成 777，也不要将密钥复制进镜像。

## 从 Docker 到 K8s 的基本使用

先使用 Docker Compose 验证多服务配置和依赖；需要多节点调度、声明式副本和统一治理时再使用 K8s。

```bash
kubectl get pods -n demo
kubectl describe pod <pod-name> -n demo
kubectl logs <pod-name> -n demo --tail=100
kubectl logs <pod-name> -n demo --previous
kubectl get events -n demo --sort-by=.metadata.creationTimestamp
kubectl rollout status deployment/web -n demo
```

Pod 名称和 namespace 用实际环境值。Pending 先看调度、资源和 PVC；CrashLoopBackOff 看上一轮日志与退出原因；Running 但不通看 readiness、Service endpoints、端口和网络；OOMKilled 查限制、峰值和应用分配行为。

## 常见场景：发布与回滚

Readiness 控制是否接流量，liveness 检测是否需要重启，startup probe 保护长启动阶段。滚动更新还要有足够容量、正确探针、优雅终止与连接排空；`maxUnavailable: 0` 本身不能保证请求零失败。数据库结构、配置和消息格式必须允许新旧版本共存。

监控至少包含请求量、错误率、p95/p99、CPU/内存、连接池、队列和磁盘。告警要对应用户影响和明确处置动作。备份必须验证恢复；重启不是根因修复。

## 面试递进

| 基础题 | 场景追问 | 深入要点 |
|---|---|---|
| 镜像和容器区别？ | 容器重建后文件去哪了？ | 可写层、volume、不可变产物 |
| 容器不通怎么查？ | 应用正常但代理 502？ | 监听、端口、DNS、代理和上游 |
| K8s 怎么发布？ | 为什么滚动更新仍失败？ | readiness、优雅终止、容量和兼容性 |
| requests/limits 怎么配？ | 主机内存够却 OOMKilled？ | cgroup、QoS 和应用资源需求 |
| CI/CD 做什么？ | 怎么回滚有数据库变更的版本？ | 质量门禁、产物追溯、兼容迁移 |
