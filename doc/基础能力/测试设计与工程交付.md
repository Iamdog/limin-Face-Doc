# 测试设计与工程交付

## 解决什么问题

知识点能背出来，不代表代码在失败和升级后仍正确。测试用于把预期行为变成可重复验证的证据，交付流程用于把代码可靠地送到目标环境。

## 基本使用：先为一个业务规则写用例

以“库存不足不允许下单”为例，先列输入与输出：库存 0、库存 1、重复请求、并发请求、数据库失败。纯规则用单元测试验证；唯一约束、事务和并发更新用真实数据库的集成测试验证；页面成功、空数据、错误、返回与重复点击用 UI 测试验证。

单元测试使用 fake/mock 隔离外部依赖，集成测试验证真实边界；mock 返回成功不能证明网络协议、SQL 或事务真的正确。不要为了覆盖率而只断言实现内部调用了哪个方法。

## 工程交付基本能力

| 能力 | 最小实践 | 常见追问 |
|---|---|---|
| Git | 分支、diff、commit、冲突解决、revert | revert 与 reset 对共享历史的影响 |
| 依赖管理 | 锁文件、工具链版本、可重现构建 | 本机正常 CI 失败先查版本和环境 |
| 单元测试 | 验证规则和边界 | mock 会掩盖哪些真实问题？ |
| 集成测试 | API、数据库、消息、缓存 | 数据隔离、清理、真实故障如何复现？ |
| 契约测试 | 请求/响应结构和兼容性 | 多端或多服务不同步发布怎么办？ |
| 性能测试 | 固定流量模型、记录 p95/p99 与错误率 | 测试瓶颈是否在压测机、连接池或数据库？ |
| 发布 | 构建产物、灰度、探针、回滚 | 数据结构和配置是否支持旧版本？ |
| 排查记录 | 现象、证据、假设、验证、修复 | 为什么证明是根因而非相关性？ |

## 常见场景：线上故障转回归用例

先用最小输入重现故障，保留修复前会失败、修复后会通过的用例。例如分页重复数据要验证稳定排序与游标边界；超时重试重复扣款要验证同一幂等键的并发请求和响应丢失后重试。只在测试里给接口加固定 sleep 通常不能稳定制造竞态，应通过屏障或可控假依赖安排执行顺序。

## 再深入：测试策略与取舍

用较多快速单元测试保护业务规则，用较少集成测试覆盖关键协议和数据边界，用少量端到端测试保护核心用户流程。比例取决于项目风险和可测试性。异步和分布式系统还需要注入超时、重复消息、乱序、宕机、恢复等故障。

可用性通过错误率和用户流程验证，性能通过分位延迟和资源验证。平均延迟、单次成功和截图都不足以证明整体正确。

## 面试与完成标准

能说明一条测试为什么必要、覆盖哪种失败、未覆盖什么；能说明发布如何回滚、配置和数据如何兼容；能拿出一次故障的证据链。每个专题练习保留代码、运行环境、预期结果和至少一个失败分支，之后再用原理解释观察结果。
