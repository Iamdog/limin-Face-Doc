# 微信小程序社招高频核心面试 30 题全景通关

本专题面向 **3~5 年及以上前端/跨平台工程师**，汇总一线大厂在微信小程序领域考核频次最高、深度挖掘最严苛的 **30 道核心面试连环问**，全面覆盖双线程架构底层、setData 性能调优、组件通信、分包隔离、生命周期机制与安全风控。

---

## 1. 架构与运行原理（第 1 ~ 10 题）

### Q01: 简述微信小程序的双线程模型及为什么要这样设计？
> **答题要点**：
> 逻辑层（JSCore/V8）与渲染层（每个页面一个独立的 WebView）相互隔离，通信依赖 Native 原生 JSBridge 桥接。
> **设计原因**：1. **安全性**：杜绝开发者在脚本中任意操纵 DOM、跳转外链或盗取敏感 Cookies；2. **性能与体验**：渲染层与逻辑层各司其职，长时间的逻辑运算不会导致界面渲染完全被冻结（卡死）。

### Q02: 为什么小程序中无法使用 jQuery、Vue 或 React 这种直接操作 DOM 的库？
> **答题要点**：
> 逻辑层运行在纯粹的 JS 引擎内，宿主环境中不存在任何 `window`、`document`、`navigator` 对象，所有 DOM 相关的标准 Web API 均未提供，因此依赖真实 DOM 树操作的传统库全部无法运行。

### Q03: 小程序启动过程包括哪些阶段？冷启动与热启动的区别？
> **答题要点**：
> - **冷启动**：用户首次打开或小程序被微信后台主动销毁后重新打开，需经历：下载基础库/代码包 $\to$ 启动双线程 $\to$ 初始化 Page 与逻辑层 $\to$ 首屏渲染；
> - **热启动**：用户离开小程序进入后台，5秒内再次切回，直接从内存唤起，只触发 `App.onShow` 和 `Page.onShow`，无需重新下载和初始化。

### Q04: 页面生命周期的完整执行顺序是怎样的？
> **答题要点**：
> `onLoad`（仅执行一次，用于解析页面入参）$\to$ `onShow`（页面每次可见时执行）$\to$ `onReady`（页面初次渲染完成，可进行节点查询）$\to$ `onHide`（页面切入后台）$\to$ `onUnload`（页面销毁）。

### Q05: 路由跳转 `wx.navigateTo`、`wx.redirectTo`、`wx.switchTab`、`wx.reLaunch` 的区别？
> **答题要点**：
> - `navigateTo`：保留当前页面，新页面压入页面栈（页面栈上限 10 层）；
> - `redirectTo`：关闭当前页面，新页面替换当前栈帧；
> - `switchTab`：专用于跳转 TabBar 页面，并关闭所有非 TabBar 页面；
> - `reLaunch`：清空所有页面栈，只保留目标页面。

## 2. 性能优化与数据流（第 11 ~ 20 题）

### Q06: setData 传输数据的上限是多少？为什么大对象会导致卡顿？
> **答题要点**：
> 单次传输数据官方建议不超过 256KB（最大不得超过 1MB）。数据必须经过 `JSON.stringify` 序列化跨线程传递，体积过大会导致逻辑层 CPU 飙升、传输管道拥堵，且渲染层需要耗费大量时间执行反序列化和全局 Virtual DOM 树 Diff。

### Q07: 如何进行 setData 的差量局部更新？
> **答题要点**：
> 使用字符串属性路径表达式替代全量替换。例如：`this.setData({ ['list[' + index + '].title']: '新标题' })`，只将变动的具体字段推入传输流。

### Q08: WXS 的执行环境与优势是什么？与普通 JS 有什么限制？
> **答题要点**：
> WXS 直接运行在渲染层 WebView 内，能直接捕获手势事件并修改组件样式，免去了跨线程通信；
> **限制**：WXS 语法是类 ES5 的独立语法，不能使用 ES6+ 高级特性，也不能调用微信绝大部分原生 API（如 wx.request）。

### Q09: 独立分包（Independent Subpackages）的特性与使用场景？
> **答题要点**：
> 独立分包可以在不下载主包的情况下直接秒开启动。常用于裂变海报页、活动落地页，以极低的等待时间获取极致转化率。但其自身不能依赖主包的任何样式和公共模块。

### Q10: 小程序中的自定义组件通信方式有哪些？
> **答题要点**：
> 1. 父传子：`properties` 属性绑定；
> 2. 子传父：`this.triggerEvent('myevent', myEventDetail)` 自定义事件冒泡；
> 3. 获取组件实例：`this.selectComponent()`；
> 4. 全局状态共享：基于发布订阅模型或全局 App 实例。

## 3. 业务实战与安全风控（第 21 ~ 30 题）

### Q11: 微信小程序的登录凭证 code 为什么不能重复使用？
> **答题要点**：
> `code` 是一次性的临时票据（5分钟有效期）。微信服务端在通过 `code2Session` 置换为 `openid` 后，该 code 立即失效，防止重放攻击。

### Q12: 微信支付中，前端 `wx.requestPayment` 成功后为什么不能直接判定交易完成？
> **答题要点**：
> 前端返回仅代表客户端本地收银台交互成功，极易被恶意劫持或通过抓包篡改。真实交易状态必须由商户后台接收微信支付官方发送的带公钥签名的异步 Webhook 回调通知（验签解密）为准。

### Q13: 如何突破小程序的 2MB 主包体积限制？
> **答题要点**：
> 1. 配置 `subpackages` 分包加载，主包仅保留 TabBar 页面和核心公共库；
> 2. 静态大图全面迁移至 CDN / 云存储；
> 3. 开启 `preloadRule` 分包预下载，抹平分包跳转白屏延迟。

### Q14: 如何防止用户在网络波动时快速重复点击按钮造成重复提交订单？
> **答题要点**：
> 1. 前端按钮添加防抖（Debounce）或在提交中加入 `loading` 禁用态（`disabled`）；
> 2. 后端生成唯一防重请求 Token（Idempotent Token），结合 Redis 分布式锁 `setNX` 做接口级防刷。

### Q15: 小程序与 WebView（H5）通信的机制与时机？
> **答题要点**：
> H5 通过接入 `weixin-js-sdk` 调用 `wx.miniProgram.postMessage({ data: ... })` 向小程序发消息；但该消息**只会在特定时机被触发接收**：仅在小程序后退、组件销毁或分享时才会由 `<web-view>` 的 `bindmessage` 事件捕获，非实时双向通信。
