# 系统设计基本方法与可靠性实践

## 解决什么问题

系统设计用于在功能、容量、成本和可靠性约束下组织服务与数据。先设计一个可以完成业务的单体，再通过测量和失败场景判断需要增加什么组件。

## 基本使用：设计订单系统

先问清下单、支付、取消、库存和查询的规则；定义状态和资源权限；用单体服务与数据库事务完成创建订单、条件扣减库存和唯一请求号。返回 orderId，提供状态查询。先证明不会重复下单和超卖，再估算吞吐。

```text
客户端 → 鉴权与校验 → 业务事务 → 数据库
                          ↓
                    订单状态查询
```

需要异步通知时，在同一数据库事务写订单和 outbox 事件，独立任务投递消息，消费端按事件 ID 幂等处理。发布者可能投递重复消息，因此 outbox 不是“全链路恰好一次”的自动保证。

## 容量估算：每个数字有依据

日请求数 = DAU × 每用户操作数 × 每操作请求数；平均 QPS = 日请求数 / 86400；峰值来自流量曲线和突发目标。并发在稳定条件下可近似为吞吐 × 平均服务时间。存储要考虑记录、索引、副本、日志和增长。

某种 CPU 配置没有固定 QPS，数据库也没有一个普遍的“单机极限”。通过相近业务和数据规模压测，观察 p95/p99、错误率、连接池、CPU/IO、锁等待和队列，才能确定容量。数量级估错可能改变方案，必须检查假设和敏感性。

## 常见场景：一步步升级

| 证据 | 首先改什么 | 何时升级 |
|---|---|---|
| 查询慢 | SQL、索引、返回字段、分页 | 热点重复读明显再加缓存 |
| 同步任务拖慢响应 | 分离耗时任务、持久任务表 | 重试/吞吐/多消费者需求增加再加 MQ |
| 单实例故障 | 多副本、健康检查、状态外置 | 再做跨可用区与故障切换 |
| 热点写冲突 | 条件更新、幂等、限流 | 再评估排队、分片与预扣 |
| 团队发布互相影响 | 模块边界与契约 | 再按稳定边界拆服务 |

## 可靠性和一致性必须回答

超时后结果可能未知，客户端用幂等键重试并查询最终状态。消息可能重复和乱序，消费者结合唯一键、版本或状态条件更新。重试配置次数、退避、抖动和总预算；不可无限重试放大故障。

限流保护容量，熔断暂停调用持续失败的依赖，隔离避免一个依赖耗尽所有线程/连接。降级必须保持业务安全，例如推荐可以返回默认内容，支付不能随意返回成功。

定义 SLI（成功率和延迟等实际指标）、SLO（目标）、RPO/RTO（恢复目标）；建立备份、恢复和切流演练。跨区多活还需要明确写入归属、冲突、延迟和网络分区行为，不能只画两个机房。

CAP 描述网络分区发生时一致性与可用性的取舍，不能脱离分区条件简单说“任取两项”。缓存和数据库的最终一致性也必须给出允许窗口、失败补偿和校验机制。

## 经典场景训练与面试递进

| 题目 | 从基本功能开始 | 再追问 |
|---|---|---|
| 短链接 | 生成、唯一性、跳转、过期 | 碰撞、缓存、恶意链接、统计与容量 |
| 消息通知 | 事件持久化、发送、状态查询 | 重复、顺序、失败补偿、频控 |
| 文件存储 | 上传、元数据、授权下载 | 分片、内容校验、对象存储与 CDN |
| 订单支付 | 状态机、条件更新、幂等 | 异步回调、对账、超时未知与一致性 |
| 多级缓存 | 数据源和读写流程 | 失效传播、陈旧窗口、热点和雪崩 |

回答顺序固定为需求 → 基本链路 → 数据约束 → 容量 → 瓶颈与升级 → 故障与取舍 → 验证。之后读 [幂等](/doc/SystemDesign/幂等性设计与重复请求治理)、[限流](/doc/SystemDesign/限流算法与分布式限流实战)、[秒杀](/doc/SystemDesign/高并发秒杀系统全链路设计)。
