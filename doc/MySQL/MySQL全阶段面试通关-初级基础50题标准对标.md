# MySQL全阶段面试通关-初级基础50题标准对标

本篇面向 0~2 年初级后端开发、数据分析与数据库管理工程师，系统梳理 MySQL 核心架构基础、SQL 语言分类、数据类型精准选型、五大约束规范、单表检索与过滤、**分组查询（GROUP BY）与聚合函数**、常用内置函数、多表连接基础、简单事务提交回滚以及新手高频 Error 排查等 50 道高频面试标准真题与对标解析。

---

### Q1: 简述 MySQL 的逻辑三层架构及其各自核心职责。
**答**：
1. **连接层（Connection Layer）**：负责客户端连接管理、TCP 握手、身份认证（用户名/密码/Host 白名单）与安全权限核验；
2. **Server 核心层（SQL Layer）**：跨存储引擎的核心中枢，包含 SQL 词法语法解析器（Parser）、预处理器（Preprocessor）、基于代价的查询优化器（Optimizer）与执行器（Executor），以及所有内置函数；
3. **存储引擎层（Storage Engine Layer）**：插件式架构，负责数据的底层物理存储与提取，遵循统一的 handler 接口规范。最常用的是 InnoDB（支持事务/行锁）与 MyISAM。

---

### Q2: MySQL 为什么采用“插件式存储引擎”架构？
**答**：
插件式架构实现了“计算与存储物理分离”。Server 层专注于通用的 SQL 解析、执行计划生成与权限控制，而存储引擎可根据不同业务特性自由拔插替换（如高并发 OLTP 选用 InnoDB，纯静态全量分析选用 MyISAM 或 Memory，海量归档选用 Archive），极大增强了数据库的扩展性与灵活性。

---

### Q3: 为什么 MySQL 8.0 彻底移除了“查询缓存（Query Cache）”？
**答**：
1. **命中率极低且极其脆弱**：只要一张表发生了一笔任意 `INSERT`、`UPDATE` 或 `DELETE`，该表关联的所有查询缓存必须全部失效并被强行清空；在现代高频写入的业务中，命中率几乎为 0；
2. **严重的全局锁竞争**：所有读写线程访问 Query Cache 时必须争抢全局互斥锁，成为严重的吞吐瓶颈。现代架构统一将缓存后置到应用侧 Redis。

---

### Q4: 简述 SQL 语言的四大主要分类（DDL、DML、DQL、DCL）及其代表语句。
**答**：
- **DDL（Data Definition Language，数据定义语言）**：用于定义或修改数据库结构。如 `CREATE`、`ALTER`、`DROP`、`TRUNCATE`；
- **DML（Data Manipulation Language，数据操作语言）**：用于增删改数据记录。如 `INSERT`、`UPDATE`、`DELETE`；
- **DQL（Data Query Language，数据查询语言）**：用于检索数据。如 `SELECT`；
- **DCL（Data Control Language，数据控制语言）**：用于权限与事务控制。如 `GRANT`、`REVOKE`、`COMMIT`、`ROLLBACK`。

---

### Q5: 为什么在显式开启的事务中执行 `ALTER TABLE` 无法通过 `ROLLBACK` 回滚？
**答**：
所有 DDL 语句在 MySQL 内部都具备**“隐式提交（Implicit Commit）”**机制。当执行到 DDL 语句的第一行时，系统会自动强行触发一次 `COMMIT`，将当前事务前序的所有 DML 持久化；DDL 执行完成后再次隐式 `COMMIT`。因此 DDL 不受事务保护，无法被撤销回滚。

---

### Q6: 详述 `DELETE`、`TRUNCATE` 与 `DROP` 的核心区别。
**答**：
1. **语言属性与事务**：`DELETE` 是 DML 语句，逐行删除并记录完整 undo log，可安全回滚；`TRUNCATE` 和 `DROP` 是 DDL，隐式提交，不可回滚；
2. **执行速度**：`DROP` 最快（直接删文件）；`TRUNCATE` 极快（释放数据页重建空根页）；`DELETE` 最慢（逐行扫描与打标记）；
3. **磁盘空间释放**：`DELETE` 仅将行标记为可复用垃圾链表，**.ibd 文件不缩小**；`TRUNCATE` 立即释放空间重置为初始大小；`DROP` 彻底删除物理文件；
4. **自增主键**：`TRUNCATE` 强制重置自增 ID 为 1，`DELETE` 保持现有计数器继续递增。

---

### Q7: 整型中 `TINYINT`、`INT`、`BIGINT` 占用的存储字节与适用场景是什么？
**答**：
- `TINYINT`：占用 1 字节（有符号 -128~127，无符号 0~255），适合状态值（`status`）、枚举类型与逻辑删除标识；
- `INT`：占用 4 字节（无符号约 0~42.9 亿），适合单表千万级以内的绝大多数业务主键或外键 ID；
- `BIGINT`：占用 8 字节（无符号约 0~1844 亿亿），适合海量流水账单表主键与分布式雪花算法（Snowflake ID）。

---

### Q8: `INT(4)` 与 `INT(11)` 在底层物理存储上有何区别？括号里的数字代表什么？
**答**：
**物理存储完全没有任何区别**，两者在底层都恒定占用 4 个字节，可存的最大整数完全相同。
括号里的数字仅代表**“显示宽度（Display Width）”**，且仅在显式声明了 `ZEROFILL` 时才会生效（不足位数时在左侧补 0 显示）；若未声明 `ZEROFILL`，该数字无任何物理意义。在 MySQL 8.0.17+ 中，整型的显示宽度语法已被官方正式废弃。

---

### Q9: 为什么处理涉及金钱、价格、财务核算的字段，绝对严禁使用 `FLOAT` 或 `DOUBLE`？
**答**：
`FLOAT` 和 `DOUBLE` 是基于 IEEE 754 标准的二进制浮点数，很多十进制小数（如 0.1）在二进制下是无限循环小数，强制截断后会产生精度丢失与微小误差，累加后导致账目不平。财务字段必须强制使用 **`DECIMAL(M, D)`** 定点数类型，底层采用紧凑十进制整型数组存储，确保 100% 精确计算。

---

### Q10: `CHAR(N)` 与 `VARCHAR(N)` 的核心区别是什么？各自适用什么场景？
**答**：
- `CHAR(N)`：固定长度字符串，长度不足 $N$ 时右侧自动用空格填充补齐；适合存储长度绝对固定的字段（如 32 位 MD5 哈希、UUID、身份证号、定长编码），检索效率极高且无碎片；
- `VARCHAR(N)`：变长字符串，按实际内容长度存储，且额外消耗 1~2 字节存储长度前缀；适合存储长度动态波动的文本（如用户名、地址、标题），最大化节省磁盘与 Buffer Pool 空间。

---

### Q11: `DATETIME` 与 `TIMESTAMP` 有何核心区别？为什么推荐使用 `DATETIME`？
**答**：
1. **取值范围**：`TIMESTAMP` 仅能存到 **2038-01-19 03:14:07**（32位时间戳溢出问题），而 `DATETIME` 可存至 9999 年；
2. **时区相关性**：`TIMESTAMP` 写入时转为 UTC，读取时按当前会话时区转换，时区变动易引发数据漂移；`DATETIME` 是绝对时间，与系统时区完全无关；
3. **存储空间**：`DATETIME` 占 5 字节（5.6+），`TIMESTAMP` 占 4 字节。大厂普遍推荐使用 `DATETIME`。

---

### Q12: 关系型数据库的三大完整性约束包含哪些？
**答**：
1. **实体完整性（Entity Integrity）**：要求表中每一行记录必须是可唯一标识的，通过 `PRIMARY KEY` 或 `UNIQUE` 约束实现；
2. **参照完整性（Referential Integrity）**：定义表与表之间的外键关系与级联规范，通过 `FOREIGN KEY` 实现；
3. **域完整性（Domain Integrity）**：限制特定列的数据输入必须符合预设规则，通过数据类型、`NOT NULL`、`DEFAULT` 与 `CHECK` 实现。

---

### Q13: 为什么大厂普遍要求建表字段显式声明 `NOT NULL DEFAULT ...`？允许为 `NULL` 有什么危害？
**答**：
1. **存储开销**：InnoDB 行记录头部必须额外占用 1 个或多个字节的“NULL 值位图（NULL Bit Mask）”；
2. **统计陷阱**：`COUNT(列名)` 会自动排除该列为 NULL 的记录，极易导致业务统计数据失真；
3. **比较三值逻辑**：SQL 中 `NULL` 不等于任何值（包括 `NULL = NULL` 结果也是 `UNKNOWN`），只能用 `IS NULL` 判定，极易诱发逻辑 Bug。

---

### Q14: 为什么大厂强制禁止在数据库层面建立物理外键（`FOREIGN KEY`）？
**答**：
1. **并发锁性能崩塌**：插入或更新子表时必须向父表申请共享锁（S 锁），极易导致高并发下的锁等待超时与大面积死锁；
2. **阻碍分布式分库分表**：物理外键无法跨数据库实例生效，一旦做微服务垂直分库或水平分库分表，物理外键彻底瘫痪；
3. **运维与导数困难**：批量导入历史数据必须严格按父子拓扑顺序执行，且级联删除容易引发连环误删惨案。业务一致性必须由应用层代码与分布式事务保证。

---

### Q15: 自增主键为什么强烈建议使用单调递增的整型（如 `BIGINT AUTO_INCREMENT`）而非随机 UUID？
**答**：
InnoDB 的物理聚簇索引底层是一棵 B+ 树：
- 递增 ID 写入时始终在当前物理页尾部顺序追加，数据页填充率高达 95%+，属于极速顺序 I/O；
- 随机 UUID 导致每次插入都在 B+ 树中间随机寻址，频繁触发**数据页分裂（Page Split）**与物理数据移动，磁盘空间利用率断崖式跌至 50%，产生海量碎片与慢速随机 I/O。

---

### Q16: 逻辑删除（软删除）表中，如何处理唯一索引与被删除数据的冲突？
**答**：
将删除标记由传统的 `0/1` 改为记录主键 ID 或微秒时间戳：
定义 `delete_token BIGINT DEFAULT 0`；未删除时固定为 0，删除时将 `delete_token` 置为该行自身的 `id`，并建立复合唯一索引 `UNIQUE KEY (biz_key, delete_token)`。这样即使相同业务键被删除多次，由于每次删除的 `delete_token` 绝对唯一，彻底消除唯一键冲突。

---

### Q17: 为什么在 SQL 规范中强制禁止书写 `SELECT *`？
**答**：
1. **丧失覆盖索引优化**：无法利用二级索引直接返回数据，强制触发回表（Random I/O）查询聚簇索引；
2. **浪费网络与内存**：将表中的冗余大字段（如 TEXT、JSON）无脑拉入内存 Buffer Pool，并通过网卡传输，极易打爆网络带宽；
3. **破坏架构健壮性**：表结构追加字段可能直接引发应用层 OOM 或对象映射异常。

---

### Q18: 在 WHERE 条件中，比较运算符 `=` 与 `<>` / `!=` 的核心区别与索引影响是什么？
**答**：
- `=`：精确等值查找，优化器能以极低成本直接走 B+ 树二分检索（`const` 或 `ref` 级别）；
- `<>` / `!=`：不等于查找，在绝大多数场景下由于无法利用 B+ 树的单调有序区间，优化器会直接放弃索引扫描，退化为全表扫描（`ALL`）。

---

### Q19: `BETWEEN ... AND ...` 是开区间还是闭区间？
**答**：
**严格全闭区间 `[A, B]`**，不仅包含两端的边界值，且必须满足前小后大（即 `A <= B`）；若写成 `BETWEEN 500 AND 100`，由于逻辑矛盾，查询结果将永远返回空。

---

### Q20: 为什么 `WHERE id NOT IN (1, 2, NULL)` 会永远返回空结果集（Empty Set）？
**答**：
根据 SQL 德·摩根定律，`NOT IN` 展开后等价于 `(id != 1) AND (id != 2) AND (id != NULL)`。在 SQL 三值逻辑中，任何值与 `NULL` 的不等号比较结果恒为 `UNKNOWN`。整个表达式因包含 `AND UNKNOWN` 而永远无法为 `TRUE`，被优化器判定为永假条件。

---

### Q21: 模糊查询中，`LIKE 'abc%'` 和 `LIKE '%abc%'` 在执行机制上有何本质差异？
**答**：
- `LIKE 'abc%'`（前缀匹配）：字符串前缀是确定的，优化器可以利用 B+ 树索引的字典序执行二分查找（Index Range Scan 范围索引扫描）；
- `LIKE '%abc%'`（全模糊匹配）：以通配符开头，优化器无法获知起始查找位置，普通 B+ 树索引彻底失效，强制退化为全表扫描。

---

### Q22: `ORDER BY` 多列排序时的执行规则是怎样的？
**答**：
严格遵循从左到右的优先级：`ORDER BY col1 ASC, col2 DESC` 表示首先严格按 `col1` 升序排列；只有当存在多行记录的 `col1` 值完全相同时，这部分记录内部才继续按照 `col2` 降序排列。

---

### Q23: 为什么执行带有 `ORDER BY` 的分页查询时，建议最后追加主键 `id` 排序？
**答**：
防止**排序不稳定导致翻页数据重复或遗漏**。如果业务排序字段存在大量相同的值（如同一秒创建的时间），MySQL 内部排序算法无法保证物理读取的确定性顺序，翻页时可能导致某条记录在第 1 页和第 2 页同时出现。追加唯一主键（`ORDER BY create_time DESC, id DESC`）能确保排序结果绝对唯一稳定。

---

### Q24: 详述 `WHERE` 与 `HAVING` 的核心区别与执行时序。
**答**：
1. **执行时机**：`WHERE` 发生在 `GROUP BY` 分组之前，对原始物理行执行初筛；`HAVING` 发生在 `GROUP BY` 聚合之后，对分组聚合后的指标进行二次过滤；
2. **聚合函数支持**：`WHERE` 内部绝对禁止使用聚合函数；`HAVING` 专门用来对聚合函数计算结果（如 `HAVING COUNT(*) > 5`）做条件过滤；
3. **性能差异**：能写在 `WHERE` 的条件绝不写在 `HAVING`，在分组前提前裁剪数据可极大减少内存临时表开销。

---

### Q25: `COUNT(*)`、`COUNT(1)` 与 `COUNT(列名)` 有何本质区别？哪一个性能最好？
**答**：
- `COUNT(*)`：符合 SQL-92 标准的统计总行数语法，包含 NULL 行；InnoDB 底层做了专门优化，直接遍历最小的二级索引树累加计数器；
- `COUNT(1)`：等价于 `COUNT(*)`，性能毫厘无差；
- `COUNT(列名)`：**自动忽略该列为 NULL 的记录**，只统计非 NULL 数量，性能最慢（因为要从数据行中逐行取出该字段做判空操作）；
- **结论**：统计全表总行数，**首选且强推 `COUNT(*)`**。

---

### Q26: `SUM(列名)` 和 `AVG(列名)` 在处理 NULL 值时有什么暗坑？
**答**：
1. `SUM(列名)`：自动忽略 NULL。若全表为空或所有值全为 NULL，`SUM` 返回 `NULL` 而非 `0`（业务层需使用 `IFNULL(SUM(...), 0)` 兜底）；
2. `AVG(列名)`：计算平均值时，**分母会自动剔除 NULL 所在的行**！例如 5 名学生中 1 人缺考为 NULL，`AVG` 的分母算的是 4 而非 5，导致平均分被非正常拉高。

---

### Q27: 为什么升级到 MySQL 5.7+ 后，很多分组查询会抛出 `Error 1055 (ONLY_FULL_GROUP_BY)`？
**答**：
为了捍卫关系代数的数学确定性。在 `ONLY_FULL_GROUP_BY` 模式下，`SELECT` 投影列表中出现的字段，**必须要么包含在 `GROUP BY` 子句中，要么被聚合函数包裹**。严禁出现未参与分组且未被聚合的“自由列”，防止由于该组有多条明细而随机随机抽取某行产生非确定性逻辑 Bug。

---

### Q28: 线上遇到 1055 报错，为什么严禁直接通过修改 `sql_mode` 移出 `ONLY_FULL_GROUP_BY`？应该如何优雅重构？
**答**：
- 暴力修改 `sql_mode` 属于“掩耳盗铃”，会在整个数据库级别破坏数据一致性校验，导致未来其他业务查出不可预测的乱序脏数据；
- **优雅重构 SOP**：
  1. 若该列确实无需精准对齐，在 SELECT 中显式包裹 `ANY_VALUE(col_name)`；
  2. 若该列需要精准对齐，通过子查询先分组聚合出指标，再通过 `INNER JOIN` 关联回主表取明细；
  3. 将相关联的唯一维度列直接补充进 `GROUP BY`。

---

### Q29: `GROUP_CONCAT()` 函数默认有什么物理限制？如何防止数据截断丢弃？
**答**：
默认受系统参数 **`group_concat_max_len = 1024`** 字节限制。一旦多行拼接后的字符串超过 1024 字节，超出的内容会被底层**静默截断丢弃且不报错**！
排障方案：在配置中调大该参数：`SET GLOBAL group_concat_max_len = 10485760;`（支持 10MB）。

---

### Q30: 什么是多维层次汇总统计 `WITH ROLLUP`？
**答**：
在 `GROUP BY col1, col2 WITH ROLLUP` 语法中，MySQL 会在完成正常分组后，额外自动追加多级小计（Subtotal）与最终大计（Grand Total）汇总行，省去了在应用层多次分别查库再合并计算的代码开销。

---

### Q31: `LENGTH('中国')` 与 `CHAR_LENGTH('中国')` 在 `utf8mb4` 字符集下的返回值各是多少？
**答**：
- `LENGTH('中国')`：计算字节长度，返回 **6**（utf8mb4 下每个汉字占 3 字节）；
- `CHAR_LENGTH('中国')`：计算纯字符数，返回 **2**。校验用户昵称字数必须使用 `CHAR_LENGTH`。

---

### Q32: `CONCAT('a', 'b', NULL)` 的返回值是什么？如何安全规避？
**答**：
返回 **`NULL`**！`CONCAT` 内部只要有一个参数是 NULL，整个结果无脑变成 NULL。
安全替代方案：使用 **`CONCAT_WS('-', 'a', 'b', NULL)`**，它会自动跳过 NULL 值，安全返回 `'a-b'`。

---

### Q33: `DATEDIFF('2026-11-20', '2026-11-17')` 与 `TIMESTAMPDIFF(DAY, '2026-11-17', '2026-11-20')` 结果有什么异同？
**答**：
- 两者最终计算出的天数差均为 **3**；
- `DATEDIFF(expr1, expr2)` 是以前项减后项（$expr1 - expr2$），且仅精确到天；
- `TIMESTAMPDIFF(unit, expr1, expr2)` 是以后项减前项（$expr2 - expr1$），支持细粒度指定时间单位（SECOND, MINUTE, HOUR, DAY, MONTH, YEAR）。

---

### Q34: `IFNULL(a, b)` 与 `COALESCE(a, b, c, ...)` 有何异同？
**答**：
- `IFNULL(a, b)` 是双参数函数，仅在 $a$ 为 NULL 时返回 $b$；
- `COALESCE(...)` 是标准 SQL 变长参数函数，支持传入任意个参数，从左到右依次扫描，返回**第一个非 NULL 的元素**，所有参数均为 NULL 时返回 NULL。

---

### Q35: 解释 `CASE WHEN` 语句的两种语法形态及其适用场景。
**答**：
1. **简单 CASE 表达式**：`CASE col WHEN val1 THEN ... WHEN val2 THEN ... ELSE ... END`，用于单一列的等值精确匹配；
2. **搜索式 CASE 表达式**：`CASE WHEN condition1 THEN ... WHEN condition2 THEN ... ELSE ... END`，支持复杂的范围比较（如 `score >= 90`）、多条件组合逻辑与行转列报表统计。

---

### Q36: 为什么在 `WHERE` 条件中对索引字段使用函数（如 `WHERE DATE(create_time) = '2026-11-17'`）会导致索引完全失效？
**答**：
B+ 树索引内部的物理键值是按照列的**原始绝对值**保持单调有序排列的。当在列上套用函数时，计算后的值在索引树上不再满足原有的连续单调性，优化器无法执行二分查找，只能将整棵索引树从头到尾退化为全表扫描。正确做法是保持列原生不变，将函数计算转移至常量端：`WHERE create_time >= '2026-11-17 00:00:00' AND create_time < '2026-11-18 00:00:00'`。

---

### Q37: 什么是多表关联中的“笛卡尔积（Cartesian Product）”？它产生的根本原因是什么？
**答**：
表 A（$M$ 行）与表 B（$N$ 行）在关联时，由于**漏写了 `ON` / `WHERE` 连接条件**，或者连接条件为永真（如 `ON 1=1`），导致左表的每一行都与右表的所有行无脑进行全量排列组合，生成 $M \times N$ 行的中间结果集。上万行的大表产生笛卡尔积会瞬间耗尽内存与磁盘，引发数据库假死。

---

### Q38: 简述 `INNER JOIN`、`LEFT JOIN` 与 `RIGHT JOIN` 的集合交并语义。
**答**：
- `INNER JOIN`（内连接）：仅返回左右两表严格满足 ON 条件的**交集行**；
- `LEFT JOIN`（左外连接）：完整保留左表全部数据行，右表若无匹配则右表各字段填充 `NULL` 返回；
- `RIGHT JOIN`（右外连接）：完整保留右表全部数据行，左表若无匹配则左表各字段填充 `NULL` 返回（大厂建议一律改写为 `LEFT JOIN`）。

---

### Q39: 在 `LEFT JOIN` 中，把对右表的过滤条件放在 `ON` 与放在 `WHERE` 有何致命差异？
**答**：
- 放在 `ON` 中：属于**连接条件**，右表不满足条件时仅将右表置为 `NULL`，**左表记录仍然会被完整保留**；
- 放在 `WHERE` 中：属于**连接后的全表结果集过滤**，右表为 `NULL` 的行在比对时直接被判定为假剔除，导致未匹配的左表记录被误杀，**`LEFT JOIN` 彻底隐式退化为了 `INNER JOIN`**！

---

### Q40: MySQL 原生支持 `FULL OUTER JOIN` 吗？如果不支持如何实现？
**答**：
**原生不支持**。
可通过将 `LEFT JOIN` 与 `RIGHT JOIN` 两个查询通过 **`UNION`**（自动去重）进行合并拼接，从而完美模拟出全外连接的效果。

---

### Q41: 什么是自连接（Self Join）？其典型应用场景是什么？
**答**：
一张数据表与它自身进行的 `JOIN` 关联（通过给同一张表赋予不同的别名如 `t1`, `t2` 实现）。
典型场景：存储了树状上下级关系的数据表，如“查询员工及其直属上级领导姓名（员工表的 `manager_id` 关联领导行的 `id`）”、多级分类目录递归查询。

---

### Q42: 事务的四大特性（ACID）分别代表什么？
**答**：
1. **原子性（Atomicity）**：事务中的所有操作要么全部成功持久化，要么全部失败回滚（undo log 保障）；
2. **一致性（Consistency）**：事务前后数据库必须从一个合法的业务状态迁移到另一个合法状态，是事务的终极目标；
3. **隔离性（Isolation）**：并发执行的各个事务之间互不干扰，根据隔离级别限制相互可见性（锁 + MVCC 保障）；
4. **持久性（Durability）**：事务一旦成功提交，对数据的修改即永久生效，即使断电宕机也不丢失（redo log 保障）。

---

### Q43: 什么是 `autocommit`？它在 MySQL 中的默认表现是什么？
**答**：
`autocommit` 是控制单条 SQL 是否自动提交事务的全局/会话变量，**MySQL 默认值为 1（ON，开启）**。在开启状态下，每一条独立执行的 `INSERT`、`UPDATE` 或 `DELETE` 语句执行完成后，MySQL 底层都会自动隐式执行一次 `COMMIT`。

---

### Q44: 如何在 MySQL 客户端中显式开启并提交/回滚一个多步骤事务？
**答**：
```sql
START TRANSACTION; -- 或 BEGIN; 显式开启事务，挂起自动提交
UPDATE t_account SET balance = balance - 100 WHERE id = 1;
UPDATE t_account SET balance = balance + 100 WHERE id = 2;
COMMIT;   -- 校验成功，永久提交
-- 或 ROLLBACK; -- 校验失败，撤销并回滚现场
```

---

### Q45: 事务中的 `SAVEPOINT` 保存点有什么实际价值？
**答**：
允许在长事务中设置阶段性存档标记。通过 `SAVEPOINT sp1;` 打点，后续若非核心分支发生错误，可通过 `ROLLBACK TO SAVEPOINT sp1;` 实现**局部精确回滚**，撤销错误分支而保留前半段核心操作，最后统一 `COMMIT`。

---

### Q46: 生产环境中“长事务（Long-Running Transaction）”会导致哪两大致命灾难？
**答**：
1. **行锁长期被持有**：导致并发的其他事务陷入长时间锁等待，超时抛出 1205 报错；
2. **undo log 无法被清理**：长事务持有的 `ReadView` 会阻碍后台 Purge 垃圾回收线程，导致历史 undo 版本链无法清除，全局表空间（`ibdata1`）疯狂膨胀直至打满磁盘。

---

### Q47: 出现 `Error 1045 (28000): Access denied for user` 的两排障方向是什么？
**答**：
1. 检查密码是否正确；
2. 检查当前用户被授权绑定的 **`Host` 白名单**。MySQL 用户身份是由 `'username'@'host'` 双重决定的，若仅授权了 `'root'@'localhost'`，从外部局域网或远程 IP 登录会被直接判定为权限不足拒绝访问。

---

### Q48: 出现 `Error 1040: Too many connections` 时，管理员如何紧急接入自救？
**答**：
MySQL 为拥有 `SUPER` 或 `CONNECTION_ADMIN` 权限的高级管理员账号**专门额外保留了 1 个特权连接名额**（总连接数可达到 `max_connections + 1`）。运维人员可以在内网使用 `root` 登入，执行 `SHOW PROCESSLIST` 找出卡死的连接并 `KILL` 释放资源。在 MySQL 8.0 中也可通过专用的 `admin_port = 33062` 管理端口直连。

---

### Q49: 出现 `Error 1062 (23000): Duplicate entry 'xxx' for key` 的根本原因是什么？
**答**：
试图插入或更新的数据行，在声明了 `PRIMARY KEY` 或 `UNIQUE KEY` 唯一索引的列上，存在与表中已有记录完全一致的值，触发了数据库的唯一性约束阻断防御。

---

### Q50: 初级工程师在编写 SQL 时最容易犯的 3 个“致命初级错误”是什么？
**答**：
1. **`UPDATE / DELETE` 漏写 `WHERE` 条件**，导致全表灾难性覆写或清空；
2. **在索引列上随意套用内置函数（如 `WHERE DATE(...)`）**，导致索引失效触发全表扫描；
3. **在生产大表上执行多表关联时漏写连接条件触发笛卡尔积**，瞬间吃死数据库 CPU 与内存。
