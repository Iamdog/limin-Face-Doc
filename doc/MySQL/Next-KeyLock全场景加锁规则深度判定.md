# Next-Key Lock 全场景加锁规则深度判定

在后端技术面试中，“请详细说一下在可重复读（RR）级别下，这条 SQL 到底加了什么锁？”堪称筛选候选人底层功底的“分水岭”题目。绝大多数人只能含糊说出“加了行锁”或“加了间隙锁”，而中高级社招考察的是**精确到哪个开区间、哪个闭区间、哪些索引树被锁**的严密判定能力。

---

## 1. 核心加锁公理：两大原则与两条优化规则

在 **Repeatable Read（可重复读）** 隔离级别下，InnoDB 行级加锁遵循经典的“两大原则、两条优化”核心公理：

### 原则 1：加锁的基本单位是 Next-Key Lock
只要加锁，InnoDB 默认初始分配的都是 **Next-Key Lock（左开右闭区间 `(a, b]`）**。

### 原则 2：查找过程中“访问到的对象”才会加锁
只有在 B+ 树索引扫描遍历过程中，**被指针物理访问到的索引项**，才会被赋予锁。未被扫描访问的节点绝对不加锁。

### 优化 1：唯一索引等值查询，退化为“记录锁”
当在**主键或唯一索引**上进行**等值查询**，且检索的记录在表中**真实存在**时，Next-Key Lock 自动退化为单纯的 **Record Lock（记录锁）**。

### 优化 2：等值查询向右遍历到不满足条件的值时，退化为“间隙锁”
在进行等值查询时，向右遍历到最后一个**不满足等值条件**的记录时，该条记录上的 Next-Key Lock 自动退化为 **Gap Lock（间隙锁）**。

## 2. 基础数据准备与区间划分

为了使推导具象化，我们建立如下标准数据表：

```sql
CREATE TABLE `t_lock_test` (
  `id` INT NOT NULL AUTO_INCREMENT,
  `c` INT NOT NULL, -- 普通非唯一索引
  `d` INT NOT NULL, -- 无索引
  PRIMARY KEY (`id`),
  KEY `idx_c` (`c`)
) ENGINE=InnoDB;

-- 插入 5 条基线数据
INSERT INTO `t_lock_test` VALUES (5, 5, 5), (10, 10, 10), (15, 15, 15), (20, 20, 20), (25, 25, 25);
```

此时主键 `id` 与二级索引 `c` 的默认物理区间均为：  
$(-\infty, 5], (5, 10], (10, 15], (15, 20], (20, 25], (25, +\infty)$

## 3. 全场景加锁精准推导演练

### 场景一：唯一索引等值查询（记录存在）
```sql
SELECT * FROM t_lock_test WHERE id = 10 FOR UPDATE;
```
1. 根据**原则 1**：加锁基本单位是 Next-Key Lock，首先给 $(5, 10]$ 加锁；
2. 根据**优化 1**：`id` 是主键（唯一索引），且 `id = 10` 的行在表中客观存在；
3. **退化结果**：$(5, 10]$ 自动退化为纯记录锁。
- **最终加锁范围**：**仅锁定主键 `id = 10` 这一行**。其他事务对 `id = 6~9` 或 `11~14` 的插入完全自由不受限。

---

### 场景二：唯一索引等值查询（记录不存在）
```sql
SELECT * FROM t_lock_test WHERE id = 8 FOR UPDATE;
```
1. 根据**原则 1**：查询首先定位到包含 8 的区间，即访问到下一个存在的记录 `id = 10`，给 $(5, 10]$ 加上 Next-Key Lock；
2. 由于 `id = 8` 不存在，向右遍历找到的 `10` 不等于 8；
3. 根据**优化 2**：等值查询向右遍历到不满足条件的值，Next-Key Lock 退化为间隙锁；
4. **退化结果**：$(5, 10]$ 退化为开区间 $(5, 10)$。
- **最终加锁范围**：**锁定间隙 `(5, 10)`**。此时任何事务向 `id = 6, 7, 8, 9` 插入数据都会被阻塞。

---

### 场景三：普通非唯一索引等值查询（深度考察点）
```sql
SELECT * FROM t_lock_test WHERE c = 10 FOR UPDATE;
```
这是面试中最常考的陷阱题！注意：`c` 是普通索引，允许有多个相同值！
1. 在 `idx_c` 树上扫描找到 `c = 10`，根据**原则 1**，给 `(5, 10]` 加上 Next-Key Lock；
2. 此时必须回表：由于是 `SELECT *`，主键索引树上的 `id = 10` 被访问，因此**主键索引上的 `id = 10` 被加上记录锁**；
3. **关键点**：因为 `c` 不是唯一索引，InnoDB 必须向右继续扫描，确认还有没有其他的 `c = 10`！
4. 向右遍历访问到下一条记录 `c = 15`，发现 `15 != 10`，根据**优化 2**，在 `c = 15` 上加的 Next-Key Lock `(10, 15]` 退化为**间隙锁 `(10, 15)`**；
- **最终加锁范围**：
  - **`idx_c` 索引树**：Next-Key Lock `(5, 10]` + 间隙锁 `(10, 15)`（合并等价于锁定了 `(5, 15)` 间隙，以及 `c = 10` 记录）；
  - **主键索引树**：仅在 `id = 10` 上加了记录锁。

> **覆盖索引惊天反转**：  
> 若将 SQL 改为：`SELECT id FROM t_lock_test WHERE c = 10 FOR UPDATE;`  
> 此时由于只查询 `id`，二级索引 `idx_c` 已经覆盖了全部返回列，**InnoDB 根本不需要回表**！根据**原则 2（只有访问到的对象才加锁）**，**主键索引树上将完全不加任何锁**！其他事务更新主键 `id = 10` 的其他字段完全不会被阻塞！

---

### 场景四：主键索引范围查询
```sql
SELECT * FROM t_lock_test WHERE id >= 10 AND id < 11 FOR UPDATE;
```
1. 范围查询首先定位起点：`id = 10` 等值定位，先给 $(5, 10]$ 加 Next-Key Lock，因主键等值优化退化为**记录锁 `id = 10`**；
2. 继续向右扫描：由于是范围查询，继续向右扫描到第一条不满足 `< 11` 的记录，即 `id = 15`；
3. 给 `id = 15` 加上 Next-Key Lock `(10, 15]`；
4. **注意**：范围查询不遵循“等值查询优化 2”的退化规则！
- **最终加锁范围**：**主键索引上的记录锁 `id = 10`，以及 Next-Key Lock `(10, 15]`**！

---

### 场景五：无索引字段更新（全表锁死）
```sql
UPDATE t_lock_test SET d = 100 WHERE d = 10;
```
- 由于 `d` 字段没有任何索引，InnoDB 只能通过聚簇索引做全表扫描。
- 在 RR 隔离级别下，全表扫描会将**整张表的所有聚簇索引记录以及所有记录之间的间隙全部加上排他 Next-Key Lock**！
- 此时整张表完全被锁死，任何并发的 `INSERT`、`UPDATE`、`DELETE` 全部阻塞挂起！

## 4. 社招高频面试追问

### Q1：为什么生产环境如果一定要使用 `FOR UPDATE`，强烈建议走主键或唯一索引？
- 走主键/唯一索引等值查询时，由于“优化 1”，Next-Key Lock 能够稳定退化为纯记录锁，**完全不产生间隙锁**，并发插入互不干扰，几乎不发生死锁。
- 一旦走普通二级索引或范围查询，间隙锁不可避免地蔓延，极易与业务并发的 `INSERT` 产生互斥，导致线上吞吐骤降和突发死锁。
