# 并发事务问题与四大隔离级别实现差异

在数据库高并发访问下，多个事务同时对同一批数据进行读写，必然产生并发冲突。为了规范这些冲突的表现，SQL 标准定义了隔离级别。而在社招面试中，核心关注点在于：**四大并发问题究竟是如何定义的？MySQL InnoDB 的实现与 ANSI SQL-92 标准究竟有哪些显著差异？InnoDB 的 RR 级别到底有没有彻底杜绝幻读？**

---

## 1. 并发事务引发的四大经典数据问题

| 异常现象 | 出现场景与本质定义 | 影响严重度 |
|:---|:---|:---|
| **脏读 (Dirty Read)** | 事务 A 读取到了事务 B **尚未提交的修改**。若事务 B 随后执行回滚，则事务 A 读到的数据全是不存在的“脏数据”。 | 极度严重 |
| **不可重复读 (Non-Repeatable Read)** | 事务 A 内多次读取同一条记录。在两次读取之间，事务 B 对该记录执行了 **`UPDATE` 或 `DELETE` 并提交**，导致事务 A 前后两次读到的**数据内容不一致**。 | 严重 |
| **幻读 (Phantom Read)** | 事务 A 按一定范围条件查询数据。在两次读取之间，事务 B 在该范围内执行了 **`INSERT` 并提交**，导致事务 A 再次读取该范围时，像产生幻觉一样**凭空多出了新记录（幽灵行）**。 | 严重 |
| **丢失更新 (Lost Update)** | **第一类丢失更新**：事务 A 撤销回滚时，把事务 B 已提交的数据覆盖（现代事务引擎均已杜绝）。<br>**第二类丢失更新**：事务 A 和 B 同时读取某行并修改，后提交的事务无意中**完全覆盖覆盖了先提交事务的结果**。 | 业务高危 |

---

## 2. SQL-92 标准四大隔离级别 vs InnoDB 真实实现

ANSI SQL-92 标准定义了四个隔离级别与其允许出现的异常现象：

| 隔离级别 | 脏读 (Dirty Read) | 不可重复读 | 幻读 (Phantom Read) | 业界主流默认隔离级别 |
|:---|:---:|:---:|:---:|:---|
| **Read Uncommitted (读未提交)** | 允许 | 允许 | 允许 | 极少使用 |
| **Read Committed (读已提交, RC)** | **杜绝** | 允许 | 允许 | Oracle / PostgreSQL / SQL Server 默认 |
| **Repeatable Read (可重复读, RR)** | **杜绝** | **杜绝** | *标准允许 (InnoDB杜绝大部)* | **MySQL InnoDB 默认** |
| **Serializable (串行化)** | **杜绝** | **杜绝** | **杜绝** | 强一致性金融核心 |

## 3. 核心深水区：InnoDB 的 RR 级别到底是如何解决幻读的？

按照 SQL-92 标准，RR 级别只要求解决脏读和不可重复读，幻读的解决属于 Serializable 串行化的职责。**但 MySQL InnoDB 引擎在 RR 隔离级别下，采取了双轨制机制解决了绝大部分幻读问题**：

```text
InnoDB 在 RR 下处理幻读的双轨制：
1. 快照读 (普通 SELECT) ────────▶ 通过 MVCC 生成 Read View，多次读取始终访问历史一致性版本快照
2. 当前读 (SELECT ... FOR UPDATE / UPDATE / DELETE) ──▶ 通过 Next-Key Lock 锁住记录本身以及间隙 (Gap)，彻底阻止其他事务 INSERT
```

### 3.1 机制一：快照读通过 MVCC 规避幻读
- 当事务 A 执行普通的 `SELECT * FROM orders WHERE amount > 100` 时，InnoDB 会在**第一次执行查询时生成一份 Read View 快照**。
- 随后即便事务 B 插入了 10 条新的 `amount = 500` 的订单并提交，事务 A 再次执行相同的 `SELECT` 时，由于 Read View 视图的可见性判断规则，事务 A 只能看到自己快照创建前已提交的数据，**新插入的记录在快照读中完全隐形，从而避免了幻读**。

### 3.2 机制二：当前读通过 Next-Key Lock 锁死间隙
- 当事务 A 执行当前读（锁定读）：
  ```sql
  SELECT * FROM orders WHERE amount > 100 FOR UPDATE;
  ```
- InnoDB 不仅会锁住当前所有 `amount > 100` 的已有记录（Record Lock），还会沿索引树加上 **间隙锁（Gap Lock）**，形成 **Next-Key Lock**，将 `(100, +∞)` 的整个区间完全锁死！
- 此时若事务 B 尝试执行 `INSERT INTO orders(amount) VALUES (200)`，该插入会被间隙锁直接阻塞挂起，直到事务 A 提交释放锁。**从物理锁层面彻底粉碎了新行插入的可能性**。

## 4. 社招地狱级考点：InnoDB 的 RR 级别是否彻底消除了幻读？

面试官常问：“既然有了 MVCC 和 Next-Key Lock，那 MySQL 的 RR 隔离级别是不是彻底杜绝了幻读，等同于串行化了？”

**答案：没有！InnoDB 在 RR 级别下依然存在特殊的“幻读漏网之鱼”。**

### 经典幻读复现场景：快照读与当前读混用

假设表 `users` 中只有一条记录 `id = 1, name = '张三'`。

```mermaid
sequenceDiagram
    autonumber
    actor A as 事务 A (RR)
    actor B as 事务 B (RR)
    
    A->>A: START TRANSACTION;
    A->>A: SELECT * FROM users WHERE id = 5; (查无记录，生成 Read View)
    
    B->>B: START TRANSACTION;
    B->>B: INSERT INTO users VALUES (5, '李四');
    B->>B: COMMIT; (事务 B 提交，物理写入 id=5)
    
    A->>A: SELECT * FROM users WHERE id = 5; (快照读：依然查无记录)
    
    Note over A: 诡异操作触发！事务 A 执行 UPDATE 更新了未查到的行！
    A->>A: UPDATE users SET name = '王五' WHERE id = 5; (影响行数: 1 行！)
    
    Note over A: 事务 A 再次执行普通快照读：
    A->>A: SELECT * FROM users WHERE id = 5;
    Note over A: 震撼结果：此时竟然查出了 (id=5, name='王五')！
    Note over A: 幻读彻底诞生！
```

#### 为什么会出现这种幻读？
1. 在步骤 6 中，事务 A 执行 `UPDATE` 是**当前读**。根据当前读语义，InnoDB 必须读取物理磁盘上的最新提交版本，因此 `UPDATE` 成功找到了事务 B 刚刚提交的 `id = 5`，并将其修改为 `'王五'`。
2. 关键点：在修改这条记录时，InnoDB 将该行的事务版本号 `DB_TRX_ID` 变更为**事务 A 自己的事务 ID**！
3. 当步骤 7 事务 A 再次执行普通的快照读时，根据 MVCC 规则：**“任何由本事务自己创建或修改的记录，对本事务永远可见”**！
4. 于是，这条原本在事务 A 开启时并不存在的 `id = 5`，宛如幽灵般出现在了事务 A 的普通查询结果集中！

## 5. 社招高频面试追问

### Q1：为什么互联网大厂很多公司推荐将隔离级别从 RR 改为 RC？
1. **死锁概率大幅降低**：在 RC 隔离级别下，**绝大多数常规查询和更新完全关闭了间隙锁（Gap Lock）**，仅在唯一键冲突检查或外键时使用间隙锁。这使得高并发更新时的行锁死锁率骤降。
2. **锁持有时间更短（半一致性读 Semi-Consistent Read）**：在 RC 级别下，执行 `UPDATE` 时，对于不满足 `WHERE` 条件的行，MySQL 会立刻提前释放锁，无需等待事务提交。
3. **主从复制已全面支持 ROW 模式**：早期 MySQL 之所以默认选 RR，是因为早期的 binlog 只能是 `STATEMENT` 格式（基于 SQL 语句复制）。在 RC 级别下若无间隙锁，并发写入会导致主从数据回放顺序不一致。而如今互联网公司一律强制使用 **`binlog_format = ROW`**，彻底解除了对 RR 的强依赖。
