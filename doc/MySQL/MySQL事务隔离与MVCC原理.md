# MySQL事务隔离与MVCC原理

## 1. 事务隔离级别与解决的并发问题

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 底层实现核心机制 |
| :--- | :---: | :---: | :---: | :--- |
| **读未提交 (Read Uncommitted)** | 是 | 是 | 是 | 直接读取物理行最新数据 |
| **读已提交 (RC)** | 否 | 是 | 是 | **每次 SELECT 执行时**创建全新的 ReadView |
| **可重复读 (RR, MySQL默认)** | 否 | 否 | 否（结合间隙锁） | **事务开启后首次 SELECT 时**创建 ReadView 并全程复用 |
| **串行化 (Serializable)** | 否 | 否 | 否 | 读写全加表锁/行锁串行化 |

---

## 2. MVCC（多版本并发控制）核心实现

MVCC 保证了高并发下“读写不冲突”，普通读（快照读）完全无需加锁。其依赖于三大支柱：

### 1. 隐藏字段
- `trx_id`：最近修改（插入/更新）该行记录的事务 ID。
- `roll_pointer`：回滚指针，指向写入 `undo log` 的上一版本记录，形成版本链。

### 2. undo log（回滚日志版本链）
每次数据被并发更新时，旧版本记录会被写入 undo log，通过 `roll_pointer` 串成一条由最新到最旧的历史链表。

### 3. ReadView（快照读视图）
包含 4 个核心属性：
- `m_ids`：生成 ReadView 时当前活跃（未提交）的事务 ID 集合。
- `min_trx_id`：当前活跃事务中最小的事务 ID。
- `max_trx_id`：下一个将要分配给事务的 ID（最大事务 ID + 1）。
- `creator_trx_id`：生成该 ReadView 的当前事务 ID。

#### 核心可见性比对规则
1. `trx_id < min_trx_id`：表示该版本由已提交事务生成，**可见**。
2. `trx_id >= max_trx_id`：表示该版本由将来开启的事务生成，**不可见**。
3. `min_trx_id <= trx_id < max_trx_id`：
   - 若 `trx_id` 在 `m_ids` 活跃列表中：说明生成该版本的事务还未提交，**不可见**，沿 undo log 链顺延寻找上一版本。
   - 若 `trx_id` 不在 `m_ids` 活跃列表中：说明事务已经提交，**可见**。
4. `trx_id == creator_trx_id`：当前事务自己修改的数据，**可见**。

## 3. 行锁失效升级表锁引发死锁

- **本质**：InnoDB 行锁加在**索引**上，不是加在物理行上。
- **事故复现**：
  ```sql
  -- status 字段没有建立索引
  UPDATE t_user SET age = 30 WHERE status = 2;
  ```
- **后果**：由于未命中索引，InnoDB 无法确定具体加锁范围，被迫在主键聚簇索引上将**所有记录及间隙全部锁死（Next-Key Lock 锁全表）**，导致并发线程等待并互相阻塞，引发 Deadlock。
