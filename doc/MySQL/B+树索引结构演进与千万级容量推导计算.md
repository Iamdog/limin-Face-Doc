# B+ 树索引结构演进与千万级容量推导计算

“为什么 MySQL 索引要用 B+ 树？”是后端面试中出现频率最高的经典问题。很多同学能背出“矮胖、利于磁盘 I/O、叶子节点有双向链表”，但如果面试官追问：“为什么不用红黑树或跳表？为什么非叶子节点不能存数据？3 层 B+ 树到底能存多少千万行数据？怎么推导出来的？”，往往就答不上来了。

本篇用严密的**演进对比**和**数学公式**彻底讲透 B+ 树索引底座。

---

## 1. 为什么是 B+ 树？七大数据结构的严密淘汰推导

索引的本质就是**排好序的高效查找数据结构**。为了在磁盘上存储海量数据并最小化 I/O 开销，数据结构经历了一系列演进：

```mermaid
flowchart LR
    A["线性数组 / 链表 (O(N) 慢)"] --> B["二叉查找树 BST (易退化单向斜树)"]
    B --> C["平衡二叉树 AVL (旋转严格/树太高)"]
    C --> D["红黑树 R-B Tree (二叉树太深/I/O频繁)"]
    D --> E["B 树 (多叉平衡树/非叶子节点存数据)"]
    E --> F["B+ 树 (非叶子节点仅存索引/叶子节点双向链表)"]
```

### 1.1 淘汰二叉查找树（BST）
- **缺陷**：极端情况下（按顺序自增插入），二叉查找树会退化为一条**单向链表**，时间复杂度从 $O(\log_2 N)$ 彻底退化为 $O(N)$。

### 1.2 淘汰平衡二叉树（AVL）与红黑树（Red-Black Tree）
- **缺陷**：虽然 AVL 和红黑树通过旋转保证了树的高度平衡，但它们本质上都是**二叉树**（每个节点最多只有 2 个子节点）。
- 如果存储 2000 万行数据，二叉树的高度为 $\log_2(20000000) \approx 25$ 层。
- **物理致命伤**：在磁盘存储中，树的每一个层级通常对应一次**离散磁盘 I/O**。查找一条数据需要连续进行 25 次磁盘寻道，按机械硬盘单次寻道 10ms 计算，查询一次需要 250ms，性能完全不可接受！

### 1.3 淘汰哈希表（Hash Index）
- **优势**：等值查询（`WHERE id = 1`）时间复杂度极高，达到 $O(1)$。
- **缺陷**：
  1. **完全无法支持范围查询**（如 `WHERE age > 18`），因为哈希散列后是无序的。
  2. 无法支持 `ORDER BY` 排序、模糊匹配（`LIKE 'abc%'`）和多列联合索引的最左前缀匹配。

### 1.4 为什么跳表（SkipList）用于 Redis 而未被 MySQL 用作默认磁盘引擎？
- Redis 是**纯内存数据库**，跳表实现极其简单、无锁并发维护成本低，非常适合内存操作。
- 但跳表的指针很多且节点大小不固定，物理上无法与操作系统的“4KB / 16KB 页磁盘块”对齐，在磁盘存储上面临大量的离散碎片与 I/O 放大。

### 1.5 B 树（B-Tree）vs B+ 树（B+ Tree）的决胜关键
B 树是多叉平衡查找树，每个节点可以有多个子节点。但 MySQL 最终坚定地选择了 **B+ 树**，两者的本质区别如下：

| 对比维度 | B 树（B-Tree） | B+ 树（B+ Tree） |
|:---|:---|:---|
| **非叶子节点内容** | 存放索引键值 + **完整的行数据（整行所有列）** | **只存放索引键值 + 子节点物理页指针**（绝不放数据） |
| **叶子节点组织** | 包含部分数据，节点间无链表 | 包含**全量真实数据**，同层叶子节点由**双向链表**串联 |
| **单页容纳索引量** | 极少（整行数据占用空间大，页很快被填满） | **极大**（非叶子节点仅有几字节，单页可存上千个索引项） |
| **树的高度** | 较高（通常 4~6 层） | **极矮胖（通常仅 2~3 层）** |
| **范围查询能力** | 差（必须在多层父子节点之间进行中序遍历递归回溯） | **极优**（只需找到起点叶子节点，沿着双向链表顺序向后扫描即可） |
| **查询稳定性** | 不稳定（在根节点找到即返回，底层找到则慢） | **极度稳定**（任何查询都必须平稳走到叶子节点，耗时恒定） |

## 2. 3 层 B+ 树存储两千万行数据的严密数学推导

在阿里巴巴 Java 开发手册中提到：“单表行数超过 500 万行或者单表容量超过 2GB，才推荐进行分库分表”。为什么业界通常认为 **2000 万行** 是 MySQL 单表性能的经验分水岭？

我们通过严密的数学计算来还原推导过程：

### 2.1 推导前置假设条件
1. 默认 InnoDB 数据页大小为 **16KB**（16384 字节）。
2. 主键采用标准的 **`BIGINT`**，占用 **8 字节**。
3. 在非叶子节点中，指向下一个子页面的磁盘物理指针（Page Pointer）占用 **6 字节**。
4. 假设叶子节点中每行真实业务记录平均占用 **1KB**（常规业务宽表的典型均值）。

### 2.2 步骤一：计算一个非叶子节点（目录页）能容纳多少个指针
在 B+ 树的非叶子节点（根节点或枝节点）中，每一个目录项由 **[主键值 (8B) + 子页指针 (6B)]** 构成，总计 **14 字节**。

$$\text{单页目录项数量} = \frac{16384 \text{ 字节}}{8 + 6 \text{ 字节}} = \frac{16384}{14} \approx 1170 \text{ 个}$$

即：**1 个 16KB 的非叶子节点页可以引出约 1170 个子节点页指针**。

### 2.3 步骤二：计算一个叶子节点（数据页）能容纳多少条真实行
叶子节点专门存储用户真实业务数据行，按单行 1KB 计算：

$$\text{单页叶子节点行数} = \frac{16384 \text{ 字节}}{1024 \text{ 字节}} \approx 16 \text{ 行}$$

### 2.4 步骤三：计算不同高度 B+ 树的理论最大存储容量

#### 1. 高度为 2 层（1 个根节点 + N 个叶子节点）
- 根节点拥有 1170 个指针，指向 1170 个叶子数据页。
- 总容量 = $1170 \times 16 = \mathbf{18,720 \text{ 行}}$（约 1.8 万行）。

#### 2. 高度为 3 层（1 个根节点 + 1170 个二级目录页 + N 个叶子节点）
- 根节点拥有 1170 个指针，指向 1170 个二级枝节点。
- 1170 个二级枝节点总共引出 $1170 \times 1170 = 1,368,900$ 个叶子数据页。
- 总容量 = $1170 \times 1170 \times 16 = \mathbf{21,902,400 \text{ 行}}$（**约 2190 万行！**）。

#### 3. 高度为 4 层
- 总容量 = $1170 \times 1170 \times 1170 \times 16 \approx \mathbf{256 \text{ 亿行}}$。

```text
3 层 B+ 树结构示意图：
                 ┌──────────────────┐
                 │    根节点 (16KB) │  (常驻 Buffer Pool 内存，0 次磁盘 I/O)
                 └─────────┬────────┘
             ┌─────────────┼─────────────┐ (1170 个分支指针)
             ▼             ▼             ▼
       ┌───────────┐ ┌───────────┐ ┌───────────┐
       │ 枝节点页 1│ │ 枝节点页 2│ │ 枝节点页 N│ (通常也在内存，最多 1 次 I/O)
       └─────┬─────┘ └─────┬─────┘ └─────┬─────┘
    ┌────────┼─────────────┼─────────────┼────────┐ (每个节点引出 1170 个指针)
    ▼        ▼             ▼             ▼        ▼
┌──────┐  ┌──────┐     ┌──────┐      ┌──────┐  ┌──────┐
│叶子页│◀─┼叶子页┼─...─┼叶子页┼──────┼叶子页┼─▶│叶子页│ (双向链表，1 次磁盘 I/O 读取真实行)
└──────┘  └──────┘     └──────┘      └──────┘  └──────┘
```

### 2.5 为什么两千万行是分水岭？
- 当数据量在 **2000 万以内** 时，B+ 树高度基本维持在 **3 层**。根节点和二级枝节点由于高频访问，几乎 **100% 常驻在内存 Buffer Pool** 中。因此定位任何一条数据，**物理磁盘 I/O 仅需 1 次**（直接读取目标叶子页）！
- 一旦数据突破两千万行，B+ 树高度会从 3 层上升到 **4 层**。每次查询都需要额外多读取一层非叶子节点，磁盘物理 I/O 次数增加，且随着叶子节点基数指数级膨胀，Buffer Pool 的命中率大幅下滑，从而表现为整体 QPS 下滑、慢查询陡增。

## 3. 社招高频面试追问

### Q1：如果单行记录很小（例如只有 100 字节），3 层 B+ 树能存多少数据？
- 若单行仅 100 字节，单页叶子节点可容纳 $16384 / 100 \approx 160$ 行数据。
- 3 层 B+ 树容量 = $1170 \times 1170 \times 160 \approx \mathbf{2.19 \text{ 亿行}}$！
- **结论**：B+ 树的承载容量与**单行数据的物理宽度**强相关。这也是为什么规范要求“严禁大字段存入主表、字段宽度尽量紧凑”的根本数学原因。

### Q2：为什么主键索引推荐用单调自增，如果用 UUID 插入，B+ 树在底层会发生什么？
- 自增主键插入时永远在当前最后一个数据页的尾部追加，当前页写满后直接按顺序申请新页，写入过程全是**顺序 I/O**，数据页填充率高达 90% 以上。
- 若用随机 UUID，新插入行的主键值是随机离散的，必须插入到某个已经写满的历史物理页中间。这会直接强制触发**页分裂（Page Split）**：InnoDB 必须申请新页，将原页面的 50% 数据拷贝到新页，并调整上下游前后指针。这带来巨量的随机写 I/O、磁盘碎片率飙升，并且让 B+ 树树形变得稀疏不紧凑。
