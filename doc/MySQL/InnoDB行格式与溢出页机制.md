# InnoDB 行格式与溢出页机制

我们平时在 SQL 中操作的是一行行由列组成的数据，但在磁盘数据页内部，数据是以严格的二进制字节流编码存储的。这就是 **行格式（Row Format）**。

深入剖析行格式，能彻底解开许多经典的数据库底层疑惑：为什么有三大隐藏列？MVCC 究竟通过哪个字段实现？为什么单行最大不能超过 65535 字节？

---

## 1. 四大行格式演进对比

MySQL InnoDB 历史上有 4 种行格式：

| 行格式 | 引入版本 | 特性说明 | 行溢出处理策略 |
|:---|:---|:---|:---|
| **Redundant** | 早期古老格式 | 字段长度直接冗余存放，极为消耗磁盘空间 | 溢出时在主页保留 768 字节前缀 + 20 字节指针 |
| **Compact** | 5.0+ 引入 | 引入变长长度列表与 NULL 列表，紧凑高效 | 溢出时在主页保留 768 字节前缀 + 20 字节指针 |
| **Dynamic** | **5.7+ / 8.0 默认** | Compact 的完全演进版，现代高并发标配 | **完全溢出**：主页仅保留 20 字节指针，数据全部下推溢出页 |
| **Compressed** | 5.7+ 可选 | 在 Dynamic 基础上对数据页和溢出页启用 zlib 压缩 | 占用 CPU 较高，适合大归档只读库 |

## 2. Compact / Dynamic 行格式物理布局大拆解

一条完整的 InnoDB 记录由两大部分构成：**记录的额外信息（元数据）** 与 **记录的真实数据**。

```text
┌───────────────────────────────────────────────┬───────────────────────────────────────────────┐
│              记录的额外信息 (元数据)            │                  记录的真实数据                │
├───────────────────────┬──────────────┬────────┼───────────┬───────────┬───────────┬───────────┤
│ 变长字段长度列表 (逆序) │ NULL 值列表  │ 记录头 │ DB_ROW_ID │ DB_TRX_ID │DB_ROLL_PTR│ col1,col2 │
│ (1~2 字节/字段)       │ (NULL Bitmap)│ (5字节)│ (6字节可选)│ (6 字节)  │ (7 字节)  │ 真实列数据│
└───────────────────────┴──────────────┴────────┴───────────┴───────────┴───────────┴───────────┘
                                                ▲
                                                │ next_record 指针指向此处
```

### 2.1 记录的额外信息（元数据）

#### 1. 变长字段长度列表
针对 `VARCHAR`、`VARBINARY`、`TEXT`、`BLOB` 等变长类型，必须记录其实际占用的字节数。
- **逆序排列**：若表中第 1 列是 `VARCHAR(20)`，第 2 列是 `VARCHAR(50)`，则该列表中**第 2 列的长度排在最前面，第 1 列排在后面**。
- **长度占用 1 字节还是 2 字节？**
  - 如果字符集最大单字符字节数 $\times$ 字段定义长度 $\le 255$ 字节，用 **1 字节** 存储长度。
  - 如果可能超过 255 字节，且实际存储长度 $> 127$ 字节，则用 **2 字节** 存储。

#### 2. NULL 值列表（NULL Bitmap）
为了极致压缩磁盘空间，如果某列的值为 `NULL`，InnoDB **不会在“真实数据”区为它分配任何存储空间**，而是在“NULL 值列表”中用 1 个二进制位（Bit）标记：
- 只有允许为 NULL 的列才会统计进该列表（`NOT NULL` 列不参与）。
- **逆序存放**：每个允许为 NULL 的列按字段逆序对应一个 Bit 位（1 代表该列为 NULL，0 代表不为 NULL）。
- 整体以字节对齐，不足 8 个位的高位补 0。

#### 3. 记录头信息（Record Header，5 字节 40 位）
包含控制记录状态与链表串联的关键位：
- **`delete_mask`（1 位）**：逻辑删除标记。`1` 代表该记录已被业务 `DELETE`，但物理存储未被立即擦除，而是挂入垃圾链表等待后续 Purge 线程清理。
- **`min_rec_mask`（1 位）**：标记 B+ 树非叶子节点目录项的最小主键记录。
- **`n_owned`（4 位）**：当前记录所在的 Page Directory 槽位管理的记录总条数。
- **`heap_no`（13 位）**：当前记录在页内堆中的相对物理顺序编号。
- **`record_type`（3 位）**：记录类型：0-普通记录，1-B+树非叶子节点目录项，2-Infimum 虚拟伪记录，3-Supremum 虚拟伪记录。
- **`next_record`（16 位）**：**极度核心**。记录当前记录的地址到下一条记录地址的**相对偏移量**。页内记录就是通过它构成单向链表。

> **核心设计精妙点：为什么 `next_record` 指针不指向行首，而是指向“记录头”与“真实数据”之间的分界线？**  
> 因为向右读（正向偏移）是真实列数据；向左读（负向偏移）是元数据（记录头、NULL 列表、变长列表）。这种设计使得 CPU 能够以最小的指令寻址开销双向高速访问！

---

### 2.2 记录的真实数据与三大隐藏列

除了我们自己建表时声明的字段，InnoDB 会在每行真实数据前面强制追加 **3 个核心系统隐藏列**：

| 隐藏列名称 | 物理长度 | 存在条件 | 核心作用 |
|:---|:---|:---|:---|
| **`DB_ROW_ID`** | 6 字节 | **仅当表无主键且无唯一非空索引时存在** | 作为隐式聚簇索引的键值 |
| **`DB_TRX_ID`** | 6 字节 | **所有表强制存在** | **事务 ID**，记录最后一次修改/插入该行的事务 ID（MVCC 核心） |
| **`DB_ROLL_PTR`** | 7 字节 | **所有表强制存在** | **回滚指针**，指向该行在 undo log 中的旧版本历史快照（MVCC 版本链核心） |

## 3. 行溢出（Off-Page）物理实现机制

InnoDB 要求每个 16KB 数据页至少能放下 2 行数据。当单行数据巨大时，必须发生行溢出。

### 3.1 Compact vs Dynamic 的行溢出差异
- **Compact 格式的“半溢出”**：
  若发生行溢出，主数据页中除了存放 20 字节的溢出指针外，还会**强行保留前 768 个字节**的真实数据。这导致 Compact 格式在包含多个大字段时，主数据页仍极易耗尽空间。
- **Dynamic 格式的“彻底溢出”（MySQL 8.0 默认）**：
  在 Dynamic 格式下，一旦决定行溢出，主数据页**只保留 20 字节的物理指针**，所有大字段数据 100% 剥离并存储至独立的溢出页。主数据页保持极高紧凑度，B+ 树结构更加扁平。

```text
主数据页 (Dynamic)
┌────────────────────────────────────────────────────────┐
│ id: 101 | ... | 20 字节指针 (Space ID, Page No, Offset) │
└───────────────────────────┬────────────────────────────┘
                            │
                            ▼
溢出页 1 (Overflow Page 1)  [内容前 16KB] ──▶ 物理指针
                            │
                            ▼
溢出页 2 (Overflow Page 2)  [剩余内容]
```

## 4. 社招高频面试追问

### Q1：MySQL 规定单表最大行大小为 65535 字节，为什么执行 `CREATE TABLE t(c VARCHAR(65535)) CHARSET=latin1;` 会直接报错？
- **报错信息**：`Row size too large. The maximum row size for the used table type, not counting BLOBs, is 65535.`
- **物理原因深度推导**：
  虽然 `latin1` 字符集 1 个字符占 1 字节，但单行最大 65535 包含了**所有字段的元数据开销**：
  1. 变长字段长度列表需要占用 **2 字节**。
  2. 允许为 NULL 时，NULL 值列表需要占用 **1 字节**。
  3. 因此单列 `VARCHAR` 的最大理论长度只能是 $65535 - 2 - 1 = 65532$。
  4. 若设置为 `NOT NULL`，最大可设为 $65535 - 2 = 65533$。
  5. 此外，如果在 `utf8mb4` 字符集下（1 字符最多 4 字节），单列最大长度只能是 $\lfloor 65532 / 4 \rfloor = 16383$。
