# 字符集与排序规则实战避坑

字符集（Character Set）和排序规则（Collation）看似只是建库建表时的一行配置，但在高并发多语言交互以及跨表关联的微服务系统中，它却常常成为“Emoji 存入截断报错”或“跨表 JOIN 索引离奇失效”的隐形元凶。

---

## 1. utf8 与 utf8mb4 的历史渊源与 Emoji 事故

### 1.1 MySQL 历史上的“伪 utf8”假象
- 按照官方国际 Unicode 标准，标准的 UTF-8 编码是一种变长编码，长度为 **1 到 4 个字节**。
- 但在早期（MySQL 5.5 之前），MySQL 内部实现的 `utf8` 字符集其实是 **`utf8mb3`（Most Bytes 3）**，它最多只支持存储 **3 个字节** 的字符。
- 常见的英文字符占 1 字节，绝大多数常用汉字占 3 字节，因此在当时日常中文开发中并未暴露问题。

### 1.2 Emoji 与生僻字的 4 字节截断事故
随着移动互联网爆发，用户昵称、聊天内容、评论中充斥着大量的 Emoji 表情符号（如 😄, 🎉），以及部分生僻汉字（如“𫚉”、“𬱖”）。
- **Emoji 在 UTF-8 中必须占用 4 个字节**。
- 如果将含有 4 字节 Emoji 的字符串存入一个配置为 `utf8`（即 `utf8mb3`）的字段中，MySQL 会触发严重事故：
  - **严格模式（`STRICT_TRANS_TABLES`）开启下**：直接抛出严重异常终止写入：  
    `ERROR 1366 (HY000): Incorrect string value: '\xF0\x9F\x98\x84' for column 'nickname'`
  - **非严格模式下**：Emoji 及后面的全部文本被**无声无息地直接截断丢弃**，导致严重数据损坏！

> **生产铁律**：从 MySQL 5.5.3 起新增了 **`utf8mb4`（Most Bytes 4）**，这是真正完整的 UTF-8 标准。在现代所有业务库、表和字段中，**必须一律强制使用 `utf8mb4`**！

## 2. 排序规则（Collation）深度剖析与精准选型

排序规则定义了字符串如何进行**比较大小、排序（ORDER BY）以及唯一性判重（UNIQUE / GROUP BY）**。

### 2.1 常见 Collation 后缀命名规范
MySQL 的排序规则命名非常规范，从后缀即可判断其核心特性：
- **`_ci`（Case Insensitive）**：**大小写不敏感**。即 `'admin'` 与 `'ADMIN'` 被判定为相同值。
- **`_cs`（Case Sensitive）**：**大小写敏感**。`'admin'` 与 `'ADMIN'` 属于不同值。
- **`_bin`（Binary）**：**二进制字节编码直接比对**。直接对比每个字符的 ASCII/二进制编码值，大小写敏感，执行速度最快。

### 2.2 生产三大排序规则对比

| 排序规则 | 适用版本 | 精度与国际化支持 | 比较性能 | 典型场景 |
|:---|:---|:---|:---|:---|
| **`utf8mb4_general_ci`** | 早期 5.7 常用 | 较弱（多语言连字、德语变音符特殊转换可能不准） | 极快（简易查表） | 早期追求极致 CPU 节约的国内简单系统 |
| **`utf8mb4_unicode_ci`** | 5.7+ 常用 | 极高（符合 Unicode 标准排序算法 UCA 4.0） | 适中 | 规范的多语言全球化应用 |
| **`utf8mb4_0900_ai_ci`** | **MySQL 8.0 默认** | **最高**（基于 Unicode 9.0 规范，ai 代表 accent-insensitive 重音符不敏感） | 极优（经过全新优化） | **MySQL 8.0 首选推荐** |
| **`utf8mb4_bin`** | 全版本通用 | 精确二进制比对 | 极致 | 区分大小写的账号密码哈希、Token、校验码 |

## 3. 生产极高危事故：跨表字符集不一致导致“索引失效”

这是中高级社招面试与线上事故排查中的经典连环追问。

### 3.1 事故现象
开发人员执行以下联表查询，`orders` 表的 `user_id` 和 `users` 表的 `id` 明明都建了主键或二级索引，但执行计划 `EXPLAIN` 显示 `users` 表居然走了 **`ALL`（全表扫描）**：

```sql
SELECT o.order_no, u.username 
FROM orders o 
LEFT JOIN users u ON o.user_id = u.id 
WHERE o.created_time >= '2026-11-01';
```

### 3.2 事故根因推导（隐式转换）
排查两张表的 DDL 定义发现：
- `orders` 表建于早期，字符集为 `utf8`；
- `users` 表建于后期，字符集为 `utf8mb4`。

在进行关联比对时，因为 `utf8mb4` 是 `utf8` 的超集，MySQL 内部会将较小字符集转换为较大字符集以防止数据丢失，优化器将上述语句在底层**自动改写**为：
```sql
SELECT ... FROM orders o LEFT JOIN users u 
ON CONVERT(o.user_id USING utf8mb4) = u.id; -- 驱动表列转换，或者被驱动表列被函数包裹
```
一旦被驱动表的索引字段参与了函数转换（如 `CONVERT(u.id USING ...)`），**索引树上的排序规律被彻底破坏，MySQL 只能被迫放弃索引，执行全表扫描！**

### 3.3 解决方案
1. **统一字符集**：推动业务窗口期，将所有表的字符集及排序规则统一迁移至 `utf8mb4`。
2. **临时应急修复**：如果无法立即改表，在 SQL 中对驱动表显式强制转换，避免被驱动表失效：
   ```sql
   ON o.user_id = CONVERT(u.id USING utf8) -- 保证被驱动表字段裸露无函数
   ```

## 4. 线上大表平滑迁移 utf8mb4 标准 SOP

如果生产库历史存在千万级 `utf8` 旧表，绝不能直接执行 `ALTER TABLE users CONVERT TO CHARACTER SET utf8mb4;`。在大型生产库上这会锁表数小时，造成业务长时间不可用。

### 正确的平滑迁移步骤：
1. **预估容量增幅**：`utf8` 转 `utf8mb4` 后，原本 3 字节的字符可能扩展，且 `VARCHAR` 长度可能影响唯一索引最大长度（InnoDB 索引键最大限制为 3072 字节，在 `utf8mb4` 下单列最大为 $3072 / 4 = 768$ 个字符）。
2. **使用在线无锁 DDL 工具**：采用 **`gh-ost`** 或 **`pt-online-schema-change`** 进行影子表数据增量同步与切换，全程不锁生产主表。
3. **应用端连接配置核验**：确保 JDBC 驱动 URL 不强制锁死旧字符集：
   ```properties
   # 正确连接串（移除 characterEncoding=utf8，MySQL 8.0 驱动会自动协商 utf8mb4）
   spring.datasource.url=jdbc:mysql://localhost:3306/mall?useUnicode=true&characterEncoding=utf8&serverTimezone=Asia/Shanghai
   ```

## 5. 社招高频面试追问

### Q1：为什么 MySQL 8.0 将默认字符集从 `utf8` 切换为 `utf8mb4`，并且推荐 `utf8mb4_0900_ai_ci`？
- 过去在 MySQL 5.7 中，由于 `utf8mb4_unicode_ci` 需要处理庞大的 Unicode 转换权重规则，其计算性能略逊于简陋的 `utf8mb4_general_ci`。
- MySQL 8.0 对 Unicode 排序算法底层进行了重构与汇编级指令集优化，推出了 `utf8mb4_0900_ai_ci`（基于 Unicode 9.0 规范）。它不仅全面精准支持多语言、生僻字、Emoji 排序，且**执行性能超越了老旧的 `general_ci`**，因此成为了 8.0+ 的第一官方推荐标准。
