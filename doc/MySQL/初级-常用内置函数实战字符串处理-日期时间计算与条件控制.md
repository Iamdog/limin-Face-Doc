# 初级-常用内置函数实战字符串处理-日期时间计算与条件控制

在关系型数据库中，内置函数是处理文本修剪、时间加减、动态分支逻辑转换的利器。然而，初级工程师在使用函数时往往缺乏“执行成本”与“索引友好性”的意识，极其容易写出**“在 WHERE 条件列上套用函数导致索引彻底失效、引发全表扫描”**的灾难级 SQL。本文系统梳理字符串处理、日期时间计算、数值转换与条件控制流的核心内置函数，并深入剖析函数对索引树检索的破坏机理与生产级重构方案。

## 二、源码级实战推导：核心函数用法与规范操作

### 2.1 字符串处理核心函数

```sql
-- 1. 字符串拼接 (CONCAT vs CONCAT_WS)
-- CONCAT 中若任意一个参数为 NULL，整个结果直接返回 NULL!
SELECT CONCAT('Hello', ' ', NULL); -- 返回 NULL (踩坑点!)
-- CONCAT_WS (With Separator): 自动忽略 NULL，指定首个参数为分隔符
SELECT CONCAT_WS('-', '2026', '11', '17'); -- 返回 '2026-11-17'

-- 2. 字节长度 (LENGTH) vs 字符长度 (CHAR_LENGTH)
-- 在 utf8mb4 下，1个汉字占 3~4 字节
SELECT LENGTH('MySQL数据库');      -- 返回 14 (5 + 3*3)
SELECT CHAR_LENGTH('MySQL数据库'); -- 返回 8 (纯字数统计，适合校验昵称字符数)

-- 3. 子串截取 (SUBSTRING: 从第 1 位开始计数)
SELECT SUBSTRING('13812345678', 1, 3); -- 返回 '138' (前缀)
SELECT SUBSTRING('13812345678', 8);    -- 返回 '5678' (后4位)

-- 4. 字符串脱敏与替换 (REPLACE)
SELECT REPLACE('13812345678', '1234', '****'); -- 返回 '138****5678'
```

### 2.2 日期时间计算核心函数

```sql
-- 1. 获取当前即时时间
SELECT NOW();     -- 返回 '2026-11-17 13:30:00' (日期+时间)
SELECT CURDATE(); -- 返回 '2026-11-17' (仅当前日期)

-- 2. 时间增减计算 (DATE_ADD / DATE_SUB)
-- 业务场景：查询 7 天内即将过期的优惠券
SELECT DATE_ADD(NOW(), INTERVAL 7 DAY);
-- 查询 30 天前创建的数据
SELECT DATE_SUB(NOW(), INTERVAL 30 DAY);

-- 3. 日期相差计算
-- DATEDIFF: 仅计算天数差值 (日期1 - 日期2)
SELECT DATEDIFF('2026-11-20', '2026-11-17'); -- 返回 3
-- TIMESTAMPDIFF: 精准计算不同时间粒度差 (年/月/日/时/分/秒)
SELECT TIMESTAMPDIFF(MINUTE, '2026-11-17 12:00:00', '2026-11-17 13:30:00'); -- 返回 90 (分钟)

-- 4. 日期格式化 (DATE_FORMAT)
SELECT DATE_FORMAT(NOW(), '%Y年%m月%d日 %H时%i分%s秒');
```

### 2.3 条件控制流函数（IF & CASE WHEN）

```sql
-- 1. IF(expr, true_val, false_val) 简易三元判断
SELECT 
    order_no,
    pay_amount,
    IF(pay_amount >= 100, '包邮', '收取运费') AS freight_status
FROM t_order;

-- 2. 空值处理 (IFNULL vs COALESCE)
-- IFNULL 仅支持 2 个参数：首选为 NULL 则取次选
SELECT IFNULL(commission_pct, 0.00) FROM t_employee;
-- COALESCE 支持 N 个参数，从左到右返回首个非 NULL 的值
SELECT COALESCE(mobile, telephone, email, '无联系方式') FROM t_user;

-- 3. 复杂多分支条件控制 (CASE WHEN)
-- 业务场景：订单状态数字转中文可读标签，且汇总不同区间的订单量
SELECT 
    order_no,
    status,
    CASE status
        WHEN 0 THEN '待支付'
        WHEN 1 THEN '已支付待发货'
        WHEN 2 THEN '已发货运输中'
        WHEN 3 THEN '已完成'
        ELSE '已取消'
    END AS status_desc,
    -- 结合聚合函数实现行转列指标透视
    CASE 
        WHEN pay_amount < 50 THEN '低客单'
        WHEN pay_amount BETWEEN 50 AND 200 THEN '中客单'
        ELSE '高客单'
    END AS amount_tier
FROM t_order;
```

## 三、社招高频硬核连环追问

### 追问 1：为什么在 `WHERE` 条件中对索引列使用函数（例如 `WHERE DATE(create_time) = '2026-11-17'`），会导致 B+ 树索引彻底失效？

> **考官意图**：考察 B+ 树叶子节点单调有序性的物理本质与谓词转换。

**回答硬核要点**：
1. **破坏了单调有序性（Order Breaking）**：
   - B+ 树索引之所以能进行 $O(\log N)$ 的二分查找，前提是索引树内部保存的键值是**按列的原生绝对值单调有序排列的**。
   - 函数本质是一个数学黑盒映射（$f(x)$），优化器无法预先获知经过 $f(x)$ 运算后的结果在索引树上是否依然有序。
2. **无法下推执行范围查找**：
   - 执行器只能将索引树退化，从根到叶把整张表的所有数据行全部加载一遍，在内存中针对每行数据调用一次函数计算，然后再做比对。
3. **生产级重构 SOP（将函数移到等号右侧）**：
   - 绝不在索引列上套函数，**将计算转移到常量侧**：
     ```sql
     -- 极慢反例 (全表扫描)
     SELECT * FROM t_order WHERE DATE(create_time) = '2026-11-17';

     -- 极速正例 (走 create_time 索引范围扫描 Range Scan)
     SELECT * FROM t_order 
     WHERE create_time >= '2026-11-17 00:00:00' 
       AND create_time <  '2026-11-18 00:00:00';
     ```

---

### 追问 2：MySQL 8.0 引入了“函数索引（Functional Key Parts）”，它从根本上解决了上述问题吗？其实现原理是什么？

> **考官意图**：考察 MySQL 8.0 现代特性与虚拟生成列（Virtual Generated Column）的底层渊源。

**回答硬核要点**：
- **实现原理**：
  - MySQL 8.0.13+ 允许直接在索引定义中包含函数表达式：
    ```sql
    ALTER TABLE t_order ADD INDEX idx_func_date ((DATE(create_time)));
    ```
  - 底层机制是：MySQL 会在内部隐式创建一个看不见的**隐藏虚拟生成列（Virtual Generated Column）**，并将该虚拟列的值存入 B+ 树索引节点中。
- **局限与权衡（Trade-off）**：
  - 虽然允许 `WHERE DATE(create_time) = ...` 命中该函数索引，但它增加了额外的索引树维护开销，且**只对完全吻合该函数签名的查询生效**。在实际工程中，大厂依然优先推荐规范化地书写日期范围查询，而非滥用函数索引。

---

### 追问 3：在统计分析中，`COUNT(IF(status = 1, 1, NULL))` 与 `COUNT(IF(status = 1, 1, 0))` 为什么结果截然不同？

> **考官意图**：考察候选人对 `COUNT()` 的 NULL 忽略机制与 `IF` 函数的组合应用。

**回答硬核要点**：
- **`COUNT(IF(status = 1, 1, 0))` 的严重 Bug**：
  - 当 `status != 1` 时，`IF` 函数返回数字 `0`。
  - **`COUNT(列/表达式)` 只要表达式返回值不是 `NULL`，就会无脑计入数量（数字 0 也是非空值！）**，最终导致统计出来的结果等于**全表的总行数**，完全丧失了过滤效果！
- **正确写法**：
  - 当条件不满足时，必须显式返回 `NULL`（被 `COUNT` 自动忽略）：
    `COUNT(IF(status = 1, 1, NULL))`；
  - 或者使用更标准直观的 `SUM` 累加法：
    `SUM(IF(status = 1, 1, 0))`。

## 四、生产级避坑指南与排障 SOP

### 4.1 生产级常用函数避坑矩阵

| 错误写法 | 隐形地雷 | 工业级改造方案 |
| :--- | :--- | :--- |
| **`WHERE YEAR(birth_date) = 1995`** | 索引列套用 `YEAR()` 函数导致全表扫描 | 改为范围过滤：`WHERE birth_date >= '1995-01-01' AND birth_date <= '1995-12-31'` |
| **`WHERE status + 1 = 2`** | 索引列参与算术运算破坏索引二分检索 | 算术运算移到常量侧：`WHERE status = 2 - 1` |
| **`WHERE CONCAT(first_name, last_name) = '张三'`** | 联合索引列拼接后索引失效 | 拆解为多列精确匹配：`WHERE first_name = '张' AND last_name = '三'` |
| **`SELECT NOW()` 包含毫秒精度丢失** | `NOW()` 默认只保留到秒 | 若需毫秒精度，显式声明精度：`NOW(3)` 或 `NOW(6)` |

### 4.2 行转列（Pivot）透视报表经典实战 SOP

使用 `SUM(CASE WHEN ...)` 语法，在单条高效 SQL 中实现按月份分列透视统计：

```sql
-- 统计每个用户在 2026 年 Q1 各月份的充值总金额（由多行展开为横向三列）
SELECT 
    user_id,
    SUM(CASE WHEN MONTH(pay_time) = 1 THEN pay_amount ELSE 0 END) AS m1_amount,
    SUM(CASE WHEN MONTH(pay_time) = 2 THEN pay_amount ELSE 0 END) AS m2_amount,
    SUM(CASE WHEN MONTH(pay_time) = 3 THEN pay_amount ELSE 0 END) AS m3_amount,
    SUM(pay_amount) AS q1_total_amount
FROM mall_db.t_recharge_record
WHERE pay_time >= '2026-01-01 00:00:00' 
  AND pay_time <  '2026-04-01 00:00:00'
GROUP BY user_id;
```
