# 初级-核心数据类型选用规范数值-字符串-日期时间与JSON

在数据库建表设计中，数据类型的选择直接决定了**磁盘存储空间、内存利用率（Buffer Pool 缓存命中率）以及查询性能（B+ 树节点扇出大小）**。许多初级工程师常犯“盲目全部用 BIGINT、VARCHAR(255)”的严重错误，不仅导致存储体积翻倍膨胀，还会急剧降低索引性能与 I/O 效率。本文全面解析 MySQL 核心数据类型（整型、定点数、变长字符串、时间戳与 JSON）的底层存储字节与精准选型规范。

---

## 一、核心底层机制与全景架构

### 1.1 常用核心数据类型物理存储空间与边界全景矩阵

```mermaid

    Type[MySQL 数据类型选型决策树] --> Num[数值类型]
    Type --> Str[字符串类型]
    Type --> Time[日期时间类型]
    Type --> Adv[现代高级类型]

    Num --> INT1[TINYINT: 1字节 / -128~127 或 0~255]
    Num --> INT4[INT: 4字节 / 约 +/- 21亿]
    Num --> INT8[BIGINT: 8字节 / 约 +/- 922亿亿]

```

### 1.2 核心数据类型物理存储与边界速查表

| 数据类型 | 物理占用字节 | 存储取值范围 / 语义边界 | 最佳业务选型场景 |
| :--- | :--- | :--- | :--- |
| **`TINYINT`** | 1 字节 | 有符号: `-128 ~ 127`<br/>无符号: `0 ~ 255` | 状态位（如 `status`：0待付, 1已付）、性别、逻辑删除标记 `is_deleted` |
| **`INT`** | 4 字节 | 有符号: 约 `-21亿 ~ +21亿`<br/>无符号: 约 `0 ~ 42.9亿` | 绝大部分常规业务主键或外键 ID（单表行数在千万级以内） |
| **`BIGINT`** | 8 字节 | 无符号: `0 ~ 1844亿亿` | 分布式全局唯一 ID（雪花算法 Snowflake ID）、海量流水账单表主键 |
| **`DECIMAL(M,D)`** | 变长（每 9 位数字占 4 字节） | `M` 为总有效数字位数（<=65），`D` 为小数点后位数 | **所有涉及金钱、价格、财务结算的字段（绝对严禁使用 FLOAT/DOUBLE）** |
| **`CHAR(N)`** | $N \times \text{字符集单字字节}$ | 固定长度字符（不足长度右侧自动补空格） | 长度固定字符串：MD5 校验码（32位）、UUID、国家/省份标准编码 |
| **`VARCHAR(N)`** | 实际字符长度 + 1~2 字节长度前缀 | 变长字符串（$N$ 表示字符数，不是字节数） | 长度动态波动的文本：用户名、标题、地址、邮箱 |
| **`DATETIME`** | 5 字节（带微秒增至 8 字节） | `1000-01-01 00:00:00` 至 `9999-12-31` | 业务真实事件发生时间（不受时区变动影响，推荐标准） |
| **`TIMESTAMP`** | 4 字节 | `1970-01-01` 至 `2038-01-19 03:14:07` | 仅适合记录 UTC 时间戳且必须有时区自动转换特性的特定场景 |

## 二、源码级实战推导：浮点精度丢失与 VARCHAR 物理行限制

### 2.1 浮点数（FLOAT/DOUBLE）精度丢失推导

计算机底层采用 IEEE 754 标准以二进制科学计数法存储浮点数（底数 $\times 2^{\text{指数}}$）。因为很多十进制小数（例如 `0.1`）在二进制下是无限循环小数，强制截断后会产生微小误差：

```sql
-- 试验：浮点数累加引发的致命财务灾难
CREATE TABLE t_money_test (
    amount_float FLOAT NOT NULL,
    amount_decimal DECIMAL(10, 2) NOT NULL
);

INSERT INTO t_money_test VALUES (0.1, 0.1), (0.2, 0.2);

-- 查询累加结果对比
SELECT SUM(amount_float), SUM(amount_decimal) FROM t_money_test;
-- 输出结果：
-- SUM(amount_float)   = 0.30000000447034836  (发生精度畸变！在财务对账中会直接导致账不平)
-- SUM(amount_decimal) = 0.30                 (精确无误)
```

> **底层解析**：`DECIMAL` 在底层采用**定点数十进制紧凑数组**表示，整数部分和小数部分分别按每 9 个十进制数字打包压缩为 4 个字节进行无损整数计算，因此能实现 100% 绝对精确的金融级运算。

### 2.2 `VARCHAR(N)` 的物理极限：为什么不能建 `VARCHAR(65535)`？

很多初学者认为 `VARCHAR` 最多能存 65535 个字符，但在建表时直接写 `VARCHAR(65535)` 会立即报错：

```sql
-- 报错: Row size too large. The maximum row size for the used table type, not counting BLOBs, is 65535.
CREATE TABLE t_overflow (
    content VARCHAR(65535)
) CHARSET=utf8mb4;
```

**数学物理推导过程**：
1. **InnoDB 行物理限制（Row Size Limit）**：单个数据行中所有列定义的总长度（除大文本溢出指针外）**不能超过 65535 个字节**。
2. **字节与字符换算**：`utf8mb4` 字符集下一个字符最多占用 4 个字节。
3. **行额外开销（Row Overhead）**：
   - 长度大于 255 字节的 `VARCHAR` 需占用 **2 个字节** 存储长度前缀；
   - 若字段允许为 NULL，还需占用 **1 个字节** 的 NULL 标志位位图（NULL Bit Mask）。
4. **最大允许字符数计算公式**：
   $$N_{\max} = \frac{65535 - 2 (\text{长度前缀}) - 1 (\text{NULL标志位})}{4 (\text{每个字符最大字节})} = \frac{65532}{4} = 16383$$
   因此在 `utf8mb4` 字符集下，单列 `VARCHAR` 的最大上限只能是 `VARCHAR(16383)`！

## 三、社招高频硬核连环追问

### 追问 1：建表语句中写 `INT(4)` 和 `INT(11)`，它们能存储的最大数字是一样的吗？括号里的数字到底代表什么？

> **考官意图**：考察候选人对整数字节存储与可视化显示格式的本质区分能力。

**回答硬核要点**：
- **最大取值范围绝对完全一样！**
  - 不论是 `INT(4)` 还是 `INT(11)`，在底层操作系统与磁盘物理层面，它们都**恒定占用 4 个字节（32 位二进制）**，有符号整型的取值范围永远是 `-2,147,483,648 ~ 2,147,483,647`。
- **括号内数字的真实含义**：
  - 括号里的数字仅仅代表**显示宽度（Display Width）**，且**必须搭配 `ZEROFILL` 属性时才会有可见视觉效果**！
  - 例如声明 `id INT(4) ZEROFILL`，当插入数字 `5` 时，命令行客户端查询出来会展示为 `0005`（不足 4 位在左侧自动用 0 填充显示）；若未指定 `ZEROFILL`，括号里的数字没有任何物理意义。在 MySQL 8.0.17+ 中，官方已彻底废弃整型类型的显示宽度语法。

---

### 追问 2：为什么记录时间时，大厂普遍强制规范使用 `DATETIME` 而非 `TIMESTAMP`？

> **考官意图**：考察系统跨跨周期可用性与时区灾备安全。

**回答硬核要点**：
1. **2038 年灾难（Y2038 Problem）**：
   - `TIMESTAMP` 底层采用 32 位有符号整数记录自 Unix 纪元（1970-01-01）以来的秒数，它的物理极限是 **2038-01-19 03:14:07**。一旦超出该时间点，整数溢出变为负数，导致业务时间倒退产生严重 Bug。
   - `DATETIME` 占用 5 字节，时间范围直接覆盖至 **9999 年**，彻底杜绝 2038 年隐患。
2. **时区变更引发的脏数据灾难**：
   - `TIMESTAMP` 在写入时会将本地时间转为 UTC 时间存盘，读取时根据客户端当前会话时区（`time_zone`）动态反解。如果跨国业务客户端或者数据库服务器的时区配置发生改变，查询出来的时间就会偏移数小时。
   - `DATETIME` 是所见即所得的绝对时间，不随系统时区变更而漂移，具有更稳定的确定性。

### 追问 3：为什么即使字符只占几个字节，也不建议把 `VARCHAR(20)` 随手写成 `VARCHAR(255)`？

> **考官意图**：考察对内存临时表（Memory Temp Table）与排序缓冲区（Sort Buffer）内存开销的认知深度。

**回答硬核要点**：
1. **磁盘层面没区别，但内存层面差异巨大**：
   - 在 InnoDB 磁盘存储与写入时，`VARCHAR` 是按实际字符串长度加前缀存储的，存 `"abc"` 确实只占 3 字节。
2. **内存消耗暴增（Memory Allocation）**：
   - 当 SQL 执行复杂的 `GROUP BY`、`DISTINCT` 或 `ORDER BY` 时，MySQL 需要在内存中开辟**内部临时表（Internal Temporary Table）**或 `Sort Buffer`。
   - 内部内存临时表（MEMORY 引擎）底层通常采用**定长固定内存块分配策略**：它会直接按列定义的最大可能长度分配空间！
   - `VARCHAR(255)` 在 `utf8mb4` 下会被预先分配 $255 \times 4 = 1020$ 字节内存；而 `VARCHAR(20)` 仅分配 80 字节。原本可以容纳 10 万行数据的内存空间瞬间被撑满，导致频繁溢出并退化为**慢速磁盘临时表（On-disk Temp Table）**，引发严重的 I/O 延迟与性能崩塌。

## 四、生产级避坑指南与排障 SOP

### 4.1 生产级数据类型选型避坑速查

| 字段业务场景 | 错误选型代码 | 工业级推荐规范 | 选型原理解析 |
| :--- | :--- | :--- | :--- |
| **手机号码** | `BIGINT` | `VARCHAR(20)` | 手机号无需参与数值加减运算；可能有以 `0` 开头的特殊号码或国际区号（如 `+86`） |
| **商品价格/账户余额** | `FLOAT / DOUBLE` | `DECIMAL(12, 2)` | 严禁浮点数运算，防止对账产生分毫误差 |
| **用户 IP 地址** | `VARCHAR(15)` | `INT UNSIGNED` | 配合 `INET_ATON()` / `INET_NTOA()` 存储为 4 字节无符号整型，节约 70% 空间且索引查询极快 |
| **枚举状态（如审核中/通过/拒绝）**| `ENUM('A','B')` | `TINYINT` | MySQL 的 `ENUM` 修改枚举成员需要重建表锁表，扩展性极差；推荐用 `TINYINT` + 应用层常量 |
| **动态拓展属性/用户画像标签** | 盲目添加预留字段 `col1, col2` | 原生 `JSON` 类型 | 支持半结构化数据，且可基于 JSON 虚拟列建立二级索引 |

### 4.2 JSON 原生字段与虚拟列索引加速实战

在 MySQL 5.7+ 中，面对商品多规格参数或动态扩展属性，推荐使用原生 JSON 结合**虚拟生成列（Generated Column）**实现秒级索引查询：

```sql
-- 1. 创建带有 JSON 扩展属性的商品表
CREATE TABLE mall_db.t_goods (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    title VARCHAR(128) NOT NULL,
    specs JSON NOT NULL COMMENT '动态规格JSON: {"color": "red", "size": "XL"}',
    -- 核心优化：定义虚拟列，自动提取 JSON 内部字段
    v_color VARCHAR(32) GENERATED ALWAYS AS (specs->>'$.color') VIRTUAL,
    PRIMARY KEY (id),
    -- 为虚拟列建立常规 B+ 树索引
    KEY idx_specs_color (v_color)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 2. 插入测试数据
INSERT INTO mall_db.t_goods (title, specs) 
VALUES ('秋冬连帽卫衣', '{"color": "crimson", "size": "XXL"}');

-- 3. 查询时直接走虚拟列索引，告别全表扫描！
EXPLAIN SELECT * FROM mall_db.t_goods WHERE v_color = 'crimson';
```
