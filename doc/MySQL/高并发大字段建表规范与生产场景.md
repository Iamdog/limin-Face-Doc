# 高并发大字段建表规范与数据类型精准选型

在 MySQL 数据库架构设计中，表结构一旦上线，后期的 DDL 变更代价极其高昂。如果字段类型选型不当或大字段滥用，随着数据量突破千万级，将直接引发 Buffer Pool 污染、大量行溢出、页分裂以及性能雪崩。

---

## 1. 核心数据类型精准选型与生产避坑

### 1.1 数值类型：整型与金额计算
- **整型选型（TINYINT / SMALLINT / INT / BIGINT）**：
  - 状态位、性别、开关等一律用 `TINYINT`（1 字节，范围 -128~127，无符号 0~255）。
  - 主键 ID、交易订单号在千万级系统必须使用 `BIGINT UNSIGNED`（8 字节，避免 INT 4 字节 21 亿上限溢出灾难）。
  - **避坑：`INT(11)` 里的 11 是什么含义？**  
    11 **不代表存储长度**，也不代表数值范围。`INT` 无论括号内写多少永远占 4 字节。11 只是客户端（如 Navicat/CLI）配合 `ZEROFILL` 属性时的**最小显示宽度**（若不足 11 位前面补 0）。
- **高精度金融金额：严禁使用 FLOAT / DOUBLE**：
  - `FLOAT` / `DOUBLE` 是二进制浮点数，底层遵循 IEEE 754 标准，很多小数（如 0.1）在二进制中是无限循环小数，无法精确表示，计算时必然存在精度丢失（如 `0.1 + 0.2 = 0.30000000000000004`）。
  - 金额、费率、佣金一律使用 `DECIMAL(M, D)`。
    - $M$ 代表总位数（有效数字），$D$ 代表小数位数。例如 `DECIMAL(10, 2)` 表示整数部分最多 8 位，小数部分 2 位。
    - 另一种高性能做法：在业务层统一以“分”或“厘”为单位，在数据库中使用 `BIGINT` 存储（例如 100.50 元存为 10050）。

### 1.2 字符类型：VARCHAR vs CHAR
- **`CHAR(N)`**：固定长度字符串。存储时不足 $N$ 个字符会在末尾用空格补齐，检索时 MySQL 默认会移除末尾空格。适用于长度恒定的短字段（如 MD5 哈希 32 位、国家代码 2 位、手机号 11 位）。
- **`VARCHAR(N)`**：可变长度字符串。存储时需要额外的 1~2 个字节记录实际字符串的长度（长度 $\le 255$ 字节用 1 字节记录，$> 255$ 字节用 2 字节记录）。
  - **$N$ 代表什么？** 在 MySQL 5.0+ 中，$N$ 代表**字符数**，而非字节数。在 `utf8mb4` 字符集下，1 个汉字或 Emoji 占用 1~4 字节，`VARCHAR(20)` 可以存 20 个汉字。
  - **为什么建议高频字段长度设为 255 以内（如 `VARCHAR(128)`、`VARCHAR(255)`）？**
    1. 长度 $\le 255$ 字节时，长度信息仅占 1 字节。
    2. 内存临时表和排序操作（filesort）在分配内存时，会根据字段定义的最大长度预分配固定内存空间。若将手机号设为 `VARCHAR(1000)`，排序时将极度浪费内存并容易导致排序下推磁盘。

### 1.3 时间类型：DATETIME vs TIMESTAMP
| 对比维度 | `DATETIME` | `TIMESTAMP` |
|:---|:---|:---|
| 存储占用 | 5 字节（MySQL 5.6.4+） | 4 字节 |
| 时间范围 | `1000-01-01` 到 `9999-12-31` | `1970-01-01` 到 `2038-01-19`（2038年问题） |
| 时区相关性 | **与时区无关**，存什么取出来就是什么 | **与时区强相关**，存入时转为 UTC，取出时按当前时区转换 |
| 生产推荐 | 绝大多数业务系统**强烈推荐** `DATETIME` | 仅在需要跨全球多时区强绑定的遗留系统中使用 |

> **2038 年灾难风险**：`TIMESTAMP` 只有 4 字节有符号整数，最大值为 $2^{31}-1 = 2147483647$ 秒，将在北京时间 2038-01-19 11:14:07 溢出。金融与长效业务绝对不可使用。

## 2. InnoDB 16KB 数据页与“行溢出”机制

### 2.1 为什么大字段是性能杀手？
InnoDB 存储引擎以 **数据页（Page，默认 16KB）** 为最小物理 I/O 单位。B+ 树的每个叶子节点就是一个 16KB 的数据页。
- 理论上，一个 16KB 的数据页应该容纳数百条记录，保证 B+ 树的矮胖结构与极高的缓存命中率。
- **行溢出（Off-Page / Page Overflow）原理**：
  InnoDB 的 Compact / Dynamic 行格式规定：一个数据页必须至少容纳两行数据（保证 B+ 树树形结构的平衡）。如果某一行包含了 `TEXT`、`BLOB`、超长 `VARCHAR` 或超大 `JSON`，使得行大小超过限制（约 8KB），InnoDB 就会发生**行溢出**：
  - 在当前主数据页中，大字段的位置仅保留一个 **20 字节的指针**（指向溢出页）。
  - 大字段的真实内容被单独写入独立的**溢出页（Overflow Page）**链表中。

```text
聚簇索引 16KB 叶子节点页 (主页)
┌───────────────────────────────────────────────┐
│ id: 101 | title: "旗舰手机" | price: 4999.00  │
│ detail_ptr: ───┐ (主页内仅留 20 字节指针)     │
└────────────────┼──────────────────────────────┘
                 ▼ 跨页离散 I/O
           独立溢出页 (Overflow Page)
┌───────────────────────────────────────────────┐
│ <p>这里是 50KB 的富文本图文详情与动态参数规格...</p>│
└───────────────────────────────────────────────┘
```

### 2.2 大字段引发的线上性能灾难
1. **Buffer Pool 内存命中率雪崩**：
   MySQL 服务器的物理内存有限。执行一次未控制列的 `SELECT *`，巨量的大字段溢出页数据会迅速涌入 Buffer Pool，导致系统真正高频访问的核心热点索引和轻量数据页被强制通过 LRU 淘汰出内存！
2. **磁盘随机 I/O 暴增**：
   本来读取一行数据只需读 1 个聚簇索引物理页，一旦涉及溢出页，磁盘需要额外发起多次跨扇区的随机物理寻道。

## 3. 高并发建表三大架构铁律

### 3.1 铁律一：大字段冷热分离（垂直拆表）
将高频访问的“热数据”（如商品标题、价格、库存、状态、创建时间）留在主表；将极低频访问、大体积的“冷数据”（如富文本详情 HTML、大规格 JSON、审计入参）拆分到独立的扩展表中。
- **列表查询**：只查询主表，100% 走覆盖索引，数据页极其紧凑，单页行数翻倍，缓存命中率极高。
- **详情页查询**：用户真正点击进入商品详情时，按主键 ID 单次懒加载扩展表。

### 3.2 铁律二：超长多媒体数据沉淀至对象存储（OSS / MinIO）
- 如果富文本、长图、音视频、大附件体积超过 64KB，**严禁直接存入 MySQL 表**。
- **最佳实践**：前端/后端将大文件直传到云对象存储（OSS/COS）或本地 MinIO，MySQL 表中仅保存文件的访问 URL（`VARCHAR(255)`）。

### 3.3 铁律三：主键严禁使用随机 UUID，必须保持趋势递增
- **UUID 的致命缺陷**：UUID 是完全随机分布的。每次插入新记录，数据会被随机插入到已经充满的 16KB 数据页中间，**强制触发昂贵的“B+ 树页分裂（Page Split）”**，导致大量数据页利用率不足 50%，产生大量磁盘碎片，写性能腰斩。
- **推荐方案**：
  - 单库单表：`BIGINT UNSIGNED AUTO_INCREMENT`。
  - 分布式多库分表：雪花算法（Snowflake ID），高位时间戳保证趋势递增，低位机器号保证分布式唯一。

## 4. 生产环境冷热分离标准建表范式

### 4.1 商品核心主表（热表：极致紧凑与高性能索引）
```sql
CREATE TABLE `mall_product` (
  `id` BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '商品主键ID(趋势递增)',
  `title` VARCHAR(128) NOT NULL COMMENT '商品标题',
  `category_id` INT UNSIGNED NOT NULL COMMENT '分类ID',
  `price` DECIMAL(10, 2) NOT NULL DEFAULT '0.00' COMMENT '售价(严禁FLOAT)',
  `stock` INT UNSIGNED NOT NULL DEFAULT '0' COMMENT '可用库存',
  `status` TINYINT NOT NULL DEFAULT '1' COMMENT '状态: 0-下架, 1-在售, 2-售罄',
  `sales_count` INT UNSIGNED NOT NULL DEFAULT '0' COMMENT '销量',
  `created_time` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  `updated_time` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  INDEX `idx_category_status` (`category_id`, `status`),
  INDEX `idx_created_time` (`created_time`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='商品基础主表(热表)';
```

### 4.2 商品图文详情扩展表（冷表：按需懒加载，彻底隔离行溢出）
```sql
CREATE TABLE `mall_product_detail` (
  `product_id` BIGINT UNSIGNED NOT NULL COMMENT '关联主表ID(1对1共享主键)',
  `intro_html` MEDIUMTEXT NOT NULL COMMENT '图文富文本详情(大字段隔离)',
  `specs_json` JSON NULL COMMENT '商品动态属性规格参数(大JSON)',
  `updated_time` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`product_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='商品图文详情扩展表(冷表)';
```

## 5. 社招高频面试追问

### Q1：为什么生产规范强烈要求字段尽量定义为 `NOT NULL`？
1. **NULL 会破坏索引统计精度**：在 MySQL 中，包含 NULL 值的列在构建复合索引时，NULL 参与比较需要特殊处理，使得优化器在评估 Cardinality 时更加复杂且易发生偏差。
2. **存储空间开销**：InnoDB 每行记录的头部需要额外的 **NULL 值列表（NULL Bitmap）** 来记录哪些列为 NULL。
3. **避坑陷阱**：在 SQL 进行 `COUNT(column)` 时，该列为 NULL 的记录会被自动忽略；在使用 `!=` 或 `IN` 操作时，遇到 NULL 会出现三值逻辑（TRUE, FALSE, UNKNOWN），极易引发业务 Bug。
4. **推荐做法**：数值类型给默认值 `0`，字符串类型给默认值 `''`（空字符串）。

### Q2：`VARCHAR(50)` 改成 `VARCHAR(100)` 是否会锁表？
- 在 MySQL 5.7+ 和 8.0 中，在 0~255 字节范围内的扩大（例如字符集为 `latin1` 时由 50 扩到 100，长度字节保持 1 字节），属于 **In-Place 原地修改**，无需重建表，执行极快。
- 但是，如果扩容跨越了 255 字节门槛（例如长度记录字节由 1 字节变为 2 字节），或者由 `VARCHAR(100)` 扩到 `VARCHAR(300)`，MySQL 会退化为 **COPY 方式重建整张表**，引起长锁甚至线上业务超时！
