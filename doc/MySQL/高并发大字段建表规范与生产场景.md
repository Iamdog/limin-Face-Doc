## 一、 核心底层机制：InnoDB 16KB 数据页与“行溢出”

### 1. 为什么大字段是性能杀手？
InnoDB 存储引擎是以 **数据页（Page，默认 16KB）** 为最小单位读写磁盘的。B+ 树的每个叶子节点就是一个 16KB 的数据页。

- 一个 16KB 的页，理想状态下应该容纳数百条轻量行记录。
- **行溢出（Off-Page / Page Overflow）**：
  若单行数据超过约 8KB（Compact / Dynamic 行格式规定一页至少容纳两行数据），InnoDB 会强制将 `TEXT`、`BLOB` 或超长 `VARCHAR` 的实际内容**剥离出去，写入独立的溢出页（Overflow Page）**，原行中仅保留一个 20 字节的指针指向溢出页。

```text
聚簇索引 16KB 数据页 (主页)
┌───────────────────────────────────────────────┐
│ id: 101 | title: "手机" | price: 4999         │
│ detail_ptr: ───┐ (只保留 20 字节指针)        │
└────────────────┼──────────────────────────────┘
                 ▼ 跨页随机读取
           独立溢出页 (Overflow Page)
┌───────────────────────────────────────────────┐
│ <p>这里是数万字符的商品高清详情与富文本 HTML...</p>│
└───────────────────────────────────────────────┘
```

### 2. 引发的两大线上灾难
1. **Buffer Pool 命中率雪崩**：
   MySQL 内存中的缓冲池（Buffer Pool）是有限的。执行一次未加限制的 `SELECT *`，大字段的巨量数据会把宝贵的内存页占满，导致原本高频访问的“热点主键索引和轻量数据”被强制 LRU 淘汰出内存！
2. **磁盘随机 I/O 暴增**：
   读取包含大字段的一行数据，原本只需要读 1 个磁盘页，现在需要额外发起多次跨扇区的随机磁盘寻道去抓取溢出页。

## 二、 高并发建表三大铁律

### 1. 核心军规一：大字段与主表“冷热分离”（垂直拆表）
将高频访问的“热数据”（如标题、价格、状态、创建时间）留在主表；将极低频访问、大体积的“冷数据”（如长详情 HTML、操作日记、原始入参 JSON）拆出到独立的扩展表。

- **列表展示页**：仅查询主表，100% 走覆盖索引，单页容纳行数极多，内存缓存命中率极高。
- **详情展示页**：仅在用户真正点进详情时，根据主键 ID 单次懒加载扩展表。

### 2. 核心军规二：超长多媒体数据沉淀至对象存储（OSS / MinIO）
如果富文本、图文排版、视频介绍体积超过 64KB：
- **严禁直接存入 MySQL！**
- **正规方案**：后端将文件或大文本直传到阿里 OSS、腾讯 COS 或自建 MinIO，MySQL 表中仅保存一个长度为 `VARCHAR(255)` 的 URL 访问链接。

### 3. 核心军规三：主键严禁用 UUID，必须趋势递增（防 B+ 树页分裂）
- **UUID 的致命缺陷**：UUID 是完全随机无序的。每次插入新行，数据可能随机插入到已满的 16KB 索引页中间，**强制触发昂贵的“B+ 树页分裂（Page Split）”**，导致磁盘碎片率高达 50%，写吞吐量急剧下滑。
- **推荐主键方案**：
  - 单库单表：`BIGINT UNSIGNED AUTO_INCREMENT`（原生自增）。
  - 分布式多库分表：**雪花算法（Snowflake ID）**（高位时间戳保证趋势递增，低位机器码保证全局唯一）。

## 三、 最小 MVP 生产建表设计实战（冷热分离最佳范式）

### 1. 商品核心主表（热表：极致紧凑与高性能索引）
```sql
CREATE TABLE `mall_product` (
  `id` BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '商品主键ID(趋势递增)',
  `title` VARCHAR(128) NOT NULL COMMENT '商品标题(前缀索引)',
  `category_id` INT UNSIGNED NOT NULL COMMENT '所属分类ID',
  `price` DECIMAL(10, 2) NOT NULL DEFAULT '0.00' COMMENT '售价(严禁FLOAT浮点数)',
  `stock` INT UNSIGNED NOT NULL DEFAULT '0' COMMENT '库存',
  `status` TINYINT NOT NULL DEFAULT '1' COMMENT '状态: 0-下架, 1-在售, 2-售罄',
  `sales_count` INT UNSIGNED NOT NULL DEFAULT '0' COMMENT '销量',
  `created_time` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  `updated_time` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  INDEX `idx_category_status` (`category_id`, `status`),
  INDEX `idx_created_time` (`created_time`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='商品基础主表(热表)';
```

---

### 2. 商品图文详情扩展表（冷表：按需加载，隔离行溢出）
```sql
CREATE TABLE `mall_product_detail` (
  `product_id` BIGINT UNSIGNED NOT NULL COMMENT '关联主表ID(1对1共享主键)',
  `intro_html` MEDIUMTEXT NOT NULL COMMENT '图文富文本详情(大字段隔离)',
  `specs_json` JSON NULL COMMENT '商品动态属性规格参数(大JSON)',
  `updated_time` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`product_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='商品详情扩展表(冷表)';
```

## 四、 常见字段类型精准选型速查表（实战加分项）

| 业务场景 | 错误设计 | 正规高并发设计 | 性能提升根因 |
| :--- | :--- | :--- | :--- |
| **状态/布尔值** | `VARCHAR(10)` ('ENABLE') | `TINYINT` (0/1/2) | 占用 1 字节 vs 数十字节，CPU 整数比对快于字符串 |
| **金额货币** | `FLOAT` / `DOUBLE` | `DECIMAL(10, 2)` 或存以分为单位的 `BIGINT` | 避免二进制浮点数精度截断丢失（0.1+0.2 != 0.3） |
| **时间字段** | `VARCHAR(20)` | `DATETIME(0)` (5字节) 或 `TIMESTAMP` (4字节) | 节省空间，支持内置原生日期范围比较与分区表 |
| **IP 地址** | `VARCHAR(15)` | `INT UNSIGNED` (结合 `INET_ATON()`) | 仅占 4 字节，走索引范围检索极快 |
| **固定长度码** | `VARCHAR(32)` (MD5) | `CHAR(32)` | 定长列不需要额外的 1~2 字节长度记录头，碎片更少 |
