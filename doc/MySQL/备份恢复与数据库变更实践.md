# 备份恢复与数据库变更实践

## 解决什么问题

误删、磁盘损坏、迁移失败和发布改错字段都需要恢复数据。复制和高可用提升可用性，但误删可能同步到所有副本，因此备份必须独立存在并能实际恢复。

## 基本使用：先在隔离环境恢复一次

以下适用于有事务表的 MySQL 演练环境，数据库名 `demo` 为示例。用交互密码或受控凭证配置，避免把密码直接写入命令与仓库。

```bash
mysqldump -u backup_user -p --single-transaction --routines --events --triggers --databases demo > demo.sql
mysql -u restore_user -p < demo.sql
```

恢复命令应在独立测试实例上执行，`--databases` 包含建库和 USE 语句，不能为了测试把文件导入生产实例。`--single-transaction` 提供事务表的一致性快照，不保证非事务表一致性；备份过程中避免影响结构的 DDL。权限、GTID、版本、字符集和对象定义需要按环境处理。大库可评估物理备份，不能把此逻辑备份命令当作所有规模的方案。

恢复后检查表结构、行数、关键业务总额、索引、触发器和程序能否正常读写，并记录备份耗时、恢复耗时和文件校验值。

## 维护流程与基础概念

| 能力 | 基本做法 | 验证 |
|---|---|---|
| 全量备份 | 定期复制可恢复数据和结构 | 独立实例恢复并校验业务 |
| binlog 保留 | 连续保留变更日志和恢复位点 | 证明全量备份之后日志完整可用 |
| RPO | 允许丢失多长时间的数据 | 最近可恢复位点距故障时间多久 |
| RTO | 允许多久恢复服务 | 实测恢复、校验、切流总耗时 |
| 数据变更 | 预览条件、分批、审计与回滚 | 影响行数和预期一致 |
| DDL | 评估算法、锁、容量、复制影响 | 在相近数据量下演练 |

## 常见场景：误删后按时间点恢复

1. 冻结相关写入并保留现场，不覆盖现有备份与日志。
2. 确定错误事务、时间范围、备份位点及业务恢复目标。
3. 在隔离实例恢复全量备份，重放之后的 binlog 至错误事务前的正确边界。
4. 核对数据，用业务规则决定恢复整库、受影响记录还是合并之后的合法新写入。
5. 完成审计、切换和应用验证，再恢复流量。

`mysqlbinlog` 可以查看和重放日志；时间戳只是定位线索，精确事务/GTID/position 更可靠。不要把“跳过一条 DELETE”当作通用恢复，因为后续事务可能依赖它，跨表约束也可能受到影响。

## 常见场景：发布改变表结构

采用兼容的扩展 → 应用迁移 → 收缩流程。例如先增加允许为空的新字段，发布同时兼容新旧字段的应用，再分批回填、核对一致性，最后约束收紧和移除旧字段。在线 DDL 仍可能在开始/结束时等待元数据锁，并消耗 I/O、CPU 和临时空间。应用回滚也要与数据库版本兼容。

`ALTER TABLE` 等 DDL 常有隐式提交，不能指望事务 ROLLBACK 撤销所有结构变更。具体支持的 ALGORITHM 和 LOCK 随版本和操作变化。

## 面试递进

| 基础题 | 场景追问 | 深入要点 |
|---|---|---|
| 主从复制算备份吗？ | 误删同步到从库怎么办？ | 独立备份、日志保留和时间点恢复 |
| 怎么证明备份成功？ | 有 SQL 文件但恢复失败怎么办？ | 恢复演练、对象/权限/版本检查 |
| 在线 DDL 就不锁表吗？ | ALTER 长时间等待如何定位？ | MDL、长事务、资源与复制延迟 |
| 如何安全回滚发布？ | 应用已写入新结构怎么办？ | 向后兼容、数据回填与回滚边界 |
| 怎么确定 RPO/RTO？ | 能否接受丢失一分钟？ | 业务目标与备份/复制/切流成本 |
