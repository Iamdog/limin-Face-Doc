# 登录认证、权限与接口安全基础

## 解决什么问题

认证回答“你是谁”，授权回答“你能操作什么”。先实现登录、退出和服务端资源权限，再考虑签名、网关和复杂安全架构。前端隐藏按钮不能阻止用户直接调用接口。

## 基本使用：最小登录与权限流程

1. 服务端校验用户名密码或合法的第三方登录凭证；密码用专门密码哈希算法及合适成本参数，不明文存储或使用普通快速哈希。
2. 创建 Session 或签发经过验证的 Token，设定过期、撤销、刷新和退出规则。
3. 每次请求从可信会话提取用户身份，不相信请求 body 自填的 userId/role。
4. 验证操作权限和资源归属，匿名、普通用户、管理员分别测试。
5. 返回一致的 401/403/业务错误信息，记录必要审计但不记录密码、完整 Token 和敏感正文。

资源授权示意：

```sql
SELECT id, status FROM orders
WHERE id = :order_id AND user_id = :authenticated_user_id;
```

`:authenticated_user_id` 来自服务端验证后的身份，SQL 参数必须绑定，不能拼接。对更新、删除、下载、导出和批量接口同样校验；管理员通道需独立验证权限和范围。

## 方案选择与使用边界

| 方案 | 基本用法 | 代价与边界 |
|---|---|---|
| 服务端 Session | 客户端持会话标识，服务端保存会话 | 需要共享存储、过期和容量治理；撤销相对直接 |
| JWT | 校验签名、算法、issuer、audience、有效期 | 签名不是加密；立即撤销需额外状态，不能只解码 payload |
| RBAC | 用户→角色→权限 | 对对象、租户、组织范围仍需数据授权 |
| Cookie | HttpOnly/Secure/SameSite，限制域和路径 | 凭证自动携带时评估 CSRF；XSS 仍能发起同源操作 |
| Bearer Token | Authorization 携带，明确保存策略 | 脚本可读取的存储受 XSS 风险影响 |
| OAuth/OIDC | 使用成熟库处理授权码、state、PKCE 和身份校验 | OAuth 是授权框架，不能把任意 access token 当作身份证明 |

## 常见场景与防护

- **越权**：改变订单 ID、租户 ID 或批量 ID 尝试读取他人数据，服务端逐项校验资源权限。
- **SQL 注入**：使用参数绑定；表名、排序字段等不能绑定的位置用严格白名单。
- **XSS**：默认转义、可信 HTML 消毒、CSP 和依赖治理。
- **CSRF**：结合 SameSite、CSRF Token、Origin 校验；CORS 不能代替 CSRF 防护。
- **SSRF**：服务端请求外部 URL 时限制协议、域名/IP、重定向和网络出口，防止访问内网与元数据服务。
- **文件上传**：大小、实际内容、扩展名、存储位置、访问权限和恶意内容分别控制。

客户端持有的签名密钥可以被提取，因此“前端请求加签”不能独立证明可信用户或防住全部攻击。服务端之间的签名适用于另一个信任模型。

## 验证与面试递进

| 基础问题 | 场景追问 | 深入讨论 |
|---|---|---|
| Session/JWT 怎么用？ | 退出、封号如何立即生效？ | 状态、撤销、刷新、密钥轮换 |
| 认证与授权区别？ | 用户修改资源 ID 怎么拦？ | 数据权限、租户边界与批量接口 |
| 401 与 403 区别？ | 多请求同时过期如何恢复？ | 单次刷新、失败退出、重试幂等 |
| XSS 与 CSRF 区别？ | HttpOnly 能防住所有 XSS 吗？ | 脚本读凭证与代用户操作是不同能力 |
| 请求签名有什么用？ | App 内密钥泄漏怎么办？ | 信任边界、密钥管理、重放与审计 |

交付前测试匿名访问、他人资源、权限变更、过期会话和恶意输入；再读 [防刷与防重放](/doc/Fullstack/接口防刷与全栈安全攻防实战)。
