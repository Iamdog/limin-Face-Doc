# 全栈 MVP 最新实现与使用场景

MVP 的目标是用最少的组件验证核心业务，而不是一次搭建完整的微服务平台。项目应先具备可运行的页面、接口和数据库，再根据真实问题增加缓存、消息、搜索和服务拆分。

## 一、版本与技术基线

官方资料会持续更新，项目必须在代码仓库中锁定具体版本，并记录升级日期。本文采用以下学习基线：

| 层次 | 推荐基线 | 适用说明 |
| --- | --- | --- |
| 前端 | Vue 3 + Composition API + 单文件组件 + TypeScript | 适合中后台、管理端和小型业务应用 |
| 后端 | Java 17 或 21 + Spring Boot 3.5.x 或 4.x | 新项目优先使用官方当前稳定线；企业存量项目以现有依赖兼容性为准 |
| 持久化 | MySQL 8.4 + MyBatis 或 MyBatis-Plus | 适合事务型业务、订单、任务、用户和权限数据 |
| 缓存 | Redis | 仅用于有明确热点或短期状态的数据 |
| 异步 | 一种消息队列 | 用于通知、日志、耗时任务和系统解耦 |
| 本地环境 | Docker Compose | 固化 MySQL、Redis 和本地依赖版本 |
| 生产环境 | 云数据库、生产服务器或容器平台 | 应包含备份、监控、日志和回滚能力 |

官方参考：

- [Spring Boot 官方项目页](https://spring.io/projects/spring-boot)
- [Vue 官方入门指南](https://vuejs.org/guide/introduction.html)
- [MySQL 8.4 官方参考手册](https://dev.mysql.com/doc/refman/8.4/en/)

版本选择的原则是“锁定稳定版本，定期升级”，而不是在每次开发时自动使用最新版本。升级前应检查 Java、Spring、数据库驱动、ORM、鉴权库和部署镜像的兼容性。

## 二、MVP 的最小架构

```text
Vue 3 + TypeScript
        ↓ HTTPS / JSON
Spring Boot 单体应用
  ├─ Controller：HTTP 协议
  ├─ Service：业务规则和事务
  ├─ Mapper：SQL 访问
  ├─ Redis：热点缓存和短期状态
  └─ MQ：异步任务和通知
        ↓
MySQL 8.4：业务事实数据
```

MVP 阶段优先使用单体应用，并通过包结构划分业务模块：

```text
com.example.app
├── auth
├── user
├── task
├── notification
└── common
```

每个模块内部保持 `controller / service / mapper / domain / dto` 的层次。这样既能快速交付，也为后续拆分服务保留边界。

## 三、按业务场景选择组件

### 场景 1：用户、任务、订单等核心数据

使用 MySQL 作为唯一事实来源：

1. 表结构先满足约束、查询和审计需求。
2. 通过唯一键、状态字段和事务保证数据正确性。
3. Java 事务只覆盖本地数据库操作。
4. 所有结构变更使用版本化迁移文件。

不应把 Redis 当作主数据存储，也不应把前端状态当作最终事实来源。

### 场景 2：热点详情和重复查询

满足以下条件时引入 Redis：

- 同一个查询在短时间内被大量重复访问。
- 数据允许短时间内存在旧值。
- 数据库查询已经通过索引优化，仍然无法满足延迟目标。

推荐缓存模式：

```text
读取：Cache Aside
请求 → 查 Redis → 未命中 → 查 MySQL → 写入 Redis → 返回

更新：先写 MySQL，再删除缓存
```

缓存必须设置过期时间，并考虑空值缓存、热点 Key、穿透、击穿和雪崩。订单金额、账户余额和库存结果不能只依赖缓存。

### 场景 3：通知、日志、报表和耗时任务

以下任务适合异步化：

- 注册后发送邮件或站内通知。
- 订单完成后生成报表或推送消息。
- 图片、视频和大文件的转码处理。
- 操作日志写入和数据同步。

消息处理至少需要：业务消息 ID、消费幂等、失败重试、死信处理和人工补偿入口。发送成功不代表业务一定完成，消费成功也不代表下游一定可用。

### 场景 4：定时任务

单体应用内的定时任务适合：

- 清理过期缓存和临时文件。
- 扫描超时任务。
- 生成低频报表。

多实例部署时，必须处理重复执行问题。可使用数据库抢占、分布式锁或专用调度平台，并为任务设计幂等键。

### 场景 5：微服务拆分

出现以下信号时再考虑拆分：

- 模块需要独立扩容，且流量特征明显不同。
- 发布周期和故障影响范围必须隔离。
- 团队已经具备服务发现、配置管理、链路追踪和故障恢复能力。
- 单体应用的模块边界已经通过代码和数据库约束验证。

没有上述需求时，单体应用更容易调试、部署和维护。微服务会增加网络调用、数据一致性、配置、监控和发布复杂度。

## 四、四个 MVP 版本

### MVP-0：页面与静态数据

交付内容：

- Vue 页面、路由、表单和列表。
- 本地 Mock 数据。
- 错误状态、空数据状态和加载状态。

验收标准：刷新页面、缩放窗口和重复提交不会破坏页面状态。

### MVP-1：单体 CRUD

交付内容：

- Spring Boot 接口。
- MySQL 表结构和迁移脚本。
- 参数校验、统一响应和异常处理。
- 分页、筛选、排序和操作日志。

验收标准：正常、错误、越权、重复和并发更新请求均有明确结果。

### MVP-2：登录与权限

交付内容：

- 登录、退出、Token 续期或会话管理。
- 用户、角色、资源权限。
- 后端接口鉴权和前端路由守卫。
- 密码哈希、敏感信息脱敏和登录失败限制。

验收标准：未登录、越权、Token 过期和重复登录均能正确处理。

### MVP-3：异步与部署

交付内容：

- Redis 热点缓存或短期状态。
- 消息队列处理通知和耗时任务。
- Docker 镜像、环境变量、健康检查。
- 日志、监控、备份和回滚脚本。

验收标准：依赖不可用时应用有明确降级或失败提示，发布后能够定位错误并恢复版本。

## 五、最小接口规范

以任务创建接口为例：

```http
POST /api/tasks
Content-Type: application/json
Authorization: Bearer <token>

{
  "title": "完成接口测试"
}
```

统一响应：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "id": 1001,
    "title": "完成接口测试",
    "status": "TODO"
  },
  "requestId": "req-20261111-0001"
}
```

接口设计要求：

- 请求体只包含客户端允许修改的字段。
- 用户身份从后端鉴权上下文获取，不信任前端传入的 `userId`。
- 修改接口返回受影响结果或明确的业务错误码。
- 分页接口统一返回 `items`、`page`、`pageSize`、`total`。
- 错误响应不包含堆栈、SQL、密钥和内部文件路径。

## 六、MVP 的目录和环境配置

```text
project/
├── web/                  Vue 前端
├── server/               Spring Boot 后端
├── db/migration/         数据库迁移脚本
├── deploy/               Docker、Nginx、启动脚本
├── docs/                 接口、数据字典、发布记录
└── docker-compose.yml    本地依赖
```

环境变量至少包含：

```text
SPRING_PROFILES_ACTIVE=dev
TASK_DB_URL=jdbc:mysql://mysql:3306/task
TASK_DB_USERNAME=task
TASK_DB_PASSWORD=change-me
REDIS_HOST=redis
JWT_SECRET=change-me
```

密码和密钥不得提交到版本库。开发、测试和生产环境使用不同的数据库、缓存和凭据。

## 七、从 MVP 升级到生产版本

| 发现的问题 | 升级动作 | 升级前提 |
| --- | --- | --- |
| 查询重复且延迟高 | 增加 Redis 缓存 | 已有索引、缓存失效和一致性策略 |
| 请求中包含耗时任务 | 增加消息队列 | 已设计消息 ID、重试和补偿 |
| 数据库写入压力大 | 分库、读写分离或批处理 | 已有容量数据和备份恢复演练 |
| 单体发布影响全部功能 | 拆分独立模块或服务 | 边界、数据归属和监控已经明确 |
| 前端首屏较慢 | 分包、懒加载和 CDN | 已通过指标定位资源或接口瓶颈 |
| 线上故障难以定位 | 增加日志、指标和链路追踪 | 日志包含请求 ID 和业务主键 |

每次升级都应记录：问题证据、变更方案、兼容策略、回滚方法和验证结果。没有证据支撑的组件增加，会提高系统复杂度而不能保证性能提升。

## 八、MVP 发布清单

- [ ] 前端、后端、数据库和部署脚本均可从干净环境启动。
- [ ] API 文档包含请求示例、响应示例、错误码和权限要求。
- [ ] 数据库变更已经在测试环境执行并验证回滚。
- [ ] 所有写操作具备参数校验、权限校验和幂等策略。
- [ ] 慢查询、异常、超时和下游失败都有日志和请求 ID。
- [ ] 生产密钥通过环境变量或密钥管理系统注入。
- [ ] 健康检查、备份、回滚和紧急联系人已经验证。
- [ ] Redis、消息队列和微服务均有明确使用场景，不存在无目的引入。

MVP 完成的标志是业务链路可以稳定运行、问题可以被定位、数据可以被恢复。功能数量不应作为唯一的完成标准。
