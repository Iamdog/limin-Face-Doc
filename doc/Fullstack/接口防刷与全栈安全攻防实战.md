# 接口防刷与全栈安全攻防实战

## 🎯 招聘面试核心考点
- **面试官设问**：“开放给 App 或 Web 前端的接口，如何防止黑产抓包后恶意篡改参数并反复调用？如何设计**防重放攻击（Anti-Replay Attack）**？”
- **深水区追问**：“‘**时间戳（Timestamp）+ 随机数（Nonce）+ 接口签名（Sign）**’的设计精髓是什么？XSS 与 CSRF 的底层区别与防御落地是什么？面对突发流量，如何结合 **Redis 令牌桶** 或 **Sentinel** 进行多级熔断限流？”

---

## 🏢 真实生产业务场景
- **短信验证码与营销优惠券发放**：防止羊毛党利用自动化脚本刷爆短信费用或掏空促销券。
- **虚拟资产转账与订单支付**：防止请求在公网被黑客抓包后篡改支付金额或收款账户。
- **敏感信息提交与富文本展示**：防止恶意注入 `<script>` 脚本窃取用户 Cookie（XSS 攻击）。

## 一、 防重放攻击与签名验证（Sign + Nonce + Timestamp）

### 1. 核心流程与防范机制
```text
客户端                                                服务端 (API 网关/拦截器)
  │                                                        │
  ├─── 1. 参数字典序排序 + SecretKey 密钥计算 HMAC ────────┤
  │    (携带: params, timestamp, nonce, sign)             │
  │    ───────────────────────────────────────────────────>│
  │                                                        ├── 2. 校验时间戳: |now - timestamp| > 5m? (拒绝历史超时请求)
  │                                                        ├── 3. 校验 Nonce: Redis setnx 检查防重? (已存在则判定为重放攻击)
  │                                                        └── 4. 服务端用相同密钥重新计算 sign，核对是否一致 (防篡改)
```

1. **防超时失效（Timestamp）**：校验请求时间与服务器当前时间差是否在合理窗口（如 5 分钟）内，超过直接丢弃。
2. **防重复重放（Nonce + Redis）**：每次请求生成全局唯一随机数 `nonce`。服务端将该 `nonce` 存入 Redis 并设置 5 分钟 TTL（`setnx nonce:123 1 EX 300`）。若已存在，说明是**黑客抓包后重放的重复请求**，直接拦截！
3. **防参数篡改（Sign）**：将所有请求参数按字母字典升序排序，拼上双方约定的非对称/对称私钥 `SecretKey`，计算 SHA-256 或 MD5 生成摘要。黑客即使中途篡改了金额或 ID，由于不知道服务端的 `SecretKey`，签名必然无法匹配。

### 2. 最小可运行 MVP 代码实战

#### ① 客户端/前端：参数排序与签名生成（TS/JS）
```javascript
// client_signer.js
const crypto = require('crypto');

function generateSign(params, secretKey) {
  const timestamp = Date.now();
  const nonce = crypto.randomBytes(8).toString('hex');

  // 1. 合并基础参数
  const fullParams = { ...params, timestamp, nonce };

  // 2. 字典序排列所有参数 Key
  const sortedKeys = Object.keys(fullParams).sort();
  const queryString = sortedKeys.map(k => `${k}=${fullParams[k]}`).join('&');

  // 3. 拼装 SecretKey 并执行 HMAC-SHA256 签名
  const sign = crypto.createHmac('sha256', secretKey)
                     .update(queryString)
                     .digest('hex');

  return { ...fullParams, sign };
}

// 模拟调用：转账请求
const payload = generateSign({ toUser: '1002', amount: 500 }, 'MY_SECRET_SALT_888');
console.log('生成的加密请求包:', payload);
```

#### ② 服务端：Spring Boot 拦截器统一校验验签
```java
@Component
public class SignAuthInterceptor implements HandlerInterceptor {

    @Autowired
    private StringRedisTemplate redisTemplate;
    private final String SERVER_SECRET = "MY_SECRET_SALT_888";

    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) throws Exception {
        String timestampStr = request.getHeader("X-Timestamp");
        String nonce = request.getHeader("X-Nonce");
        String clientSign = request.getHeader("X-Sign");

        if (timestampStr == null || nonce == null || clientSign == null) {
            throw new SecurityException("缺少安全验签请求头！");
        }

        // 1. 校验时间戳 (限制 5 分钟之内)
        long clientTime = Long.parseLong(timestampStr);
        if (Math.abs(System.currentTimeMillis() - clientTime) > 5 * 60 * 1000) {
            throw new SecurityException("请求已过期失效！");
        }

        // 2. 校验 Nonce (基于 Redis 原子 setnx 防重放)
        String nonceKey = "nonce:" + nonce;
        Boolean isFirstRequest = redisTemplate.opsForValue().setIfAbsent(nonceKey, "1", Duration.ofMinutes(5));
        if (Boolean.FALSE.equals(isFirstRequest)) {
            throw new SecurityException("检测到非法重放攻击！");
        }

        // 3. 服务端按规则重构排序签名并比对
        // (获取 request 所有参数执行相同 HMAC-SHA256 计算)
        String calculatedSign = mockCalculateHmac(request, clientTime, nonce, SERVER_SECRET);
        if (!clientSign.equalsIgnoreCase(calculatedSign)) {
            throw new SecurityException("参数签名比对失败，请求已被恶意篡改！");
        }

        return true; // 验签通过，放行到下游 Controller
    }

    private String mockCalculateHmac(HttpServletRequest req, long time, String nonce, String salt) {
        return req.getHeader("X-Sign"); // 模拟匹配
    }
}
```

## 二、 XSS 与 CSRF 攻防全解

| 攻击类型 | 攻击原理与传播方式 | 典型受害场景 | 生产级终极防御方案 |
| :--- | :--- | :--- | :--- |
| **XSS (跨站脚本)** | 攻击者在用户输入框注入恶意 HTML/JS 脚本，受害者浏览时脚本在受害者浏览器**直接执行，窃取本地 Cookie / Token** | 博客评论区、论坛帖子、聊天室输入 `<script>stealCookie()</script>` | 1. 敏感 Token 必须设置 **`HttpOnly` Cookie**，JS 脚本无法通过 `document.cookie` 读取<br>2. 富文本使用 **DOMPurify** 库进行严格标签白名单过滤<br>3. 开启浏览器的 CSP (Content-Security-Policy) |
| **CSRF (跨站请求伪造)** | 诱导用户打开钓鱼网站，利用用户在目标站已登录的 **Cookie 自动附带特性**，冒用用户身份向目标服务发送转账或修改密码请求 | 钓鱼页面中隐藏 `<img src="https://bank.com/transfer?to=hacker&amount=1000">` | 1. **彻底放弃以 Cookie 存鉴权凭证**，全栈改用 Header 携带 **Bearer JWT Token**（第三方网站发起的请求无法自动注入 Header）<br>2. Cookie 设置 **`SameSite=Strict`** 属性阻止第三方携带 |
