# 接口防刷与全栈安全攻防实战

## 一、解决什么问题

防刷限制自动化滥用，防重放阻止合法请求被重复利用，幂等防止重试产生重复业务结果。三者不能互相替代。先完成 [认证与资源权限](/doc/Fullstack/登录认证权限与接口安全基础)，再给短信、优惠券、支付等高风险接口增加相应措施。

## 二、基本使用：先建立业务防线

短信接口按账号、手机号、设备/IP 和时间窗口限制，并结合验证码或风险识别；优惠券用唯一约束和资格验证；支付金额由服务端订单计算，不相信前端自填。返回 429 或明确业务失败，记录风险指标和误伤反馈。

前端按钮禁用和防抖改善体验，不能替代服务端控制。共享 IP 和代理环境下只按 IP 限制会误伤用户，需结合身份和场景。

## 三、常见场景：可信调用方的 HMAC 防重放

HMAC 适合服务端间共享密钥的调用；浏览器/App 内嵌密钥可被提取，不能当作可靠身份或防攻击边界。TLS、身份、资源权限和业务幂等仍然必要。

### 1. 基本签名示例

下面是可独立运行的 **Node.js 服务调用方签名示例**，不是浏览器代码。这里只生成签名；接收端必须按同一格式实现验证。

```js
const crypto = require('node:crypto')
function signRequest({ method, path, body, timestamp, nonce }, secret) {
  const bodyHash = crypto.createHash('sha256').update(body).digest('hex')
  const canonical = [method.toUpperCase(), path, timestamp, nonce, bodyHash].join('\n')
  return crypto.createHmac('sha256', secret).update(canonical).digest('hex')
}
const secret = process.env.API_SIGNING_SECRET
if (!secret) throw new Error('请配置 API_SIGNING_SECRET')
const request = {
  method: 'POST', path: '/api/transfer', body: JSON.stringify({ orderId: 'o1' }),
  timestamp: String(Date.now()), nonce: crypto.randomBytes(16).toString('hex')
}
console.log({ timestamp: request.timestamp, nonce: request.nonce,
  sign: signRequest(request, secret) })
```

格式必须约定路径与 query、编码、原始 body 字节、时间单位和字段边界；若接口含 query，应把规范化后的 query 纳入签名。简单地把任意参数拼成 `a=b&c=d` 会存在歧义。HMAC 是带密钥认证码，不是“拼盐再做 MD5”，也不是加密正文。

### 2. 接收端验证顺序

```text
校验格式与长度
→ 根据 keyId 查受控密钥
→ 校验时间窗口
→ 以相同规范重建待签名数据
→ 解码并用常量时间比较验证 HMAC
→ 原子写入 keyId + nonce 防重记录并设置有效 TTL
→ 校验身份/权限与业务幂等
→ 执行业务
```

先验签再占用 nonce，避免未认证请求抢占合法 nonce。Redis 原子操作是 `SET key value NX EX seconds`，不是把 SETNX 与过期分成两步。nonce 保留时间需覆盖完整可接受窗口；允许未来时间时，从接收时算固定短 TTL 可能留下重放窗口。依赖不可用时按风险明确拒绝或降级，不能悄悄放行。

防重放会拒绝同一个请求 nonce；业务幂等键需要稳定，让用户在网络失败后仍可查询或安全重试。签名失败、重复 nonce 和业务重复是不同结果。

## 四、进阶：多级限流、重试与熔断

网关做入口保护，业务按账号/资源限制，依赖调用设置连接池、并发上限和 deadline。Redis 原子脚本可协调多实例限流；Sentinel 等组件可管理限流和熔断，但阈值仍需依据容量实测。

重试设置上限、退避、抖动与总预算，只对适合的错误和幂等操作执行。短信和资金操作宁可返回明确失败或未知状态，也不能在无法确认时伪造成功。记录正常用户被拒绝率，防刷效果不能只看拦截数。

## 五、XSS、CSRF 与使用边界

| 风险 | 基本防护 | 需要避免的误解 |
|---|---|---|
| XSS | 转义、可信 HTML 消毒、CSP、依赖治理 | HttpOnly 只阻止读取 Cookie，不能阻止脚本代用户操作 |
| CSRF | SameSite、CSRF Token、Origin 等校验 | Cookie 可以安全使用；JWT 本身不是 CSRF 防护 |
| SQL 注入 | 参数绑定、动态字段白名单 | `#{}` 不能绑定任意表名/排序列 |
| 越权 | 服务端资源/租户权限 | 前端隐藏按钮、请求签名都不能替代授权 |

## 六、面试递进与验证

| 基础题 | 场景追问 | 深入回答 |
|---|---|---|
| 防抖和限流区别？ | 脚本绕过页面怎么办？ | 服务端多维限额、风险控制和误伤 |
| 幂等与防重放区别？ | 超时重试需要新 nonce 吗？ | 请求身份与业务身份分别设计 |
| HMAC 如何签名？ | body 和编码不一致怎么办？ | 规范化、原始字节、时间与比较方式 |
| 前端内嵌密钥安全吗？ | 提取密钥后怎么处理？ | 信任边界、服务端认证、轮换和风控 |
| 限流依赖宕机怎么办？ | 全部放行会不会雪崩？ | 业务风险、缓存策略和本地保护 |

至少测试篡改 body、篡改路径、过期请求、重复 nonce、相同幂等键并发、依赖不可用和普通用户误伤。实现中的“模拟验证直接返回客户端签名”不具备任何验签能力，不能用于真实接口。
