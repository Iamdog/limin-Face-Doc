# Vue 3 快速 Diff 最长递增子序列 LIS 算法贪心二分数学推导

Vue 3 在虚拟节点的子节点列表比对上，全面废弃了 Vue 2 沿用多年的双端 Diff，自研引入了业界顶尖的 **快速 Diff 算法（Fast Diff Algorithm）**。该算法的核心数学思想借鉴了 `inferno` 框架：通过 **前后置预处理（Pre-pass & Post-pass）** 极速消除首尾公共节点，并结合 **最长递增子序列（Longest Increasing Subsequence, 简称 LIS）** 算法，求解出在乱序重排中**能够完全保持物理不动（Zero DOM Moves）的最大子集**。本专题从算法数学逻辑、二分贪心实现到源码逐行深入推导。

## 源码级/数学物理底层推导

### 1. 前置与后置预处理源码

```typescript
let i = 0
const l2 = c2.length
let e1 = c1.length - 1 // 旧列表末尾指针
let e2 = l2 - 1        // 新列表末尾指针

// 1. 前置预处理：从头部开始比对
while (i <= e1 && i <= e2) {
  const n1 = c1[i]
  const n2 = c2[i]
  if (isSameVNodeType(n1, n2)) {
    patch(n1, n2, container, null)
    i++
  } else {
    break
  }
}

// 2. 后置预处理：从尾部开始比对
while (i <= e1 && i <= e2) {
  const n1 = c1[e1]
  const n2 = c2[e2]
  if (isSameVNodeType(n1, n2)) {
    patch(n1, n2, container, null)
    e1--
    e2--
  } else {
    break
  }
}
```

### 2. 未知子序列中 `source` 数组的物理意义

在消除了首尾相同的节点后，假设中间剩下的未处理乱序序列为：
- 旧子节点：`[ C, D, E, B ]`（对应旧索引：`2, 3, 4, 5`）
- 新子节点：`[ D, B, C, E ]`（对应新索引：`0, 1, 2, 3`）

Vue 3 会构建一个定长数组 `newIndexToOldIndexMap`（简称 `source` 数组），长度等于新子序列长度，初始全为 `0`：
`source = [ 0, 0, 0, 0 ]`。
通过遍历旧节点，记录**新节点在旧列表中的原始物理索引 + 1**（加 1 是为了与初始值 0 区分，0 代表全新节点）：
`source = [ 4, 6, 3, 5 ]`（代表：新列表第 0 项 D 来自旧索引 3；新第 1 项 B 来自旧索引 5...）。

---

### 3. 最长递增子序列（LIS）的数学物理推导

#### 为什么要找最长递增子序列？
- 在 `source = [ 4, 6, 3, 5 ]` 中：
  - 数字代表旧列表的相对物理顺序；
  - 找出一个“严格递增”的子序列，比如 `[ 4, 5 ]`（对应节点 D 和 E）；
  - **递增的物理本质意味着：节点 D 和节点 E 在旧列表中的前后相对顺序，与它们在新列表中的前后相对顺序是完全一致的！**
  - **数学推论**：**这几个处于最长递增子序列中的节点，真实 DOM 根本不需要做任何物理移动！** 我们只需要移动那些不在子序列中的少数节点（如 B 和 C），从而将原生 DOM `insertBefore` 的移动次数降到数学理论极限！

#### $O(N \log N)$ 贪心 + 二分查找 + 前驱回溯完整算法源码

```typescript
// @vue/runtime-core/src/renderer.ts
function getSequence(arr: number[]): number[] {
  const p = arr.slice() // 用于记录前驱节点索引，支持最终回溯
  const result = [0]    // 存储最长递增子序列对应的索引
  let i, j, u, v, c
  const len = arr.length

  for (i = 0; i < len; i++) {
    const arrI = arr[i]
    if (arrI !== 0) {
      j = result[result.length - 1]
      // 贪心策略 1：如果当前值大于子序列末尾值，直接追加到末尾
      if (arr[j] < arrI) {
        p[i] = j // 记录前驱索引
        result.push(i)
        continue
      }

      // 贪心策略 2：当前值较小，通过二分查找找到 result 中第一个大于等于 arrI 的位置并替换它
      u = 0
      v = result.length - 1
      while (u < v) {
        c = (u + v) >> 1
        if (arr[result[c]] < arrI) {
          u = c + 1
        } else {
          v = c
        }
      }

      if (arrI < arr[result[u]]) {
        if (u > 0) {
          p[i] = result[u - 1] // 记录前驱
        }
        result[u] = i // 二分替换
      }
    }
  }

  // 核心回溯修正：从后向前沿 p 数组还原出真正物理正确的递增序列
  u = result.length
  v = result[u - 1]
  while (u-- > 0) {
    result[u] = v
    v = p[v]
  }
  return result
}
```

## 社招高频硬核连环追问

### 追问 1：相比 Vue 2 的双端 Diff，Vue 3 的快速 Diff 在性能上究竟发生了什么维度的质变？

#### 深度剖析
1. **真实移动次数大幅削减**：
   - Vue 2 的双端比对一旦遇到“把末尾节点移动到前面”、“复杂的局部乱序”，4 种猜想失效后只能退化为哈希表盲目插入，导致很多本不需要移动的节点被迫发生了 DOM 移动；
   - Vue 3 通过数学上的最长递增子序列（LIS），求得了**能够保持不动的节点集合的最大基数（Max Cardinality）**。这在数学上被证明是**DOM 移动次数的最少解**；
2. **倒序遍历插节点稳定性**：
   - Vue 3 在最终移动节点时，采用**从后向前倒序遍历（From Right to Left）**；
   - 倒序遍历的物理优势在于：当处理当前节点时，**其后面的锚点节点（Anchor Node）必定已经处理就绪并稳定挂载在 DOM 树上了！** 只需要直接调用 `hostInsert(child, container, anchor)` 即可，逻辑极其收敛简单，杜绝了正序插入时找不到后置锚点的麻烦。

---

### 追问 2：为什么标准二分查找求出的递增子序列结果长度是对的，但里面的元素可能不是真实的子序列？为什么必须加 `p` 前驱数组回溯？

#### 深度剖析
假设输入数组为：`[10, 9, 2, 5, 3, 7, 101, 18]`：
- 贪心二分在扫描到 `3` 时，会把之前 `[2, 5]` 中的 `5` 替换为 `3`，得到 `[2, 3]`；
- 但如果输入是 `[1, 3, 5, 2]`：
  1. 遇到 1，序列为 `[1]`；
  2. 遇到 3，序列为 `[1, 3]`；
  3. 遇到 5，序列为 `[1, 3, 5]`；
  4. 遇到 2，二分查找把 3 替换掉，序列变成了 `[1, 2, 5]`！
  - **严重 Bug 产生**：原数组中 `2` 是在 `5` 的后面出现的，在时间线上根本不存在 `[1, 2, 5]` 这样一个子序列！
- **`p` 数组的物理救赎**：
  二分替换仅仅是为了保证后续能接入更小的可能值以维持**长度（Length）的正确性**。为了获得真实元素的正确索引，Vue 在每次操作时用 `p` 数组记录了每个节点“真正的前驱是谁”；算法在最后一步从末尾反向回溯 `v = p[v]`，精准提取出真正的连续拓扑序列。

## 生产级避坑指南与排障 SOP

### 1. 规避在 `v-for` 中滥用纯文本且不加唯一 key

- **现象**：当列表项包含大量未配置 key 的同质元素时，Vue 3 会将其标记为 `UNKEYED_FRAGMENT`。
- **物理回退**：
  由于没有 key，快速 Diff 算法的全部优化将被**彻底抛弃**！Vue 会回退到最朴素的按数组下标就地 patch 逻辑，中间一旦插入一项，后面所有节点的内容全被强制覆写，大幅拖慢渲染性能。

---

### 2. 避免动态列表生成超大稀疏数组导致内存剧增

- **排查 SOP**：
  在未知子序列处理中，`newIndexToOldIndexMap` 的大小是根据新节点未处理数量分配的。如果在前端无意中构造了长度上万的稀疏未知序列（如分页逻辑写错导致一次性渲染 20000 条乱序数据），快速 Diff 内部的数组分配与 LIS 递归回溯会瞬间占用数十兆内存。**列表数据超过 500 条时，必须采用“虚拟列表（Virtual List）”分片渲染。**
