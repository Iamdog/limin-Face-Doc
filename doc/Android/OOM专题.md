# Android OOM专题

## 使用入口：先解决问题，再做验证

定位分配失败并减少大对象、缓存与泄漏造成的风险。

**先做基本操作**：先按业务动作观察 Java/Native 内存曲线，在测试环境采样堆与引用链，验证修复后峰值和基线。初次学习可先完成[本模块基础实践](/doc/Android/Android应用基本开发与验证)。

**再逐步深入**：基本 API 与输入输出 → 常见失败和使用边界 → 场景排查与优化 → 本文机制分析与源码。面试先讲用途和自己的操作过程，再回答场景与原理追问。

OOM 是 Android 稳定性核心问题。技术总结的核心不是背定义，而是“为什么发生、如何定位、如何治理”。

## 1. 什么是 OOM？

- Java OutOfMemoryError 表示某类分配或资源请求失败，不只是进程总内存不够；可能涉及 Java 堆、线程等资源。Native 分配失败和系统低内存杀进程需分别定界。
- 常见于大图、缓存失控、对象泄漏、Native 内存增长。

## 2. 高频触发场景

- 一次性加载大图或多图。
- 列表图片缓存策略失控。
- 页面频繁创建大对象导致内存峰值抬升。
- Activity/Fragment 泄漏导致旧页面堆积。
- JNI/Bitmap 等 Native 内存未释放。

## 3. 排查路径

1. 先看异常/退出原因与具体分配失败信息，结合 Java 堆、Native、线程、FD 和系统压力区分问题。
2. 用 Memory Profiler 看峰值增长曲线。
3. 用 Heap Dump 查主导对象和引用链。
4. 对照业务场景复现：列表滑动、相册选择、长时间后台等。

## 4. 治理策略

- 图片按需解码，控制尺寸与格式。
- 缓存设置上限，避免无限增长。
- 大对象分批加载，避免峰值集中。
- 生命周期结束及时释放引用。
- 在开发/测试环境引入 LeakCanary 做持续检测；线上堆分析先评估暂停、隐私与版本兼容。

## 5. `largeHeap` 要不要用？

- 可以作为兜底，不应当作根治方案。
- `largeHeap` 会掩盖问题并增加系统整体内存压力。

## 6. 核心高频问题

### Q1: OOM 和内存泄漏有什么关系？
A: 泄漏不一定立刻 OOM，但会持续抬高基线，最终显著提高 OOM 概率。

### Q2: 为什么图片最容易引发 OOM？
A: 因为图片内存占用按像素展开，常远大于文件体积。

### Q3: Java 堆没满也会 OOM 吗？
A: 会，尤其是 Native 内存、线程栈或大对象连续分配失败时。

### Q4: 如何证明是缓存导致 OOM？
A: 看堆快照中的缓存容器对象数量和 retained size 是否长期上升且不回落。

### Q5: OOM 治理的第一优先级是什么？
A: 先定位主导来源，再做限流和上限控制，避免“盲目清理一切缓存”。

## 7. 小结

OOM 治理要以“峰值控制 + 泄漏治理 + 场景复现”三板斧推进，先稳住崩溃率，再逐步优化体验和性能。
