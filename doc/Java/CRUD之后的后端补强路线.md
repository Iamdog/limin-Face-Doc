# CRUD 之后的 Java 后端补强路线

## 先确定你要解决的问题

你已经能写简单 CRUD，下一阶段要能回答：**写到一半失败了怎么办、谁有权修改这条数据、同时更新怎么避免覆盖、失败请求怎么定位**。学习重点放在这些真实接口行为上，完成后再进入代理、隔离级别、线程和分布式原理。

这一轮用同一个任务管理项目贯穿：创建任务时同时写操作记录；只有归属用户能访问任务；只有编辑角色能修改；版本冲突返回明确结果；每次请求都有可追踪 ID。可运行代码和启动方法见 [后端练习项目说明](/examples/java-backend-workshop/README)，讲解见 [事务、权限与排错实战](/doc/Java/事务权限与排错实战)。

## 一、先把已有 CRUD 的完成标准补齐

| 能力 | 原来能完成 | 现在要补齐 |
|---|---|---|
| 新增 | 数据能插入 | 校验输入、归属来自认证、多个写入一起提交 |
| 查询 | 能按 ID 查数据 | 资源归属、列表范围、分页上限、找不到的结果 |
| 更新 | 能执行 UPDATE | 版本条件、影响行数、冲突提示与审计 |
| 失败 | 会打印异常 | 正确 HTTP 状态、统一错误码、requestId、数据库最终状态 |
| 测试 | 手工成功一次 | 越权、重复/冲突、回滚与异常分支可重复验证 |

先给自己的一组接口补上这张表，也可以直接修改练习项目。测试不是检查“Controller 有没有调用 Service”，而是验证实际响应与数据结果。

## 二、第一关：事务，保证一组修改的结果

**解决的问题**：任务写入成功，但操作记录写入失败，不能留下半成功数据。

**先使用**：在 Spring 管理的 Service 公开业务方法上使用 `@Transactional`，经 Controller 或其他 Bean 调用；Mapper 使用同一数据源与事务管理器。先做两个写入成功，再让第二个写入之后抛出运行时异常，查看两张表都没有残留。

**过关证据**：能运行 `failureAfterBothInsertsRollsBackBothTables` 和 `failedUpdateRollsBackTitleVersionAndAudit`，解释任务、版本和记录最终是什么状态。测试方法没有外围 `@Transactional`，避免测试自己的回滚掩盖业务事务是否生效。

**再深入**：默认回滚规则、catch、代理自调用、REQUIRED/REQUIRES_NEW、不同线程与资源边界。随后读 [事务专题](/doc/Java/Spring/Spring核心与事务失效实战) 和 [数据库双会话实验](/doc/MySQL/MySQL事务隔离与MVCC原理)。

## 三、第二关：权限，保证调用者只能操作自己的数据

**解决的问题**：用户 B 把 URL 中的任务 ID 改成用户 A 的，就读到或修改了 A 的任务。

**先使用**：通过认证组件取得身份；角色判断能否调用写接口；SQL 中再次限定 `id + owner`。请求 DTO 只允许 title/version，不能接受客户端自填归属。

**过关证据**：匿名访问返回 401；只读用户写入返回 403；B 读或改 A 的任务返回本项目规定的 404，数据库不改变；列表只返回本人的数据。404 是本项目避免暴露资源存在性的选择，其他项目可按一致的 API 约定处理。

**再深入**：Session/JWT、退出与撤销、CSRF、RBAC、组织/租户范围。先把这套权限闭环写正确，再设计 Token 刷新；参考 [认证和授权基础](/doc/Fullstack/登录认证权限与接口安全基础)。

## 四、第三关：并发更新，避免两次编辑互相覆盖

**解决的问题**：两个页面都读到 version=0，后提交的修改覆盖了前一个已成功的修改。

**先使用**：UPDATE 的 WHERE 中带 `id + owner + version`，成功时 `version + 1`；必须检查影响行数。不匹配时返回 409，客户端刷新并让用户确认如何合并，不静默覆盖。

**过关证据**：运行 `staleVersionReturns409AndDoesNotOverwriteData` 和双线程更新测试，同一个旧版本只有一次更新成功；失败请求不产生多余操作记录。

**再深入**：数据库条件更新与记录锁、乐观锁/悲观锁、重试与业务幂等。普通编辑先把数据库约束做好，再判断是否需要分布式锁。

## 五、第四关：排错，建立一条失败请求的证据链

**解决的问题**：前端只说“提交失败”，不知道请求被权限拦截、参数不合法、数据库冲突还是应用异常。

**先使用**：读 URL/方法/JSON → HTTP 状态与错误码 → 响应 X-Request-Id → 相同 ID 的服务日志 → Service 分支和 SQL → 最终数据。练习项目在安全过滤链之前生成 requestId，因此 401/403 也能关联。

**过关证据**：分别复现 400、401、403、404、409 和测试中的 500，说明每种失败发生在哪层。区分“请求没发出”“服务未收到”“业务没成功”“响应丢失”，不能仅凭前端错误提示推测是否回滚。

**再深入**：连接池、慢 SQL、锁等待、超时、线程与指标；只有证据指向运行时资源后，才进入 [JVM 排查](/doc/Java/JVM底层原理与调优实战)。

## 六、第五关：把验证带到交付流程

先会 `./mvnw test`、`./mvnw package`、`java -jar`，读懂构建错误、启动错误和请求错误的区别。固定依赖版本，配置与密钥分离，使用测试数据。练习的 H2 便于快速验证 Spring 事务和权限，MySQL 隔离、锁、SQL 方言与恢复仍需真实 MySQL 实验。

当上述关卡都能独立完成，再按业务需要继续 Redis → MQ → 线程池/JVM → 微服务与分布式一致性。每引入一个组件先回答用途、API、失败、验证，然后分析原理。

## 七、面试回答顺序

| 主题 | 先说使用与业务 | 再说失败与验证 | 最后说原理 |
|---|---|---|---|
| 事务 | 哪些 SQL 必须一起提交 | 注入异常后查两张表 | 代理、连接绑定与回滚规则 |
| 权限 | 如何认证并限制数据归属 | 其他账号不能读取和修改 | 过滤链、授权层次与会话策略 |
| 并发 | WHERE version 防覆盖 | 两请求只有一个成功 | 条件更新、锁与隔离 |
| 排错 | 从状态码和 requestId 定位 | 实际请求/日志/数据证据 | 请求链路、线程/连接与资源 |

能讲清一次“失败后数据为什么仍然正确”，是这一阶段最值得积累的后端经验。
