# Java 后端事务、权限与排错实战

## 一、解决什么问题

以“任务新增与修改”为例：任务和操作记录必须一起成功；用户只能访问自己的任务；同时编辑不能静默覆盖；失败需要明确状态和可追踪日志。这些是 CRUD 进入可靠业务接口的基础。

项目位于仓库的 `examples/java-backend-workshop`，使用 JDK 17+、Spring Boot 3.5.13、MyBatis 3.0.5、Spring Security 和 H2。完整文件、命令与接口在 [项目说明](/examples/java-backend-workshop/README)。默认仅监听本机回环地址，演示账号用于学习，不是生产账号设计。

## 二、先跑起来，观察成功请求

进入项目目录：

```bash
./mvnw test
./mvnw spring-boot:run
```

使用 `alice / alice-demo` 请求 `GET http://127.0.0.1:8081/api/tasks`，得到当前用户列表。用 `GET /api/csrf` 获取写入所需 Token，并保留同一会话 Cookie。按项目说明携带该 Header 新增任务，预期 201、id 与 version=0；更新同一任务，预期 200、version=1。

服务启动后按请求链路读代码：

```text
RequestLogFilter：生成 requestId
  ↓
Spring Security：身份、角色、CSRF
  ↓
TaskController：解析和校验 DTO，提取认证身份
  ↓
TaskService：归属、版本、业务事务
  ↓
TaskMapper / AuditWriter：绑定参数执行 SQL
  ↓
H2：任务与操作记录
```

身份错误和访问拒绝发生在安全过滤链中，不应指望 ControllerAdvice 自动处理所有安全错误；本项目为过滤链和 Controller 异常分别提供一致错误模型。

## 三、事务基本使用：把两个数据库写入组成业务操作

```java
@Transactional
public Task create(String actor, String title) {
    Task task = new Task();
    task.setOwner(actor);
    task.setTitle(title.trim());
    mapper.insert(task);
    audit.write(task.getId(), actor, "CREATE");
    return find(actor, task.getId());
}
```

这是项目 `TaskService` 的实际业务方法。`actor` 由 Controller 从 Spring Security 的 Principal 提取；title 由请求 DTO 校验。AuditWriter 与 Mapper 使用同一个数据源，没有独立事务传播配置。

**先验证行为**：正常调用产生任务与记录；测试在 audit 已经写入后抛出异常，HTTP 返回 500，并确认两张表都为 0。另一个测试修改任务和 version 后注入失败，确认 title/version/记录一起恢复原状。故障只通过测试中的 spy 注入，业务 API 没有“触发故障”参数。

### 常见失败怎样处理

| 情况 | 基本处理 | 需要区分 |
|---|---|---|
| RuntimeException/Error 离开业务边界 | 默认回滚规则覆盖 | Spring 版本与事务配置可改变规则 |
| 受检异常离开边界 | 按业务需要配置 rollbackFor | 不是所有方法都强制写 Exception.class |
| catch 后正常返回 | 普通情况下可能提交 | 如果资源或内层事务已标 rollback-only，最终还可能回滚/报 UnexpectedRollbackException |
| 同类方法内部调用 | 被调用方法的新事务属性通常不经过代理 | 外层已有事务时仍可能在外层事务里运行 |
| 新线程/异步任务 | 设计独立事务和可靠协调 | 传统线程绑定事务不会自动传到另一个线程 |
| 外部 HTTP/MQ/文件操作 | 分开设计确认、重试和补偿 | 本地数据库回滚不能撤销远端已经完成的副作用 |

### 最后解释原理

在这个 JDBC/MyBatis 项目中，外部调用经过 Spring 代理，事务管理器管理并绑定数据库连接，两个 Mapper 写入参与同一事务。方法完成并经事务拦截处理后提交或回滚，再把结果交给 Controller。

public Service 方法是易于验证的推荐边界。Spring 6 的类代理在默认配置下还支持可被代理的 protected/包可见方法；JDK 接口代理有不同可见性要求。private 方法不能用普通代理拦截，final 的类/方法也有限制，不能把所有情况写成统一“非 public 必定失效”。

## 四、权限基本使用：认证、角色与资源归属各司其职

本项目用本地 HTTP Basic 和内存账号先把行为验证清楚，密码经 BCrypt 编码。Basic 只是这个练习的认证方式；实际部署要选择合适会话/Token 方案与 HTTPS，不把演示账号直接作为上线方案。

| 身份 | 能访问什么 | 写入结果 |
|---|---|---|
| 匿名/密码错误 | 不能访问受保护接口 | 401 |
| viewer，只读角色 | 本人数据的只读接口 | 有效 CSRF 也不能绕过角色限制，403 |
| alice / bob，编辑角色 | 各自数据的读写接口 | 读/改他人任务被资源归属限制 |

```sql
SELECT id, owner, title, version FROM tasks
WHERE id = :id AND owner = :authenticated_owner;
```

`authenticated_owner` 来自服务端认证。参数实际通过 MyBatis `#{}` 绑定。请求对象没有 owner 字段，未知字段被拒绝；即使用户有 EDITOR 角色，SQL 仍不能漏掉 owner 条件。

### 操作与验证

用 alice 新建任务；换 bob 请求相同 ID，读和写都得到本项目规定的 404；alice 的内容和操作记录不改变。列表也按认证身份过滤，不能只给详情接口加权限。

本项目保留 CSRF：写请求未带正确 Token 时返回 403。排查 403 要分角色失败与 CSRF 失败，不直接认为“登录成功应该全部放行”。浏览器可能自动携带 Basic 凭证，不能用“没使用 Cookie 登录”作为一律关闭 CSRF 的理由。

### 最后解释原理

过滤链完成认证和粗粒度接口授权；Service/SQL 做资源层范围限制。角色决定可以做哪类动作，数据范围决定对哪些对象可以做。后续扩展租户、组织、管理员时，两层规则都要保持一致。

## 五、并发基本使用：版本条件与影响行数

```sql
UPDATE tasks SET title = :title, version = version + 1
WHERE id = :id AND owner = :authenticated_owner AND version = :old_version;
```

应用检查影响行数：1 表示本次版本转换成功；0 表示条件不匹配。本项目先按归属确认资源，再在更新冲突时返回 409。响应中的新版本交给客户端保存。

先顺序提交两个 version=0 的请求：第一个成功，第二个 409；再运行双线程测试，验证旧版本只有一个提交成功。它验证真实条件更新和应用分支，但 H2 的实验结果不能作为 MySQL 所有隔离级别、锁等待与死锁行为的证明。

**再深入**：条件更新在数据库中执行；“在 Java 里先比较 version，再不带条件 UPDATE”仍有竞态。事务本身也不能替代对丢失更新的业务约束。

## 六、排错基本使用：从响应进入证据链

统一失败响应示例：

```json
{
  "code": "VERSION_CONFLICT",
  "message": "版本已变化，请刷新后重试",
  "requestId": "服务端生成的本次请求标识"
}
```

响应 Header `X-Request-Id` 与日志 MDC 使用同一个 ID。日志记录方法、路径、状态和耗时，不记录认证 Header、密码或完整请求正文；未知错误记录服务端堆栈，对外返回稳定信息。

| 现象 | 先看什么 | 下一步 |
|---|---|---|
| 400 | JSON、字段类型、必填与版本 | 请求是否到达 Service，是否有写入 |
| 401 | 是否携带正确认证 | 安全链日志与凭证策略 |
| 403 | 角色或 CSRF | Cookie/Token/角色，不绕过校验 |
| 404 | ID 和资源归属 | 按可信身份确认访问范围 |
| 409 | 客户端旧 version | 查询最新数据，确认后重提 |
| 500 | requestId 与完整服务日志 | 首个异常、事务和最终数据 |
| 请求很慢 | 分段耗时、SQL、池与等待 | 区分查询慢、锁等待、连接池排队和外部调用 |

排错流程：请求事实 → 响应 → 同 ID 日志 → 业务分支 → 实际 SQL/数据库结果 → 修复与回归。requestId 是当前请求关联标识，不自动等同跨服务 traceId；异步/跨服务传播还要单独设计。

## 七、测试先验证业务结果

练习测试使用真实 Spring 安全链、Controller、Service、MyBatis 和 H2。权限验证使用 HTTP Basic 认证，事务方法由实际代理调用；只在需要稳定制造故障时对 AuditWriter 用 spy。

- 正常创建后任务与记录都提交，响应不暴露实体 owner。
- 匿名/错误密码、缺 CSRF、只读角色写入分别失败。
- 空输入和注入 owner 被拒绝，数据库无变化。
- 他人不能读写，列表范围与大小受限制。
- 旧版本和双线程更新不会覆盖已提交状态。
- 两个写入完成后抛异常，两张表都回滚；更新失败时版本也回滚。

MockMvc 的 csrf helper 用于测试请求，真实客户端仍需按项目说明拿 Token 并保留会话。测试方法不加外围事务，检查业务提交与回滚后的真实结果。
