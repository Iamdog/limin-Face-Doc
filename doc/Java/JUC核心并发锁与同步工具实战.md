# JUC 核心并发锁与同步工具实战

在并发编程中，仅仅依靠原生的 `synchronized` 已经无法满足各种灵活、复杂的业务调度诉求。JUC（`java.util.concurrent`）提供了一整套基于 AQS 构建的高级并发锁与线程协作同步工具箱。

---

## 1. ReentrantLock：公平锁 vs 非公平锁源码终极差异

`ReentrantLock` 实现了 `Lock` 接口，具备比 `synchronized` 更灵活的特性：支持响应中断、支持超时等待、支持公平锁与非公平锁选择。

### 1.1 核心源码差异点一：`lock()` 入口的粗暴插队
查看 `NonfairSync`（非公平锁）和 `FairSync`（公平锁）的入口源码：

```java
// 1. 非公平锁 (NonfairSync):
final void lock() {
    // 不管队列里有没有人在排队，不管三七二十一，上来先直接发起一次 CAS 抢锁！
    if (compareAndSetState(0, 1))
        setExclusiveOwnerThread(Thread.currentThread());
    else
        acquire(1); // 抢不到才进入 AQS 流程
}

// 2. 公平锁 (FairSync):
final void lock() {
    // 讲文明懂礼貌，直接规规矩矩进入 AQS 排队流程
    acquire(1); 
}
```

---

### 1.2 核心源码差异点二：`tryAcquire()` 中的排队检查
进入 AQS 后的 `tryAcquire(int acquires)` 方法：

```java
// 公平锁 FairSync 源码片段：
protected final boolean tryAcquire(int acquires) {
    final Thread current = Thread.currentThread();
    int c = getState();
    if (c == 0) {
        // 核心差异！必须先调用 hasQueuedPredecessors() 检查！
        // 只要发现队列中自己前面有其他线程在排队，哪怕当前锁处于空闲，也坚决不抢！直接返回 false!
        if (!hasQueuedPredecessors() &&
            compareAndSetState(0, acquires)) {
            setExclusiveOwnerThread(current);
            return true;
        }
    }
    ...
}
```

> **为什么生产默认推荐非公平锁？**  
> 线程从被唤醒（unpark）到真正恢复 CPU 执行，存在微秒级的操作系统上下文切换延迟。非公平锁允许刚来的活跃线程直接插队插走锁，**最大化榨干 CPU 密集流水线，整体吞吐量（Throughput）通常比公平锁高出数倍甚至数十倍**！只有在防止线程长期饥饿（Starvation）有强业务硬性要求的场景下才启用公平锁。

## 2. ReentrantReadWriteLock：读写分离与“锁降级”

在绝大多数互联网系统中，读请求的占比往往高达 **90% 以上**（读多写少）。如果读操作也使用互斥锁，系统性能将被锁竞争严重扼杀。

### 2.1 读写互斥矩阵
- **读 - 读并发共享**：允许多个线程同时持有读锁进行并发读取。
- **读 - 写互斥**：有线程在读时，禁止任何线程获取写锁。
- **写 - 写互斥**：同一时刻只能有一个线程持有写锁。

---

### 2.2 核心深水区：为什么允许“锁降级”，而坚决禁止“锁升级”？

#### 什么是锁降级？（写锁 $\to$ 读锁，允许！）
锁降级指的是：**当前线程持有写锁的状态下，先获取读锁，随后再释放写锁的过程**。
```java
// 生产级标准锁降级代码示范：
writeLock.lock(); // 1. 获取写锁
try {
    updateData(); // 2. 执行数据修改
    readLock.lock(); // 3. 核心！在释放写锁前，先获取读锁 (锁降级关键动作)
} finally {
    writeLock.unlock(); // 4. 释放写锁 (此时当前线程依然持有读锁!)
}

try {
    useDataWithReadLock(); // 5. 安全使用最新数据
} finally {
    readLock.unlock(); // 6. 最终释放读锁
}
```
- **为什么必须这样锁降级？**
  如果第 3 步不提前获取读锁，而是在释放写锁后再重新申请读锁：在这释放与再次加锁的瞬间，其他线程完全可能抢入拿到写锁篡改数据，导致当前线程读到被他人篡改的脏数据。**锁降级完美锁死了数据的连续一致性视图**。

#### 为什么坚决禁止“锁升级”？（读锁 $\to$ 尝试转为写锁，直接死锁！）
- 假设线程 A 和线程 B 同时持有读锁；
- 此时两者都想修改数据，并发调用 `writeLock.lock()` 尝试将读锁升级为写锁；
- 线程 A 等待线程 B 释放读锁才能拿到写锁；
- 线程 B 同样等待线程 A 释放读锁才能拿到写锁；
- **两者陷入互相死锁等待，系统永久卡死！** 因此 JUC 在底层设计上从根源上禁止了锁升级。

## 3. StampedLock：JDK 8 乐观读（Optimistic Read）黑科技

`ReentrantReadWriteLock` 虽然提升了读并发，但仍有一个痛点：**在有大量高频读线程存在时，写线程可能会被持续饥饿阻断，很久都拿不到写锁**。

JDK 8 引入了 **`StampedLock`**：
- 它提供了 **乐观读（`tryOptimisticRead()`）**：读取时**完全不加任何锁，不阻塞任何写操作**！
- 只是返回一个代表版本戳记的 `stamp` 凭证；
- 读取完成后，通过 `validate(stamp)` 检验该戳记在读取期间是否被其他写线程篡改过：
  - 若未被篡改：本次读取直接成功，**开销无限逼近无锁代码**！
  - 若被篡改：优雅降级升级为普通的悲观读锁重新读取。

│ 工具组件           │ 核心语义与工业级应用场景                                 │
├────────────────────┼────────────────────────────────────────────────────────┤
│ CountDownLatch     │ 倒计时门闩。一个或多个线程等待其他 N 个前置任务全部完成   │
│                    │ (一次性用品，计数器清零后不可复用，如主线程等待3个微服务RPC)│
├────────────────────┼────────────────────────────────────────────────────────┤
│ CyclicBarrier      │ 循环栅栏。一组固定数量的线程互相等待，全员到达屏障后再开闸│
│                    │ (支持循环重复使用，可指定开闸回调，如分段并行计算汇总)    │
├────────────────────┼────────────────────────────────────────────────────────┤
│ Semaphore          │ 信号量。控制同时访问特定物理资源的并发线程数 (限流许可证) │
│                    │ (如数据库连接池、网关限流、底层高耗算力并发度限制)        │
