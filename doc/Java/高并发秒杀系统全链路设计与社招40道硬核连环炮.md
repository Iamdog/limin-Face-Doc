# 高并发秒杀系统全链路设计与社招40道硬核连环炮

秒杀（Flash Sale）系统是互联网高并发、大流量架构的极致演练场。在瞬时数百万 QPS 的冲击下，系统面临**带宽打满、热点行锁竞争、库存超卖、恶意刷单、级联雪崩**等全方位挑战。本文将给出经过大厂实战验证的**全链路秒杀漏斗架构**，并汇总呈现**社招 40 道跨越 Java、MySQL、并发、JVM 与分布式的硬核连环追问**。

---

## 核心底层机制与全景架构

### 1. 秒杀全链路“漏斗式”防护架构

秒杀的核心设计哲学是：**分层过滤、动静分离、充分利用缓存，将 99.9% 的无效流量在上游全部拦截，只将有效写请求最终推入持久化层**。

```mermaid
flowchart TD
    User[用户海量瞬时请求 100W+ QPS] --> CDN[1. 边缘节点 CDN / Nginx<br/>静态资源缓存, 验证码错峰, 答题防刷]
    CDN -->|过滤 80% 请求, 剩余 20W QPS| Gateway[2. API 网关 Spring Cloud Gateway<br/>动态秒杀地址加盐校验, IP/UID 令牌桶限流]
    Gateway -->|过滤 90% 请求, 剩余 2W QPS| AppCluster[3. 业务服务集群 (JVM 本地内存标记)<br/>若本地标记 soldOut=true 则直接本地返回 '已售罄']
    AppCluster -->|未售罄请求| RedisCluster[4. Redis + Lua 脚本原子操作<br/>一人一单防刷校验 + 原子预扣减库存]
    RedisCluster -->|扣减成功, 剩余 1000 QPS| MQ[5. 消息队列 RocketMQ / Kafka<br/>异步削峰解耦, 缓冲下单请求]
    MQ -->|平稳消费 500 QPS| DBWorker[6. 订单处理服务]
    DBWorker -->|物理终极扣减| MySQL[7. MySQL 数据库<br/>UPDATE stock SET stock = stock - 1 WHERE id = ? AND stock >= 1]
```

## 核心技术专题深度拆解

### 1. 秒杀地址动态化与防刷（URL Hiding）
- **痛点**：防止黄牛在活动开始前提前抓包抓到下单接口，使用自动化脚本刷接口。
- **解决方案**：
  1. 活动未开始前，秒杀接口不存在；
  2. 活动倒计时结束时，客户端调用服务端接口获取一个动态生成的随机密钥：
     $$\text{PathToken} = \text{MD5}(\text{userId} + \text{goodsId} + \text{Salt} + \text{CurrentTimestamp})$$
  3. 服务端将该 Token 存入 Redis 并设置 60 秒有效期；
  4. 下单接口形如 `/seckill/{pathToken}/order`，网关或应用拦截器校验 PathToken 必须与 Redis 中一致，否则判定为非法请求直接丢弃。

---

### 2. 库存防超卖（Anti-Oversold）双重保险

#### 第一道防线：Redis + Lua 脚本原子预扣减
单靠 Java 业务代码中 `get("stock")` 然后判断并 `set("stock", stock - 1)`，在高并发下必然发生竞态条件导致严重超卖。必须使用 Lua 脚本保证**原子性判断与扣减**：

```lua
-- KEYS[1]: 库存Key, KEYS[2]: 一人一单记录Key (Set)
-- ARGV[1]: 用户ID, ARGV[2]: 购买数量
local stockKey = KEYS[1]
local userSetKey = KEYS[2]
local userId = ARGV[1]
local count = tonumber(ARGV[2])

-- 1. 校验是否已购买 (一人一单)
if redis.call('SISMEMBER', userSetKey, userId) == 1 then
    return -1 -- 重复购买错误码
end

-- 2. 校验库存是否充足
local currentStock = tonumber(redis.call('GET', stockKey) or '0')
if currentStock < count then
    return 0 -- 库存不足
end

-- 3. 原子预扣减库存并记录购买用户
redis.call('DECRBY', stockKey, count)
redis.call('SADD', userSetKey, userId)
return 1 -- 预扣减成功
```

#### 第二道防线：MySQL 数据库行级乐观锁防御
在异步下单入库时，物理 SQL 必须增加条件保障：
```sql
UPDATE seckill_goods 
SET stock = stock - #{buyCount}, version = version + 1
WHERE goods_id = #{goodsId} 
  AND stock >= #{buyCount}; -- 核心底线: 数据库行级锁防御超卖
```
利用 InnoDB 的行级排他锁特性，如果受影响行数为 0，说明库存已被扣光，回滚业务并向用户提示抢购失败。

## 社招 40 道硬核高频连环炮全景串联

为帮助资深工程师在社招面试中从容应对跨领域追问，以下按**面试真实交锋节奏**组织 40 道连环追问与核心采分点：

### 第一部分：Java 基础、集合与语言深水区（Q1 ~ Q8）
1. **Q: `String s = new String("abc")` 创建了几个对象？在什么内存区域？**  
   *A:* 1个或2个。若常量池中已有 `"abc"`，仅在堆中创建一个 String 实例；若没有，先在堆中字符串常量池创建字面量对象，再在堆中创建引用对象。
2. **Q: 为什么 Java 泛型是伪泛型？类型擦除后反射为什么还能获取泛型参数类型？**  
   *A:* 编译后类型信息被擦除替换为上限（Object）。但类、字段、方法签名中的泛型元数据被保存在 Class 文件的 `Signature` 属性中，通过 `ParameterizedType` 反射可读取。
3. **Q: JDK 动态代理为什么必须基于接口？**  
   *A:* 生成的 `$Proxy0` 类已经显式继承了 `java.lang.reflect.Proxy`。Java 遵循单继承语法限制，无法再继承目标类，只能通过实现共同接口代理。
4. **Q: CGLIB 生成代理的原理是什么？为什么比 JDK 反射快？**  
   *A:* 基于 ASM 修改字节码生成目标类的子类；利用 FastClass 机制建立方法下标索引映射表，直接通过方法索引跳转调用，避开了反射（Method.invoke）的调用开销。
5. **Q: Java SPI 机制有什么缺陷？Dubbo 是如何针对性优化的？**  
   *A:* JDK SPI 必须全量遍历实例化配置中的所有类，不支持按需加载和依赖注入；Dubbo SPI 引入了 KV 键值对寻址、自适应扩展点（`@Adaptive`）和自动 IOC 包装类。
6. **Q: HashMap 1.8 为什么引入红黑树？树化和退化的阈值为什么是 8 和 6？**  
   *A:* 防止 Hash 冲突碰撞导致链表过长退化为 $O(N)$；阈值 8 是基于泊松分布计算得出（碰撞 8 次的概率低于千万分之一）；退化阈值 6 是为了在 8 和 6 之间保留 2 个缓冲带，防止在临界值频繁插删引发剧烈的树化与链表化震荡。
7. **Q: HashMap 扩容时高低位链表转移为什么不需要重新计算 hash？**  
   *A:* 数组容量始终是 2 的整数次幂，扩容后高位仅多出 1 位（二进制掩码）。只需判断 `hash & oldCap` 是否为 0：为 0 则保留在原索引下标，为 1 则移动到 `原索引 + oldCap`。
8. **Q: ConcurrentHashMap 1.8 为什么废弃分段锁（Segment）？它的扩容协助机制是怎样的？**  
   *A:* 细化锁粒度（由分段锁降低到 Node 节点锁），利用 CAS + `synchronized` 减少内存占用；扩容时设置 `ForwardingNode`（hash=-1），支持多线程并发迁移 Transfer，协同分担扩容任务。

### 第二部分：并发编程 JMM 与锁机制（Q9 ~ Q16）
9. **Q: 什么是指令重排？JMM 的 Happens-Before 原则如何保证可见性与有序性？**  
   *A:* 编译器和 CPU 为优化执行效率改变指令执行顺序；Happens-Before 是跨线程内存可见性的规则集合（程序顺序规则、锁规则、volatile 规则、线程启动与终止规则），底层通过编译期插入特定的 Memory Barrier 内存屏障实现。
10. **Q: `volatile` 能保证原子性吗？底层汇编 `lock addl` 是干什么的？**  
    *A:* 不能保证原子性（如 `i++` 依然多线程不安全）；x86 汇编生成的 `lock addl $0x0, (%rsp)` 指令会锁住总线或缓存行，将当前处理器写缓冲区强制刷新到主存，并使其他 CPU 对应的 L1/L2 缓存行失效（MESI 协议）。
11. **Q: CAS 产生的 ABA 问题如何彻底根除？**  
    *A:* 使用带有版本号（stamp/version）的原子引用类，如 `AtomicStampedReference`，比对引用值的同时比对版本递增戳。
12. **Q: synchronized 锁升级全过程是怎样的？能降级吗？**  
    *A:* 无锁 $\rightarrow$ 偏向锁（记录线程ID） $\rightarrow$ 轻量级锁（CAS 自旋，BasicObjectLock 栈帧拷贝） $\rightarrow$ 重量级锁（ObjectMonitor 互斥排队）；重量级锁在 JVM 处于安全点（SafePoint）且 Monitor 不再被任何线程持有是允许被 GC 降级的。
13. **Q: AQS（AbstractQueuedSynchronizer）的底层核心数据结构是什么？**  
    *A:* 一个 `volatile int state` 记录同步状态，配合基于双向链表的变种 CLH 队列（Node 节点维护 waitStatus、prev、next、thread），利用 CAS 驱动入队与出队唤醒。
14. **Q: ThreadLocal 为什么会发生内存泄漏？阿里 TTL 是如何解决线程池传值的？**  
    *A:* ThreadLocalMap 的 Entry 继承自 `WeakReference`，Key 是弱引用，Value 是强引用。GC 后 Key 变 null，但 Value 强引用随线程池复用长期存在。TTL（TransmittableThreadLocal）在任务提交到线程池时做上下文抓取快照（Replay/Restore），实现跨线程池无缝透传。
15. **Q: 线程池核心线程数（corePoolSize）如何科学配置？**  
    *A:* CPU 密集型：$\text{CPU} + 1$；IO 密集型：$\text{CPU} \times \left(1 + \frac{\text{WaitTime}}{\text{ComputeTime}}\right)$ 或 $\text{CPU} \times 2$；结合动态线程池（如 Hippo4j）根据线上队列排队监控动态调整。
16. **Q: 线程池的饱和拒绝策略有哪些？生产上如何自定义？**  
    *A:* AbortPolicy（抛异常）、CallerRunsPolicy（调用者主线程执行）、DiscardOldestPolicy（丢弃最旧）、DiscardPolicy（静默丢弃）；生产推荐自定义策略：输出报警日志、打入本地磁盘队列或降级写入 Kafka。

### 第三部分：JVM 底层原理与线上排障（Q17 ~ Q24）
17. **Q: 对象的物理内存布局包含哪三部分？指针压缩（CompressedOops）为什么超过 32GB 会失效？**  
    *A:* 对象头（Mark Word + Klass Word）、实例数据（Instance Data）、对齐填充（Padding）；指针压缩基于 8 字节对齐，32 位地址最大寻址 $2^{32} \times 8\text{ B} = 32\text{ GB}$。超过 32GB 必须回退为 64 位无压缩指针寻址。
18. **Q: 类的双亲委派机制是什么？哪三大场景打破了双亲委派？**  
    *A:* 类加载请求优先委托父加载器，父加载器无法加载才由子加载器自行加载；打破场景：1. SPI / JDBC 驱动（Thread Context ClassLoader 上下文类加载器）；2. Tomcat 容器 WebAppClassLoader 隔离不同应用 Jar 包；3. OSGi 模块化热插拔。
19. **Q: G1 垃圾收集器的核心优势是什么？Card Table 与 RSet 的作用？**  
    *A:* 基于 Region 划分内存，支持可预测的停顿时间模型（`-XX:MaxGCPauseMillis`）；Card Table 记录老年代向年轻代的跨代引用；RSet（Remembered Set）避免全堆扫描，记录“谁引用了我”。
20. **Q: ZGC（Z Garbage Collector）为什么能做到 Stop-The-World 低于 1ms？**  
    *A:* 采用**着色指针（Colored Pointers）**与**读屏障（Load Barrier）**，将标记、转移（整理）等耗时核心阶段全部实现为**并发执行**，停顿时间与堆大小完全解耦。
21. **Q: 什么是伪共享（False Sharing）？Java 8 是如何解决的？**  
    *A:* 多线程并发修改位于同一个 CPU 缓存行（64 字节）内的不同变量，导致 L1/L2 缓存行频繁无效震荡；Java 8 引入 `@sun.misc.Contended` 注解并在前后自动填充 128 字节空字节规避。
22. **Q: 线上服务 CPU 100% 突发排查 SOP 步骤？**  
    *A:* 1. `top` 找出最高 CPU 占用 PID；2. `top -Hp <PID>` 找出最高 CPU 线程 TID；3. `printf "%x\n" <TID>` 转换为十六进制；4. `jstack <PID> | grep <HEX_TID> -A 30` 定位问题代码行（通常是死循环或频繁正则匹配）。
23. **Q: 线上服务突发 OOM（Java heap space）排查 SOP？**  
    *A:* 提前配置 `-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/data/dump/`；使用 Eclipse MAT 或 JProfiler 打开 hprof 快照；查看 Leak Suspects 怀疑单，排查最大 Retained Size 对象树与 GC Root 强引用链。
24. **Q: Arthas 在排障中的杀手级命令有哪些？**  
    *A:* `thread -n 3`（查看最忙线程）、`watch`（抓取方法入参和返回值）、`trace`（分析方法内部每一步耗时）、`jad`（反编译内存中运行的字节码）、`retransform`（热更新 Class 字节码）。

### 第四部分：MySQL 存储与高并发事务（Q25 ~ Q32）
25. **Q: 为什么 MySQL 索引底层选用 B+ 树而不是 B 树或红黑树？**  
    *A:* B+ 树非叶子节点只存索引键不存数据，单页（16KB）能容纳更多分支，树高更矮（千万级仅需 3~4 次磁盘 I/O）；叶子节点之间有双向链表相连，极大提升范围查询和分页性能。
26. **Q: 深度推导：千万级数据的 B+ 树高度为什么通常只有 3 层？**  
    *A:* 根节点 16KB，假设主键 bigint(8B)+指针(6B)=14B，可存约 1170 个指针；两层非叶子节点索引能力达 $1170 \times 1170 \approx 136\text{ 万}$；叶子节点按单行 1KB 算可存 16 条；三层树总容量达 $1170 \times 1170 \times 16 \approx 2190\text{ 万}$ 行。
27. **Q: InnoDB 为什么强制建议单表必须有自增主键？UUID 作主键有何致命缺陷？**  
    *A:* 自增主键写入始终追加在叶子节点末尾，只发生顺序写；UUID 离散无序，写入会导致频繁的**页分裂（Page Split）**与碎片产生，引发大量随机 I/O，聚簇索引体积膨胀。
28. **Q: 事务 ACID 四大特性底层分别由什么机制保障？**  
    *A:* A（原子性）由 Undo Log 保障；C（一致性）由其他三大特性与业务逻辑共同保障；I（隔离性）由 MVCC 多版本并发控制与锁机制保障；D（持久性）由 Redo Log + Crash-Safe 保障。
29. **Q: Redo Log 与 Binlog 的两阶段提交（2PC）崩溃恢复机制如何保证一致性？**  
    *A:* Prepare 阶段写入 Redo Log；写 Binlog；Commit 阶段写入 Commit 标记。崩溃恢复时：若 Redo Log 处于 Prepare 状态，会检查对应的 XID 在 Binlog 中是否存在。若存在则提交，若不存在则利用 Undo Log 回滚。
30. **Q: MVCC 的核心底层原理是什么？ReadView 的四个核心属性？**  
    *A:* 依赖 Undo Log 版本链与每行隐藏字段（`trx_id`, `roll_ptr`）；ReadView 核心：`m_ids`（活跃事务列表）、`min_trx_id`、`max_trx_id`（预分配下一个事务ID）、`creator_trx_id`；RC 级别每次 SELECT 都生成新的 ReadView，RR 级别仅在第一次 SELECT 时生成并复用。
31. **Q: Next-Key Lock 是如何解决 RR 隔离级别下的幻读的？加锁规则是什么？**  
    *A:* Next-Key Lock = 记录锁（Record Lock） + 间隙锁（Gap Lock），锁定左开右闭区间；等值查询唯一索引降级为记录锁；等值查询非唯一索引退化向右遍历到首个不匹配记录退化为间隙锁；范围查询锁定整个扫描涉及的间隙。
32. **Q: 千万级大表深度分页 `LIMIT 10000000, 10` 为什么极慢？如何优化？**  
    *A:* 优化器需扫描 10000010 条完整数据行并丢弃前 1000 万条，产生千万次无用回表；优化：子查询延迟关联（`JOIN (SELECT id FROM t LIMIT 10000000, 10) AS tmp USING(id)`）先利用覆盖索引极速取出 ID，再回表 10 行。

### 第五部分：分布式、微服务、中间件与高并发系统（Q33 ~ Q40）
33. **Q: Spring 三级缓存中，为什么二级缓存无法完全替代三级缓存？**  
    *A:* 为了遵循 Spring 设计契约：AOP 代理创建通常延迟在初始化之后统一生成。三级缓存通过 ObjectFactory 闭包实现按需动态提前生成代理，避免在没有循环依赖时过早破坏生命周期。
34. **Q: 声明式事务 `@Transactional` 为什么在内部方法自调用时会失效？**  
    *A:* 代理对象拦截机制被绕过。类内部 `this.innerMethod()` 直接调用的是 JVM 堆中原生对象，不会走 CGLIB/JDK 代理链，无法触发 `TransactionInterceptor`。
35. **Q: Netty 的 Reactor 主从多线程模型与零拷贝体系是怎样的？**  
    *A:* BossGroup（单/多线程）专职 Accept 握手并分发连接，WorkerGroup（多线程）通过 Selector 轮询读写事件；零拷贝包含：Linux `sendfile`（`DefaultFileRegion`）、`CompositeByteBuf` 逻辑组合、`ByteBuf.slice` 逻辑切片。
36. **Q: Redis 为什么单线程执行命令性能极高？Redis 6.0 引入多线程打破单线程了吗？**  
    *A:* 纯内存操作、非阻塞 epoll I/O 多路复用、无多线程锁竞争与上下文切换；Redis 6.0 多线程仅用于网络 I/O 读写与数据包编解码，核心数据命令的执行依然是单线程，未破坏命令串行安全性。
37. **Q: Redis 与 MySQL 双写一致性为什么推荐 Cache Aside Pattern（先更新 DB 再删缓存）？**  
    *A:* 先删缓存会导致并发读请求把 DB 旧数据重新写回缓存产生永久脏读；先更 DB 再删缓存虽然在极端高并发下有微小竞态风险，但结合 Canal 监听 Binlog 异步重试删除，可完美达成最终一致性。
38. **Q: Seata AT 模式的一阶段本地事务提交与二阶段回滚是如何做到无侵入的？**  
    *A:* 一阶段拦截业务 SQL 生成前后镜像（before/after image），将镜像作为 `undo_log` 与业务在同一个本地事务提交并向 TC 申请全局锁；二阶段回滚时先比对当前数据与 after image 防脏写，再根据 before image 执行反向 SQL 还原数据。
39. **Q: 消息队列（Kafka/RocketMQ）如何保证全链路“消息零丢失”？**  
    *A:* 生产端 `acks=all` + 带回调重试；Broker 端开启同步刷盘（SYNC_FLUSH） + 跨节点同步复制（min.insync.replicas=2）；消费端关闭自动提交 offset，在业务处理成功并落库后手动 ACK。
40. **Q: 突发遭遇千万级消息积压（Message Lag），为什么扩容 Consumer 节点可能完全无效？如何应急治理？**  
    *A:* 一个分区（Partition/Queue）同一时刻只能被单消费者组下的一个消费者消费。若 Partition 只有 8 个，扩容 32 个 Consumer 导致 24 个饥饿空转。应急 SOP：扩容临时 Topic 分区数到 64，上线纯搬运程序将积压数据快速轮询转储至新 Topic，下游部署 64 个节点全力消费。
