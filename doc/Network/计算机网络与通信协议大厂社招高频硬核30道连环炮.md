# 计算机网络与通信协议大厂社招高频硬核 30 道连环炮全景通关

本专题面向 **3~5 年及以上后端、全栈及架构师岗位**，深入汇总一线大厂（字节、阿里、腾讯、美团）在网络通信领域考核频次最高、深水区挖掘最严苛的 **30 道硬核高频连环追问**。题目直击 TCP/UDP 底核、HTTP 协议演进、DNS 根域名解析、TLS 加密安全与线上网络故障排查。

---

## 1. 传输层 TCP / UDP 核心连环炮（第 1 ~ 10 题）

### Q01: TCP 的三次握手过程中，每次握手分别可以携带数据吗？
> **答题要点**：
> 第一、二次握手绝对**不能携带数据**（若允许携带数据，黑客可利用 SYN 洪水攻击在未建立连接前耗尽服务端内存）。
> **第三次握手可以携带数据**，因为此时客户端已经确信服务端的收发能力完全正常，且自身状态已进入 `ESTABLISHED`。

### Q02: 什么是 SYN Flood（SYN 洪水攻击）？Linux 内核如何防御？
> **答题要点**：
> 黑客伪造海量不存在的 IP 地址向服务端发送 SYN 报文，服务端回复 SYN+ACK 后迟迟收不到第三次 ACK，导致**半连接队列（SYN Queue）**被打满，正常用户的连接请求被拒绝。
> **防御机制**：开启 `net.ipv4.tcp_syncookies = 1`。当半连接队列满时，内核不直接丢弃，而是利用时间戳、四元组等信息计算生成一个加密 Cookie 作为初始序列号发回，客户端回复 ACK 时校验该 Cookie 即可完成连接，完全绕过了半连接队列的内存占用。

### Q03: TCP 的流量控制（Flow Control）与拥塞控制（Congestion Control）的区别？
> **答题要点**：
> - **流量控制（滑动窗口）**：解决**点对点（发送方与接收方）**的处理能力不匹配问题，通过接收方通告的窗口大小（rwnd）限制发送速度，防止接收方缓冲区溢出；
> - **拥塞控制（拥塞窗口 cwnd）**：解决**整个网络链路中路由器与交换机拥堵**的全局问题，包含四大算法：慢启动、拥塞避免、快重传与快恢复（或新一代 BBR 算法）。

### Q04: 为什么 TCP 的 TIME_WAIT 状态是 2MSL 而不是 1MSL？
> **答题要点**：
> MSL（Maximum Segment Lifetime）是报文在网络中的最大存活时间。2MSL 刚好允许一个报文“往返一次”。若主动关闭方发送的第四次 ACK 在网络中丢失，被动方重发 FIN 最多需要 1MSL 到达，主动方在 2MSL 内仍能收到该重发的 FIN 并再次补发 ACK，确保连接安全关闭。

### Q05: 生产服务器出现大量 CLOSE_WAIT 状态，可能是什么原因？
> **答题要点**：
> `CLOSE_WAIT` 出现在被动关闭方。原因是：**服务端收到了客户端发来的 FIN，操作系统内核自动回复了 ACK，但上层业务应用程序由于代码死锁、线程池卡死或数据库连接耗尽，未能及时调用 `socket.close()` 发送自己的 FIN**。排查重点在业务层代码的 I/O 泄漏。

## 2. HTTP 协议演进与现代特性（第 11 ~ 20 题）

### Q06: HTTP/1.1 对比 HTTP/1.0 做了哪些重大演进？
> **答题要点**：
> 1. **默认开启长连接（Keep-Alive）**：允许多个请求复用同一个 TCP 连接；
> 2. **引入管道化（Pipelining）**：允许在收到前一个响应之前发出下一个请求（但存在队头阻塞）；
> 3. **强制 Host 请求头**：使得单台物理服务器虚拟主机能够托管多个不同域名的站点；
> 4. **引入 100 Continue 状态码与分块传输（Chunked Transfer）**。

### Q07: HTTP/2 的多路复用（Multiplexing）是如何解决应用层队头阻塞的？
> **答题要点**：
> HTTP/2 引入了**二进制分帧层（Binary Framing Layer）**。所有的 HTTP 报文被切片成带有流 ID（Stream ID）的独立帧（Frame）。在同一个 TCP 连接上，多个不同的请求与响应的帧可以无序交织并发传输，客户端与服务端通过 Stream ID 重新组装，彻底消除了 HTTP/1.1 中必须等待前一个响应返回才能处理下一个请求的应用层队头阻塞。

### Q08: 为什么说 HTTP/2 解决了应用层队头阻塞，但未解决 TCP 层的队头阻塞？
> **答题要点**：
> HTTP/2 底层依然是单条 TCP 连接。TCP 是严格保证报文顺序的协议。一旦网络中发生丢包，后续所有的 TCP 报文段都必须在操作系统的接收缓冲区中排队等待丢失的包被重传确认，导致整个 TCP 连接上的**所有 HTTP/2 流全部被挂起等待**。

### Q09: HTTP/3（QUIC）为什么彻底转向了 UDP？
> **答题要点**：
> HTTP/3 基于 Google 主导的 **QUIC 协议（运行在 UDP 之上）**：
> 1. **彻底解决 TCP 队头阻塞**：在应用层实现了独立的流管理，某个流丢包仅影响该流本身，其他流完全不受影响；
> 2. **0-RTT 极速连接**：将传输层握手与加密握手（TLS 1.3）合并；
> 3. **连接迁移（Connection Migration）**：使用 64 位的连接 ID（Connection ID）而非传统的四元组。当手机从 WiFi 切换到 5G 移动网络时，IP 发生变更但连接不会中断，零重连无感切换。

### Q10: HTTP 强缓存（Cache-Control）与协商缓存（ETag/Last-Modified）的区别？
> **答题要点**：
> - **强缓存**：`Cache-Control: max-age=3600`。在有效期内，浏览器**完全不向服务器发起任何网络请求**，直接从内存（memory cache）或磁盘（disk cache）读取资源，返回 `200 (from memory/disk cache)`；
> - **协商缓存**：强缓存失效后，浏览器携带 `If-None-Match (ETag)` 或 `If-Modified-Since` 向服务端询问。若文件未变，服务端直接返回 `304 Not Modified`（无响应体），通知浏览器继续使用已有缓存；若已变动则返回全新内容 `200 OK`。

## 3. 网络安全、DNS 与现场排错（第 21 ~ 30 题）

### Q11: 浏览器在地址栏输入一个 URL 并回车，一直到页面展现，经历了哪些网络阶段？
> **答题要点**：
> 1. URL 解析与本地 HSTS 检查；
> 2. 递归 DNS 查询（浏览器缓存 $\to$ 系统 hosts $\to$ 本地 Local DNS $\to$ 根/顶级/权威域名服务器）；
> 3. TCP 三次握手建立连接；
> 4. TLS 握手协商密钥（若是 HTTPS）；
> 5. 发送 HTTP 请求报文；
> 6. 服务端处理并返回响应报文；
> 7. 浏览器渲染（解析 HTML 构建 DOM 树 $\to$ 解析 CSS 构建 CSSOM $\to$ 生成 Render 树 $\to$ 布局 Layout $\to$ 绘制 Paint）；
> 8. 资源加载完毕后根据情况断开 TCP 连接（四次挥手）。

### Q12: 什么是跨域（CORS）？浏览器的“预检请求（OPTIONS）”发生在什么情况下？
> **答题要点**：
> 跨域是由浏览器的**同源策略（Same-Origin Policy，协议/域名/端口必须全同）**限制引起的。
> **预检请求**：当请求属于“非简单请求”（如使用了 `PUT/DELETE` 方法、自定义请求头如 `Authorization`、或 `Content-Type: application/json`）时，浏览器在发送真实请求前会自动发出一次 `OPTIONS` 请求，询问服务端是否允许跨域访问；服务端返回允许的 Origin、Methods 和 Headers 后，真实请求才会正式发出。

### Q13: 前端如何防范 XSS（跨站脚本攻击）与 CSRF（跨站请求伪造）？
> **答题要点**：
> - **XSS 防范**：对用户输入进行严格 HTML 实体转义编码；配置 HTTP 响应头 `Content-Security-Policy (CSP)` 限制脚本来源；对敏感 Token 开启 `HttpOnly` 防止 JS 脚本读取；
> - **CSRF 防范**：Cookie 属性配置 `SameSite=Strict / Lax` 禁止第三方外链自动携带 Cookie；前后端交互采用自定义 Header（如 `X-Requested-With`）或 CSRF Token 校验。

### Q14: 什么是 DNS 劫持与 DNS 污染？移动端如何通过 HttpDNS 解决？
> **答题要点**：
> - 运营商 Local DNS 缓存污染或恶意篡改解析结果，将用户导向钓鱼网站或广告页；
> - **HttpDNS**：移动端 App 绕过系统传统的 UDP 53 端口 Local DNS 查询，改用 **HTTPS 协议向权威服务提供商的 HTTP API 发起查询**，直接拿到真实服务器 IP，从根源上杜绝了运营商 DNS 劫持与跨网调度延迟。

### Q15: 排查网络连通性时，`ping`、`traceroute`、`telnet` 与 `curl` 的侧重点是什么？
> **答题要点**：
> - `ping`：基于 ICMP 协议，测试网络层 IP 是否可达及往返延迟（若禁 ping 则失效）；
> - `traceroute`：基于 TTL 逐跳递增原理，探测经过的所有路由器节点，定位是哪一跳路由丢包；
> - `telnet / nc`：测试传输层特定的 TCP 端口是否对外开放监听；
> - `curl -Iv`：测试应用层 HTTP/HTTPS 状态码、TLS 握手耗时与响应头。
