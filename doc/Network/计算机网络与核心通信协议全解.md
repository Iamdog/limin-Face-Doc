## 一、 TCP 核心状态机与连接治理

### 1. 为什么是“三次握手”与“四次挥手”？
- **为什么不是两次握手？**
  - **防止历史失效的连接请求突然传到服务端引发资源浪费**：客户端发出的第一个 SYN 包在网络阻塞延迟，重发第二个 SYN 成功连接并传输完毕后，第一个迟到的 SYN 到达服务端。若为两次握手，服务端直接建立连接等待数据，白白浪费内存与端口资源；三次握手能让客户端收到确认时发现是历史连接而主动发送 RST 中断。
  - **双方确认彼此的收发能力正常**并同步初始序列号（ISN）。
- **为什么挥手需要四次？**
  - TCP 是**全双工通信**。客户端发送 FIN 仅表示“客户端不再发送数据，但仍能接收数据”；服务端收到后先回复 ACK，待服务端自身剩余数据发送完毕后发送 FIN；ACK 与 FIN 有时可合并，并非总是四个报文段。

### 2. 生产级故障排查：海量 `TIME_WAIT` 与 `CLOSE_WAIT`

```text
客户端                                             服务端
  │                                                  │
  ├─── FIN (主动关闭方) ─────────────────────────────>│ 
  │<── ACK ──────────────────────────────────────────┤ 处于 CLOSE_WAIT
  │                                                  │ (等待应用释放连接)
  │<── FIN ──────────────────────────────────────────┤ 
  ├─── ACK ─────────────────────────────────────────>│ 
  │ 进入 TIME_WAIT (持续 2MSL)
```

#### ① 海量 `TIME_WAIT`（主动关闭方产生）
- **现象**：高并发下客户端或反向代理 Nginx 产生数万 `TIME_WAIT`，导致局部端口耗尽，无法发起新连接。
- **根因**：开启了 HTTP 短连接（未开启 Keep-Alive），客户端请求完毕后主动关闭连接；保留 TIME_WAIT 是为了应对最后 ACK 丢失的重传 FIN，并避免旧报文影响新连接；具体持续时间依系统实现，不把 2MSL 当作固定通用 60 秒。
- **先做治理再考虑内核参数**：确认连接复用、响应体关闭、流量和可用临时端口；TIME_WAIT 较多本身可能正常。`tcp_tw_reuse` 等参数语义和默认值随内核变化，需结合当前系统与拓扑测试，不能直接套用某组 sysctl 作为通用修复。

#### ② 海量 `CLOSE_WAIT`（被动关闭方产生，严重线上故障！）
- **根因**：客户端已经主动关闭了连接，但**服务端的应用程序代码中没有调用 `socket.close()`**（如数据库连接池未归还、线程阻塞在某处、IO 流未在 `finally` 中关闭）。
- **解决**：这是典型的**代码级连接泄漏**！排查定位未关闭连接的线程堆栈，增加超时主动释放。

## 二、 HTTPS 底层加密链路与移动端 SSL Pinning 防抓包

### 1. TLS 1.3 混合加密握手模型
1. **密钥协商**：完整 TLS 1.3 握手通常通过临时 (EC)DHE 共享秘密并经 HKDF 派生握手和应用流量密钥；不能简单套用旧版本的 RSA 加密 Pre-Master Secret 模型，PSK/恢复握手还有不同路径。
2. **身份认证**：证书链和 CertificateVerify 证明服务端身份，客户端还要验证域名、有效期和信任链。
3. **数据保护**：应用数据通常使用 AES-GCM 或 ChaCha20-Poly1305 等 AEAD；恢复与 0-RTT 有额外重放边界。

---

### 2. 移动端安全：Android OkHttp 实现 SSL Pinning（证书锁定）

黑产常用 Charles/Fiddler 在手机安装自签名根证书截获请求。可按威胁模型评估公钥 pinning，作为正常证书链与主机名校验之外的限制。要使用真实公钥哈希、备用 pin 和证书轮换预案；示例中的 AAAAA 占位值不能用于实际请求：

```kotlin
// OkHttpClient 开启证书锁定 MVP
val certificatePinner = CertificatePinner.Builder()
    // 绑定域名与公钥 SHA-256 签名 Hash
    .add("api.example.com", "sha256/AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=")
    .build()

val okHttpClient = OkHttpClient.Builder()
    .certificatePinner(certificatePinner)
    .build()
// pin 不匹配会拒绝请求；运行时被控制的客户端仍可能绕过校验
```

## 三、 跨域 CORS 的本质与 OPTIONS 预检请求避坑

### 1. 为什么带 Token 会触发两次网络请求（OPTIONS + 真实请求）？
浏览器出于同源策略（协议、域名、端口三者必须一致），将跨域请求分为：
- **简单请求**：方法为 `GET / POST / HEAD`，且 Header 仅包含标准头（`Accept`, `Content-Type: text/plain | application/x-www-form-urlencoded | multipart/form-data`）。
- **非简单请求**：包含**自定义 Header（如 `Authorization: Bearer ...`）** 或 `Content-Type: application/json`。

**浏览器在发送非简单请求前，必须先自动向服务端发送一个 `OPTIONS` 嗅探预检请求**，向服务端询问：“你是否允许我携带这些自定义头和跨域来源？”。服务端响应放行后，浏览器才会真正发送第二个实际业务请求。

---

### 2. 生产级优雅跨域配置（Spring Boot + Nginx 预检缓存）

#### ① 生产大坑：跨域导致预检请求翻倍，浪费网络吞吐
- **解决方案**：设置 `Access-Control-Max-Age` 缓存预检结果（如缓存 1 小时 3600 秒），在有效期内相同路径**不再反复触发 OPTIONS**！

#### ② Spring Boot 生产统一跨域配置
```java
@Configuration
public class CorsConfig implements WebMvcConfigurer {
    @Override
    public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("/**")
            .allowedOriginPatterns("https://*.example.com", "http://localhost:*") // 白名单
            .allowedMethods("GET", "POST", "PUT", "DELETE", "OPTIONS")
            .allowedHeaders("*")
            .allowCredentials(true) // 允许携带 Cookie / 凭证
            .maxAge(3600); // 核心：缓存 OPTIONS 预检请求 1 小时，大幅降低网络开销！
    }
}
```

## 四、 HTTP/1.1 vs HTTP/2 vs HTTP/3 演进

| 特性 | HTTP/1.1 | HTTP/2 | HTTP/3 |
| :--- | :--- | :--- | :--- |
| **底层传输协议** | 基于 TCP 字节流 | 基于 TCP 二进制分帧（Frame） | **基于 UDP 的 QUIC 协议** |
| **多路复用** | 不支持（依赖多建立 6 个 TCP 管道并发） | **支持**（单个 TCP 连接并发多个流 Stream） | 支持；多个流共享连接级拥塞控制等资源 |
| **队头阻塞 (HOL)** | 应用层队头阻塞 | **TCP 层队头阻塞**（单个丢包全阻塞重传） | 减少跨流传输队头阻塞；流内有序交付、拥塞及 QPACK 仍有等待边界 |
| **连接迁移** | 不支持（四元组变化必须重连） | 不支持 | 支持基于 Connection ID 的迁移；可达性、路径验证与实现会影响结果 |
| **头部压缩** | 纯明文冗余传输 | **HPACK 算法**（静态/动态索引表） | **QPACK 算法** |
